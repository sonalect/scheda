# 09. Isolation and perimeter

Document 9 of the Scheda package. Version 0.19, 19 October 2026.

What must not leak: network by default (**core**); isolated collections under `{vault}/.isolated/` (a gitignored nested git that never leaves the machine, owner-only Index of isolated Documents) and encryption of a collection's Document files, which is a separate property and applies to any one collection, isolated or not (**later**). Terms are in `02`. Declaration marks are in SCH-15 (isolation) and SCH-16 (encryption). Mirror traffic is in `04`. Codes: `ISO`. Phase **later** unless marked **core** or **agent**.

An assertion without a check is not a requirement.

---

## 1. Network

**ISO-1. No network unless opted in.** With `auto_sync` off and no `Scheda.Open` that clones, `Mirror.Pull`, `Mirror.Push`, or `Mirror.Sync`, Scheda does not open outbound connections for `Scheda.Open`, writes, `Index.Reindex`, or a search without an embedder. A network embedder is supplied by the caller (IDX-8). Git credentials are not stored in the Vault (`04`). *Check (**core**):* those operations succeed with the network disabled; a stub embedder that does not call out leaves the audit empty.

`Scheda.Open` with `OpenOptions.mirror` on a missing path and `auto_sync` are explicit exceptions (GIT-8, GIT-10). They still do not put host tokens in Document files.

---

## 2. Isolated collection (**later**)

The Vault is **one directory**. Isolated Documents are not a second `Scheda.Open` path elsewhere on disk.

This section is implemented in `scheda` without encryption: nested git, `0600`, no traffic with any remote, `Vault.Check` over that tree, and `journal` as well as `standard`. Isolated Documents are in the one Vault Index and are queryable by name; there is no nested Index (ISO-10 retired). The phase tag stays **later** for a reason: a binding does not need `.isolated/` to pass **core**, **search**, or **agent**. Section 3 (age encryption) is a separate property and a separate Cargo feature; a build without `encrypt` still passes this section.

**ISO-2. Nested git under `{vault}/.isolated/`, not a sibling Vault.** Declaration `isolated: true` (SCH-15) means Document files live at `{vault}/.isolated/{name}/`. Isolated Documents use the same names under that directory (`{id}` with `/` as directories, journal segments, `{declared id}` for `singleton`). The collection declaration stays in the main tree at `{vault}/{name}/.collection.yaml` (also `.yml` / `.json`) so a clone of the main Vault still lists the collection (ISO-3). The first `Scheda.Open` that creates a Vault writes `.gitignore` entries for `.scheda/` and `.isolated/` (GIT-13).

`{vault}/.isolated/` is a git working tree Scheda creates on the first isolated write (`Vault.CreateCollection` with `isolated`, or the first Document written to that collection). A write to an isolated collection is one commit of that nested repository, and `Collection.History` of its Documents reads it. File mode: owner-only (`0600` on Unix). On other systems Scheda does not change ACLs; the nested git and gitignore remain the perimeter. It is not required to exist for the main Vault to open, or for a query or search of non-isolated collections. Deleting `{vault}/.scheda/` does not delete `.isolated/` (the Index is disposable; isolated Documents are not).

`Vault.Check` reports it if the **parent** git index tracks any path under `.isolated/` (`git add -f` is not a perimeter). *Check (**later**):* fixture Vault with `.isolated/` gitignored; a query or search of a non-isolated collection returns no isolated Documents; the nested repository grows by one commit per write and is owner-only; a tracked `.isolated/` path is a `Check` problem (`tests/query.rs`: `an_isolated_collection_is_scanned_only_when_named_and_one_without_an_index_is_refused`; `tests/documents.rs`: `the_table_holds_for_an_isolated_collection`, `the_nested_repository_is_made_owner_only_by_the_first_write_that_needs_it`; `isolated::tests::a_tracked_isolated_path_breaks_the_perimeter`; `check::tests::a_tracked_isolated_path_and_a_wide_mode_are_reported`).

The caller uses the **same** `Vault`. `Vault.GetCollection(name)` for an isolated name is the opt-in for those Documents. `Vault.CreateCollection` with `isolated` writes the collection declaration in the main tree and creates the nested git if needed. A query that does not name an isolated collection returns nothing of theirs. Isolated Documents are in the one Index at `{vault}/.scheda/`, which is owner-only for that reason (ISO-4); there is no nested Index. `Index.Reindex` rebuilds that one Index from every collection it can read, isolated included. A batch does not mix isolated collections with the others (`Vault.BatchDocuments`: `INVALID_ARGUMENT`): they are two repositories. The declaration-file commit is the main repository's.

**ISO-6. Isolated collections never leave the machine.** `Mirror.Push`, `Mirror.Pull`, `Mirror.Sync`, and `auto_sync` work with the mirror of the Vault, which is the **main tree only**: Scheda never contacts a remote for `.isolated/`, whatever that nested repository has configured by hand. There is no call that reaches one, and no option that makes the mirror traverse the other tree (`push_isolated`, `pull_isolated`, and `sync_isolated` of `0.21` are gone). Isolated is for data that may be lost or rebuilt: a cache, a derived fold. Data that is private **and must survive** a lost machine goes into an **encrypted** collection of the main tree (SCH-16), which reaches the mirror as ciphertext only. What a consumer must weigh, and record in its own documents, is that ciphertext in a pushed history is permanent: a promise of the form "after this row is retired the identity behind it cannot be recovered" holds physically while the file sits on one disk that can be destroyed, and after a push it holds only while a key stays secret, because git history does not forget. *Check (**later**):* a push, a pull, and a sync after isolated writes do not call the network for `.isolated/`, with and without a nested `origin` (`tests/mirror.rs`: `no_call_contacts_a_nested_repository_under_isolated`; `tests/documents.rs`: `a_nested_repository_with_an_origin_is_never_contacted`).

**ISO-3. Agent sees isolation and encryption.** `Vault.ListCollections` lists isolated collections as isolated and encrypted ones as encrypted (the `CollectionDeclaration`), and does not list Projector columns or field names. A tool that scans broadly cannot reach isolated Documents: a query with no collection named excludes isolated collections, even though the one Index holds them (ISO-4), so surfacing them takes naming one. Reaching isolated Documents is `Vault.GetCollection(name)`; reaching an encrypted collection's bytes also needs the Vault's secret (ISO-5). *Check (**agent**):* agent tools that are not bound to that collection never return a fixture isolated value.

**ISO-4. No Index holds encrypted bytes; isolated values sit in an owner-only Index.** There is one Index per Vault, `{vault}/.scheda/`, and it covers every collection the build can read, isolated included. Identity and Projector-derived values from isolated Documents are therefore inside it, and that is safe for one reason only: the directory is owner-only (`0700` directories, `0600` files, on Unix) and gitignored, so it is readable by the owner and by nobody else, and it never leaves the machine (IDX-4, GIT-13). A mode wider than that is a `Vault.Check` problem.

No Index holds anything from an **encrypted** collection. The Index is plaintext on disk — owner-only, but plaintext — and an encrypted collection exists precisely because reading the disk as the owner is not supposed to be enough. `Index.Reindex` skips those collections and no write updates an entry for them.

State the consequence plainly, because a consumer may rely on the opposite: a backup that copies the Vault and deliberately skips `.isolated/` still carries those isolated values, in the Index. Deleting `{vault}/.scheda/` is safe (IDX-1) and is what removes them.

*Check:* the plaintext of an encrypted collection is not in the Index (`lexical::tests::the_plaintext_of_an_encrypted_collection_is_never_in_the_index`). *Check:* owner-only modes are applied after a write, and a wider mode on the Index directory is a `Vault.Check` problem with that path (`fs::tests::owner_only_modes_are_applied_and_checked`; `check::tests::a_tracked_isolated_path_and_a_wide_mode_are_reported`).

## 3. Encryption of a collection (**later**)

Encryption is a property of **one collection**, declared by its collection declaration (SCH-16), and it is independent of `isolated`: all four combinations are valid. A consumer can want ciphertext on disk for material it fully intends to publish — precisely so that a `Mirror.Push` is the backup and no directory has to be copied by hand — and can want a plain nested tree for something merely local. Unencrypted `.isolated/` remains valid (`0600`). Scheda does not encrypt a Vault, a tree, or a directory: it encrypts the Document files of the collections that ask for it, and nothing else in the working tree.

Encryption is offered for `standard` and `singleton`. An encrypted `journal` is `INVALID_ARGUMENT` when the declaration is read (SCH-16). Since no Index holds an encrypted collection (ISO-4), the ways in are `Collection.Get` by a known `id` and `Collection.GetMany`.

The capability is an opt-in Cargo feature, `encrypt`. A build without it answers `UNIMPLEMENTED` and must never hand a caller armor bytes dressed as a Document (`tests/documents.rs`: `an_encrypted_collection_in_a_build_without_the_feature_is_unimplemented`; `tests/open.rs`: `encryption_without_the_feature_is_unimplemented`).

**ISO-5. One secret on the Vault, for every encrypted collection.** `OpenOptions.encryption` (`Encryption`) carries the secret for this Vault; the message requires `passphrase` or `identity`. Unset: nothing is decrypted and nothing is encrypted, and an encrypted collection is `CRYPTO`. `Scheda.Open` never requires it, and plain collections work without it. Writing to an encrypted collection, `Collection.Get`, and a `GetMany` or `History` that asks for bytes **require** it, and without it those calls fail with `CRYPTO`; a `GetMany` listing of keys and revisions (`include_raw` unset) reads names only and works without it. There is no plaintext Document file in an encrypted collection at any moment, including during a write. One Vault carries one secret: two encrypted collections under different secrets need two Vaults. *Check (**later**):* a write then `Collection.Get` round-trips with the secret and the stored blob is age armor (`tests/documents.rs`: `the_table_holds_for_encrypted_collections`); `Get` and a write with a wrong secret are `CRYPTO` and store nothing (`tests/documents.rs`: `a_wrong_secret_is_crypto_and_stores_nothing`); a listing of keys works without the secret and one that asks for bytes is `CRYPTO` (`tests/reads.rs`: `include_raw_decrypts_and_history_gives_plain_bytes`); a missing secret is `CRYPTO` (`crypto::tests::a_missing_secret_is_crypto`).

**ISO-7. One secret, not a key pair in the API.** The caller passes either a **passphrase** or an **age identity** (private key file) as `OpenOptions.encryption` (`Encryption`). Scheda does not take separate “encrypt key” and “decrypt key” arguments. The secret is never written into the Vault working tree, `.isolated/`, or the Index. It must not arrive as a command-line argument, because argv is readable by every process on the machine: the CLI takes it from a file path or the environment (`14`). Scheda is not a KMS.

**The two forms do not cost the same, and the difference decides designs.** A passphrase is wrapped by age scrypt (ISO-8), and the derivation runs on **every Document encrypted or decrypted** — not once per Vault. Age picks a work factor deliberately near a second, because that is what makes a passphrase expensive to guess; a caller cannot opt out of it. So reading all the Documents of an encrypted collection under a passphrase costs about that per Document, and a hundred Documents cost a hundred times it. An identity is X25519: an ephemeral key agreement, microseconds, no derivation. A one-off command may carry a passphrase; anything that reads more than a handful of Documents, and any long-running process on a latency budget, carries an identity. Scheda does not cache a derived key to paper over this: caching it would mean holding the unwrapped key for the life of the Vault, which is a different security decision than the caller made when they chose a passphrase. *Check:* the secret is not in the armor (`crypto::tests::the_secret_is_not_in_the_armor`); grep of the Vault working tree, `.isolated/`, and the Index does not contain the passphrase or identity bytes used in the test.

**ISO-8. Format is age v1, armored.** On-disk files follow [age v1](https://age-encryption.org/v1) ([C2SP](https://github.com/C2SP/C2SP/blob/main/age.md)): **ASCII armor** (PEM: `BEGIN AGE ENCRYPTED FILE`), UTF-8, `\n` only, no BOM. Write always stores `\n` only: CR is dropped even when the encrypting library would emit `\r\n` (the `age` crate on Windows). A file that still contains `\r` is not armor (`CRYPTO` on read and in `Vault.Check`). Not raw Base64 and not age's binary encoding. Payload AEAD is **ChaCha20-Poly1305**. Passphrase wrapping is age's **scrypt**; identity wrapping is **X25519**. No cipher agility: implementations do not offer AES-GCM as an alternative. The contract is the **format**, not one library: a binding may use `age`/`rage` (Rust), `filippo.io/age` (Go), typage (TypeScript), pyrage (Python), Jagged (Java), or another conformant implementation. A file written by any binding must decrypt with the `age` CLI (`age -d`) using the same secret, and must round-trip with every other binding. *Check:* `age -d` on a fixture file with the test identity/passphrase yields the bytes `Collection.Get` would return; a homemade Base64 blob and a file that still contains `\r` are refused with `CRYPTO` on read and in `Vault.Check` (`crypto::tests::crlf_armor_is_crypto`, `crypto::tests::bytes_that_are_not_armor_are_crypto`, `crypto::tests::lf_only_drops_cr_and_keeps_lf`).

**ISO-9. Whole file, write like STO-5.** Encrypt the entire `standard` or `singleton` Document — **any bytes**, text or not (the bytes a write stored; the bytes `Collection.Get` returns after decrypt) — then write a sibling temp file, `fsync`, and rename (STO-5). The bytes that reach the temp file are already ciphertext: a plaintext Document file must not exist even briefly. `Document.revision` is the hash of the sealed bytes. There is no field-level encryption: do not encrypt selected columns inside a plaintext file — a partly encrypted file is neither readable without the library nor secret. *Check (**later**):* any bytes round-trip with a passphrase and with an identity (`crypto::tests::any_bytes_round_trip_with_a_passphrase_and_with_an_identity`; `tests/documents.rs`: `any_bytes_round_trip_in_an_encrypted_collection`); the blob under the Vault is armor, never the plaintext (`tests/documents.rs`: `the_table_holds_for_encrypted_collections`).

**ISO-10. Isolated Index. Retired.** There was a separate Index for `.isolated/` at `{vault}/.isolated/.scheda/`. It is gone: one Index per Vault holds every collection the build can read, and an owner-only mode on that one directory carries what the separate one carried (ISO-4). Nothing creates, reads, or writes a nested Index; `Index.Reindex` removes a leftover one. An older Vault needs no migration step — an absent journal `id` map is answered by a segment scan, which is slower and never wrong.

**ISO-11. The declaration is the marker.** Whether a collection's files are ciphertext is recorded in one place, its collection declaration (SCH-16), and nowhere else: there is no marker file, and `{vault}/.isolated/.encrypted` is not written or read. Flipping the key on a collection that already holds Documents is `FAILED_PRECONDITION` (`Vault.UpdateCollection`) and leaves those files untouched: honouring it would mean rewriting every one of them, and the caller may not even hold the secret needed to read them first. Encrypting a collection that already has content is an explicit migration by the consumer — read out, create the new collection, write in — not a declaration edit. *Check (**later**):* `encrypted` changes only while the collection holds no Document (`tests/collections.rs`: `the_kind_isolated_and_encrypted_change_only_while_the_collection_is_empty`); no `.encrypted` path exists in a fixture Vault.

## 4. What this document does not decide

Which collections a given consumer marks isolated or encrypted, and which of the four combinations each one is in — that consumer's collection declaration.

Where a consumer keeps the secret, and how it survives a lost machine — that consumer's problem, and Scheda is not a KMS (ISO-7). What Scheda owes is that a file is age v1 (ISO-8), so the `age` CLI and any conformant implementation can read it without Scheda.

How an OS other than Unix spells `0600` — Unix is `0600`; other systems leave ACLs unchanged (the nested git and gitignore are the perimeter).

Backup of `.isolated/` — none by Scheda: isolated collections never leave the machine (ISO-6). Data that must survive a lost machine belongs in an encrypted collection of the main tree.

Argon2id instead of scrypt — out of scope while the format is age v1.

Which crate or package a binding vendors — that binding, as long as ISO-8 round-trips.
