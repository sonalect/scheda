# 04. Files and git

Document 4 of the Scheda package. Version 0.47, 20 October 2026.

Normative rules for bytes on disk, the git working tree, the write lock, the one commit of each write, the mirror, `Mirror.Push` / `Pull` / `Sync`, and how `Scheda.Open` creates or clones a Vault. Terms are in `02`. Collection kinds and identity are in `03`. Isolation and “no network by default” are restated here where they touch git; the rest is `09`. Codes: `STO`, `GIT`. Phase **core** unless marked otherwise.

An assertion without a check is not a requirement. This package does not use Git LFS.

## 1. Files are the source of truth

**STO-1. Recoverable from the tree.** Anything the library cannot rebuild from Vault files must not exist in Scheda. The Index is not truth. *Check:* delete the Index, open the Vault with another copy of an implementation, `Index.Reindex`; the set of Documents and each Document's content match the files (`tests/index.rs`: `an_index_of_another_format_or_without_a_commit_is_rebuilt`).

**STO-2. Readable without the library.** A Document is bytes (`20` D20). Scheda does not ask for UTF-8 and does not require YAML 1.2 or JSON of Document contents. `standard`: the bytes at `{name}/{id}` (`id` is the vault-relative path under the collection; the library does not append `.md`). `journal`: one envelope line `{id}: {payload}\n` per Document in a segment the library names (MOD-16); `payload` is bytes without `\n` or `\r`. `singleton`: the bytes at `{name}/{declared id}`. The collection declaration file stays YAML 1.2 or JSON (`05`). There is no declaration key that picks a Document codec. *Check:* a fixture Vault opens in an editor and in `git` with no Scheda; `git diff` after changing a text `standard` Document shows those bytes, not a binary dump (`tests/documents.rs`: `a_vault_built_by_hand_takes_document_writes_and_keeps_a_person_s_files`). *Check:* a `standard` Document whose bytes are TOML and another whose bytes are JSON, in the same collection, both round-trip; so do a PNG and bytes that are not UTF-8 (`tests/documents.rs`: `any_bytes_round_trip_in_standard_and_singleton_collections`).

**Exception (SCH-16, ISO-5):** a collection whose declaration sets `encrypted: true` stores its Document files as age ASCII armor, wherever they live — the main tree or `{vault}/.isolated/`. Those files are still text and `git diff`able as armor, not as the plaintext `Collection.Get` would return. Plaintext is recovered with the `passphrase` or `identity` (Scheda or `age -d`), not by opening the blob in an editor. Only the collections that declare it are this exception; everything else in the Vault, including every other collection and the declaration files themselves, stays as given.

**STO-3. Journal lines are not rewritten.** Same as MOD-16: no update/delete API (`Update`, `Upsert`, and `Delete` are `UNIMPLEMENTED`). On read and in `Vault.Check`, a broken line is an error: a final line without `\n`, a line with no `:` delimiter, or an empty envelope `id`. It is not “JSON object failed Schema”. Scheda does not silently truncate or rewrite the segment to “fix” it. Valid lines before the damage remain readable. *Check:* flip bytes in the middle of a closed segment → `Check` reports it; `Update` / `Delete` on the collection → `UNIMPLEMENTED` (`journal::tests`: `the_check_collects_every_problem_of_every_journal`, `a_torn_tail_or_a_broken_line_ends_the_walk_with_the_segment_path`; `tests/documents.rs`: `the_table_holds_for_a_journal`). *Check:* a line with no `:` is `INVALID_ARGUMENT`; an empty payload line `{id}: \n` is a Document (`journal::tests`: `a_line_is_id_colon_space_payload_newline`).

**STO-4. Writers take turns; readers are never blocked.** Writes to one Vault, from every handle in every process, are applied one at a time, in the order they take the write lock, each as one commit. The lock is held for that commit only: a write call first checks what does not depend on the state of the Vault (`INVALID_ARGUMENT` at once, no lock taken), then takes the lock, reads the state it needs, commits, writes the files, and lets go. No call holds it while the caller works, and none fails because another write is running. A write waits for the lock at most `OpenOptions.write_timeout_ms` (default 60 000); past it the call is `ABORTED` (retryable) and writes nothing. Readers do not take the lock and are not blocked by it; they see stored state only, so a write that has not returned is seen by no read. Writes do not touch the Index, the journal `id` maps included; the indexer (`06` IDX-9) writes it under `{vault}/.scheda/index.lock`, held for one round and taken without waiting, and never takes the write lock. `Scheda.Open` takes no lock of its own: its writes (the marker of a new Vault, the pull of `auto_sync`) take the write lock as any write does (GIT-10). `Sync`, `Set`, `Remove`, and the join of `Mirror.Pull` take it; the fetch of a pull does not (GIT-11), and `Push` takes none. *Check:* 64 writes from one handle at once, and 66 from three processes, are each stored whole and none fails on the lock (`tests/write.rs`: `sixty_four_writes_from_one_handle_at_once_are_each_stored_whole`, `sixty_six_writes_from_three_processes_are_each_stored_whole`; `tests/documents.rs`: `sixty_four_document_writes_from_one_handle_are_each_stored_whole`, `sixty_six_document_writes_from_three_processes_are_each_stored_whole`). *Check:* a call that cannot take the lock within its timeout is `ABORTED` and stores nothing (`tests/write.rs`: `a_call_that_cannot_take_the_lock_in_time_is_aborted_and_stores_nothing`). *Check:* a write that has not returned is seen by no read and leaves the work tree untouched (`document_calls::tests`: `a_write_that_has_not_returned_is_seen_by_no_read_and_touches_no_file`). *Check:* a write of another handle is not held up by a fetch that waits on the network (`tests/mirror.rs`: `a_write_of_another_handle_is_not_held_up_by_a_fetch_waiting_on_the_network`). *Check:* after `Vault.Close` no lock is held (`tests/objects.rs`: `close_waits_for_a_running_write_and_holds_no_lock_after`).

The lock is an OS file lock (`flock`) on `{vault}/.scheda/commit.lock` (not a pid-file, not under `index/`). It is released when the process dies because the kernel
closes the descriptor. Stale pid-files are not the mechanism: they would
survive a crash. Every lock file Scheda takes (`commit.lock` for writes, `index.lock` for an
indexer round) is unlocked before its descriptor closes: a close alone leaves the lock held while a child process
another thread just forked (a `git` call) still has the descriptor, and a
handle trying the lock in that moment would find it taken. Locks do not travel with `Mirror.Push` / `Pull`. Two clones
are two working trees: each has its own lock and its own writers. NFS/SMB lock semantics are not
relied on; Vaults on those shares are outside **core**. *Check:* a dropped `flock` is free while a copy of its descriptor lives (`fs::tests`: `a_dropped_flock_is_free_while_a_copy_of_its_descriptor_lives`).

`Index.Reindex` takes no write lock and no lock of its own: it asks this
Vault's indexer for a rebuild and returns. The rebuild is an indexer round
under `index.lock` (`06` IDX-9), so writes, pulls, and syncs in every
handle go on while it runs; queries and searches keep answering from the
live Index until the switch (`06` QRY-4). A second `Reindex` of the same
Vault while one is asked for or runs is `ABORTED`. A build without `index`
has no Index object; its Vaults keep the journal `id` maps. *Check:*
`Reindex` returns before the rebuild and a second one is `ABORTED`
(`indexer::tests::a_rebuild_waits_for_the_lock_and_a_second_request_is_aborted`);
the rounds of two Vaults on one path never overlap
(`indexer::tests::the_rounds_of_two_handles_of_one_vault_never_overlap`).

**STO-5. A failed write is not the new truth.** Nothing is written into the work tree before the commit. A write is committed first, from git objects built on the tree of `HEAD`, and moves `HEAD` by compare and swap on the old `HEAD`; a `git` command run by hand meanwhile makes the swap fail and the call `ABORTED` with nothing written. Only then are the files written into the work tree, and git's own index brought up to the commit for those paths. Validation failure, a full disk, or a killed process must not leave a half-written `standard` or `singleton` file as the file at the Document path, must not leave a `journal` segment cut in the middle of a line as an accepted Document, and must not leave a partial `Delete` (the path holds the whole file or no file). Holding the lock, the writer lists the paths of its write in `commit.lock` before it moves `HEAD` and empties the file once the files are written. `Scheda.Open` and every take of the lock read it: a list left there means a writer died midway, and those paths are brought up to what `HEAD` holds, except a file a person changed (GIT-2); then the file is emptied. If the commit had landed, the files become its files; if not, they were never touched. Only the paths of the list: other changes in the work tree may be a person's edit and are never discarded. *Check:* a writer stopped after the list stores nothing and touches nothing; one stopped after the swap is completed by the next `Scheda.Open` and by the next write of a running handle; a `git commit` run by hand between the read and the swap aborts the write; a person's edit of another file survives (`commit::tests`: `a_write_stopped_after_the_list_stores_nothing_and_touches_nothing`, `a_write_stopped_after_the_swap_is_completed_by_the_next_open`, `a_write_stopped_after_the_swap_is_completed_by_the_next_write_of_the_handle`, `a_git_commit_between_the_read_and_the_swap_aborts_the_write`, `a_write_cut_after_the_swap_is_finished_by_the_next_open_and_a_persons_edit_survives`, `recovery_settles_listed_paths_only_and_passes_over_unsafe_entries`). *Check:* a failing write in the middle of a batch, an `Err` item, and a broken stream each store nothing, and the first names its index (`tests/documents.rs`: `a_failing_write_in_the_middle_of_a_batch_stores_nothing_and_names_its_index`, `an_err_item_an_empty_item_and_a_stream_that_breaks_store_nothing`). Technique for the files of `standard` and `singleton`: write a sibling temp file in the same directory, `fsync`, rename over the target (`fs::tests`: `atomic_write_creates_parents_and_replaces_without_leftovers`). The temp file is `.scheda.{pid}.{n}.tmp`, so two processes never share one; a name a dead process left is passed over and kept, never removed by another write (`fs::tests`: `a_temporary_name_a_dead_process_left_is_passed_over_and_kept`). Technique for `Delete`: unlink the file (atomic: the path holds the file or nothing). Technique for `journal`: append one complete line including `\n` to the open segment; the write stores the whole segment as a new blob in its commit, so the cost of an append follows the size of the open segment, which the cap (`segment_max_bytes`, 1 MiB by default) bounds; a tail without `\n` is not a Document (STO-3). Every write leaves its blobs, trees, and commit as loose objects, and nothing else would ever pack them (Scheda's `git` commands carry `gc.auto=0`, libgit2 never repacks), so each version of a segment would stay whole: 1000 appends of 200-byte lines left 68.5 MB in `.git/objects`. Scheda therefore packs in process, with the pack builder of libgit2 and no process started, under the write lock, after a write that leaves more than about 1024 loose objects (counted in a sample of the object directories, as `gc.auto` does) or, after a write that stored a blob of 64 KiB or more, more than 8 MiB of them (counted exactly). The pack holds the loose objects with the versions of one file next to each other, so each version of a segment is a delta of the line it added, and it is complete on disk before any loose object it holds is removed, so a reader never misses an object; the same 1000 appends then take about 7 MB at their worst, 1 MB just after a packing. When there are 16 packs, the four smallest are merged into one the same way, the packs it replaces removed after it; a pack with a `.keep` file and every pack while a `multi-pack-index` exists are left alone. The nested repository (ISO-6) is packed likewise. A failure to pack leaves the objects loose and does not fail the write. *Check:* the loose objects are packed with deltas and stay readable, a merge takes the smallest packs and loses no object, a `.keep` pack is not merged (`pack::tests`: `many_appends_leave_few_loose_objects_and_a_small_database`, `a_merge_takes_the_smallest_packs_and_loses_no_object`, `a_pack_a_keep_file_protects_is_not_merged`); 400 appends to a journal, in the main and in the nested repository, leave few loose objects, packs of a few segments, a repository that passes `git fsck`, and every line readable (`tests/pack.rs`: `four_hundred_appends_to_one_journal_are_packed_and_stay_readable`, `the_nested_repository_of_an_isolated_collection_is_packed_too`). A symlink on the path of a write is refused before anything is written (`commit::tests`: `a_symlink_on_the_path_of_a_write_is_refused_and_nothing_is_stored`).

## 2. The Vault is a git working tree

**GIT-1. Root is a repository.** The Vault directory is a git working tree. The Index lives **inside** that tree under `.scheda/` and is gitignored; it is not committed. A mirror is optional. Everything works on `HEAD` (`20` D22): writes, reads, and the indexer read git objects, not the files of the work tree. Local git work goes through `git2` (libgit2) in process, packing of the loose objects included (STO-5): a normal read or write starts no process. The system `git` executable runs only where no library does what system git does: `clone`, `fetch`, and `push`, so `git` must be installed and on `PATH` for a mirror. It runs with `LC_ALL=C`, and only a refused login or certificate (`UNAUTHENTICATED`) and a network that cannot be reached or does not answer (`UNAVAILABLE`), for which `git` has no other signal, are told from its `stderr`; text no pattern knows is `REPLICATION`, and a push is read from `--porcelain` (GIT-11). Authentication, `~/.ssh/config`, `ProxyCommand`, credential helpers, and host-key checking are git's, not a linked SSH library. A repository the bundled libgit2 cannot open (SHA-256 objects or reftable refs) is `UNIMPLEMENTED` at `Scheda.Open`, told from the repository's configuration (`extensions.objectformat` and `extensions.refstorage`, read from the common directory for a linked work tree), not from the text of the library's error. The init and clone of a Vault write `core.longpaths` in its local git config so Windows can stage a 255-byte filename component when the absolute path is longer than MAX_PATH. Unix ignores the key. *Check:* a read and a write without a mirror start no process (`document_calls::tests`: `a_read_and_a_write_without_a_mirror_start_no_process`). *Check:* `git status` at the Vault root lists collection files and `.gitignore`, and does not list Index files; a Vault with no mirror still commits (`tests/write.rs`: `a_missing_path_becomes_a_vault_in_one_commit`). *Check:* after `Scheda.Open` of a new Vault, local `core.longpaths` is true (the same test; `repo::tests`: `a_new_repository_starts_on_main_with_long_paths_and_sha1_objects`). *Check:* a repository libgit2 cannot read is `UNIMPLEMENTED` in every mode (`tests/open.rs`: `a_repository_the_library_cannot_read_is_unimplemented_in_every_mode`).

**GIT-2. One write, one commit; the work tree follows.** Each write call (`Collection.Create`, `Update`, `Upsert`, `Delete`; `Vault.CreateCollection`, `UpdateCollection`, `DeleteCollection`) is atomic: when it returns `Ok`, one git commit holds the write; an error means nothing was written. Several writes sent as a write stream (`Collection.Batch`, `Vault.BatchDocuments`, `Vault.BatchCollections`) are one commit: all of them happen, or none; an `Err` item, a broken stream, or a write that fails stores nothing, and the error names the write by its index. One batch holds Document writes or collection writes, never both. A call that changes nothing (identical bytes) succeeds and makes no commit. No call, field, or term of the API says commit, transaction, or `HEAD`; there is no `OpenOptions` field that turns the commit off, and no way to hold the lock between calls.

Every write of a Document carries a `note`, required and non-empty (`INVALID_ARGUMENT` before any lock is taken); history shows it. The first line of the commit message is the first line of the first note (a collection write has no note; its message is Scheda's own text, `create collection notes (standard)`), and each Document write adds one `Scheda-Note:` trailer whose value is the Protobuf JSON of its key and note on one line, so the history of a Document shows its own note even when a batch wrote several. Documents of isolated collections commit in the nested repository `{vault}/.isolated/`; collection declarations and the other Documents commit in the main repository. Two repositories cannot take one atomic step, so one batch writes the main tree or isolated collections, never both (`INVALID_ARGUMENT`).

The git author and the git committer are one identity, in the main repository and in `{vault}/.isolated/`. `OpenOptions.author` (`Author`) may set a required `name` and `email`. Unset: the local git config, then `Scheda <scheda@invalid>`. Characters git cannot carry in a name (`<`, `>`, a newline) and an address that is not an email are `INVALID_ARGUMENT` at `Scheda.Open`, not at the first commit. Commits are not signed: `OpenOptions.signing` set is `UNIMPLEMENTED` at `Scheda.Open`, and git's `commit.gpgSign` is not read (`20` §6).

**The work tree.** The files in the work tree are a person's view of the Vault: equal to `HEAD`, or a change a person has not committed. Scheda writes the files of a write itself, after its commit (a file is made `0666`, or `0777` for an executable, so the umask of the process decides its mode as it does for git's own files; the files of an isolated collection and everything under `.scheda/` are owner-only; symlink checks; not libgit2's checkout), and a file a person changed and did not commit is left as it is: the write lands in `HEAD`, and git shows the person's file as changed against it. No call reads the files, so a person's uncommitted edit is never seen by a read and never committed by a write, and a commit a person makes by hand is read at once. `Vault.Check` lists the files a person changed. Who owns untracked files the human created in the Vault is the caller's problem; Scheda does not auto-add them. *Check:* with umask `077` a written file is `0600` and an executable one `0700` (`commit::tests`: `the_umask_decides_the_modes_of_the_files_a_write_puts_in_the_tree`, run in a child process because the umask is the process's).

The CLI sends the same calls; `batch-documents` and `batch-collections` read a batch of operations from stdin (`14`).

*Check:* a batch is one commit with one result per operation, and a batch that changes nothing makes no commit (`tests/documents.rs`: `a_batch_is_one_commit_with_one_result_per_operation`, `a_batch_that_changes_nothing_makes_no_commit`; `tests/collections.rs`: `a_batch_that_succeeds_is_one_commit_with_one_result_per_operation`). *Check:* a write without a `note` is `INVALID_ARGUMENT` in every kind of collection (`tests/documents.rs`: `a_write_without_a_note_is_invalid_in_every_kind_of_collection`). *Check:* the message is the first note line with one trailer per write (`document_calls::tests`: `the_message_is_the_first_note_line_and_one_trailer_per_write`; `tests/documents.rs`: `the_trailers_of_a_batch_name_each_document_with_its_own_note`). *Check:* a batch of isolated collections is one commit of the nested repository (`tests/documents.rs`: `a_batch_of_isolated_collections_is_one_commit_of_the_nested_repository`). *Check:* `OpenOptions.author` is the git author and committer of every commit; `History` reports it (`tests/reads.rs`: `history_lists_versions_newest_first_with_revision_author_note_and_bytes`). *Check:* a person's uncommitted edit is seen by no `Get`, committed by no write of another Document, and survives a write of the same Document, which lands in `HEAD` while git shows the file as changed (`tests/documents.rs`: `a_persons_uncommitted_edit_is_seen_by_no_get_document_and_a_commit_by_hand_is`, `a_persons_edit_is_committed_by_no_write_of_another_document_and_survives_one_of_its_own`; `check::tests`: `files_a_person_changed_and_did_not_commit_are_listed_and_a_write_does_not_clear_them`). *Check:* a repository with `commit.gpgSign` set gets Scheda's commits unsigned (`tests/documents.rs`: `a_repository_with_gpgsign_gets_unsigned_commits_and_the_write_succeeds`); `signing` set is `UNIMPLEMENTED` (`tests/open.rs`: `signing_is_not_built_yet_and_refuses_to_open`).

**GIT-3. History of a Document.** `Collection.History(id)` is the same identity path as `Collection.Get`: validate the `id`, then the git commits that touched that file, as a stream, newest first (revision, time, author, note, bytes of that version, and `write_id`; the version that deleted the Document has no bytes). `write_id` names the write that made the version and is opaque, compared for equality only: every version one write made has the same one (one call, or one `Collection.Batch` or `Vault.BatchDocuments`, across Documents and collections), so a caller that keeps one record under an id that changes joins the deletion under the old id and the creation under the new one into one event; two writes never share one, in one second and with one note too, isolated collections included; it is the same on every read, after a reopen, and in a clone; the version that deleted the Document has one too. A lazy stream: a version is read when the stream reaches it. Does not ask the Index which ids exist. The caller does not pass a path. That is a VCS address of bytes, not a consumer `revision` field. Isolated Documents use the nested git. After `Delete`, the file is gone and `History` still returns the commits that stored it; an `id` that never had a commit has an empty history. A `journal` line never changes, so `History` on a journal is `UNIMPLEMENTED`. A commit a person made by hand is a version with no note. *Check:* the versions of a Document match `git show` of that file and the first entry is the newer commit (`tests/reads.rs`: `history_lists_versions_newest_first_with_revision_author_note_and_bytes`). *Check:* a Document never stored has an empty history, and a rewrite of equal bytes is no version (`tests/reads.rs`: `history_of_a_document_never_stored_is_empty_and_a_rewrite_of_equal_bytes_is_no_version`). *Check:* one write gives every version it made one `write_id`, the deletion included, through a batch of the Vault and of a collection; two writes in one second with one note have two, the isolated one included; the ids stay the same on every read, after a reopen, and in a clone (`tests/reads.rs`: `one_write_gives_every_version_it_made_one_write_id`, `two_writes_in_one_second_with_one_note_have_two_write_ids`, `a_write_id_is_the_same_on_every_read_after_a_reopen_and_in_a_clone`). *Check:* a journal is `UNIMPLEMENTED` (`tests/reads.rs`: `history_of_a_journal_is_unimplemented`); an isolated collection's history comes from the nested repository (`history_of_an_isolated_collection_comes_from_the_nested_repository`); a hand-made commit is a version with no note (`a_commit_made_by_hand_is_a_version_with_no_note`).

**GIT-4. Conflicts are git's, shown to a person.** Scheda does not merge the bytes of a Document, line by line. Where two histories meet, `Mirror.Pull` joins them Document by Document (GIT-11), and a Document changed differently on both sides is `MIRROR_CONFLICT` with nothing changed. An unfinished merge a person left with git by hand is found from git's own unmerged entries, not from `<<<<<<<` lines in a file: `Vault.Check` reports it as `UNRESOLVED_CONFLICT`. A binary file or any bytes that happen to look like a marker are content, not a conflict; `Get` returns the bytes as they are, and a journal line with such text in its payload stays readable. Two closed journal segments that never overlapped do not conflict. Each clone appends only to journal segments named with its writer identity (`OpenOptions.writer`, kept in `{vault}/.scheda/writer`, gitignored), so two clones do not manufacture an add/add conflict on a segment path. A caller who writes the same Document `id` on two clones still has a duplicate after the join; that choice is theirs. Older writerless names (`00000001.jsonl`) are read and never appended to. *Check:* a binary file that holds marker lines passes `Check`, and a real unmerged path is reported (`check::tests`: `a_binary_file_with_marker_lines_passes_and_a_real_unmerged_path_is_reported`); both sides changing one Document differently is `MIRROR_CONFLICT` and changes nothing (`tests/mirror.rs`: `both_sides_changing_one_document_differently_is_mirror_conflict_and_changes_nothing`); two clones that wrote different Documents join in one commit with both parents (`both_sides_changing_different_documents_join_in_one_commit_with_both_parents`).

**GIT-5. Several Vaults per process.** `Scheda.Open` on distinct roots is allowed; two `Open`s of one path are two Vaults on it, as in two processes. Queries and searches do not cross roots. *Check:* a Document in Vault A never appears in a query or search on Vault B (`tests/search.rs`: `a_document_of_one_vault_never_appears_in_a_query_or_search_of_another`).

**GIT-6. No Git LFS.** Collection files stay ordinary git blobs. Segment size caps (MOD-10, default in `05`) exist so hosts that reject large files (~100 MiB) and slow `git diff` are not hit. *Check:* the default cap is below 50 MiB and a larger one is refused (`collection::tests`: `journal_limits_are_checked_and_the_default_cap_is_filled_in`); the library never configures `filter.lfs`.

## 3. The mirror, open, pull, push

The **mirror** is the one optional git remote Scheda uses on the Vault repository (git calls it `origin`, and the name stays inside Scheda). GitHub is an example host, not a Scheda type. Auth is git's (credentials, SSH keys from `~/.ssh`, `~/.ssh/config`, `GIT_ASKPASS`); Scheda does not store host tokens in the Vault. Extra remotes in git config are ignored.

**GIT-7. Detect the mirror without the network.** `Scheda.Open` of an existing working tree reads git config locally. `Mirror.Info` reports the `url` of the mirror, or empty when there is none, together with `auto_sync` and the last failure of a sync the Vault ran by itself. That is not a fetch. A Vault without a mirror has the `Mirror` object too; the calls that need one are `NOT_FOUND`. *Check:* `Mirror.Info` contacts no network (`tests/objects.rs`: `mirror_info_gives_the_url_auto_sync_and_the_last_failure_of_a_sync_by_itself`); `Pull`, `Push`, and `Sync` without a mirror are `NOT_FOUND` (`tests/mirror.rs`: `pull_push_and_sync_without_a_mirror_are_not_found`).

**GIT-8. Network is opt-in.** A write (`Create`, `Update`, `Upsert`, `Delete`, a collection write, a batch) makes its local commit and calls no mirror. `Mirror.Info`, `Set`, and `Remove` contact no network. Network happens only for: `Scheda.Open` that clones (`OpenOptions.mirror` on a missing path); `Mirror.Pull` / `Push` / `Sync`; the pull of `Scheda.Open` when `auto_sync` is on; the push after a write when `auto_sync` is on. Isolated collections never leave the machine: Scheda never contacts a remote for `{vault}/.isolated/`, whatever that repository has configured. *Check:* writes with `auto_sync` off and no explicit mirror call succeed with network disabled; a nested repository with an `origin` is contacted by no call (`tests/mirror.rs`: `no_call_contacts_a_nested_repository_under_isolated`).

**GIT-9. `Scheda.Open` creates, clones, or attaches.** One call (`Scheda.Open`, `VaultOpening` and `OpenOptions`). What makes a folder a Vault is the marker (GIT-14). `OpenOptions.mode` says what `Open` may do with the path; unset is `OPEN_MODE_OPEN_OR_CREATE`. In every mode a refusal comes before anything is written.

| Path | `OPEN_OR_CREATE` | `OPEN_EXISTING` | `CREATE_NEW` |
|---|---|---|---|
| a Vault (marker present) | attach | attach | `ALREADY_EXISTS` |
| missing, or an empty folder | new Vault, cloned from `mirror` when it is set | `NOT_FOUND` (missing) / `NOT_A_VAULT` (empty folder) | new Vault, cloned from `mirror` when it is set |
| a git working tree without the marker | the marker and `.gitignore` entries in one commit, then attach | `NOT_A_VAULT` | `ALREADY_EXISTS` |
| another folder, or a file | `INVALID_ARGUMENT` | `NOT_A_VAULT` | `ALREADY_EXISTS` |

An attach to an existing Vault: a set `OpenOptions.mirror` must equal the fetch URL of `origin` (exact string after trim), else `INVALID_ARGUMENT`; unset does not change `origin`; `Scheda.Open` does not add or rewrite `origin` (`Mirror.Set` does). A clone takes `mirror` as an absolute URI (RFC 3986: `https://…`, `ssh://…`, `file:///…`) or an scp-style `git@host:path`; a filesystem path, an empty string, or a hybrid `ssh://git@host:path` is `INVALID_ARGUMENT`. A new Vault is one commit (GIT-14); two `Open`s of one new path at once make one Vault. A clone that fails leaves no Vault. A clone of a plain repository gets the marker in one commit on top of its history.

The isolated nested git is created by Scheda under `{vault}/.isolated/`; `OpenOptions.mirror` never clones into that nested tree (ISO-6). *Check:* a missing path, an empty folder, and `CREATE_NEW` each clone the mirror (`tests/mirror.rs`: `a_missing_path_an_empty_folder_and_create_new_clone_the_mirror`); an existing Vault with a mirror that is not its `origin` is `INVALID_ARGUMENT` (`tests/open.rs`: `a_mirror_that_is_not_the_origin_is_invalid_argument`); every refusal of every mode has its code and leaves the folder as it was (`tests/open.rs`: `a_missing_path_is_not_found_in_open_existing_and_stays_missing`, `an_empty_folder_is_not_a_vault_in_open_existing_and_stays_empty`, `a_git_work_tree_without_the_marker_is_refused_by_open_existing_and_create_new`, `another_folder_is_refused_by_every_mode`, `a_file_is_not_a_vault`, `create_new_refuses_a_vault_and_the_other_modes_open_it`); a form that is not a URI is `INVALID_ARGUMENT` (`vault::tests`: `options_that_break_a_rule_are_invalid_argument`); a failed clone leaves no Vault (`tests/mirror.rs`: `a_clone_that_fails_leaves_no_vault_and_returns`); two `Open`s of one new path make one Vault (`tests/write.rs`: `two_opens_of_one_new_path_at_once_make_one_vault_and_both_open_it`).

**GIT-10. `auto_sync`.** Option at `Scheda.Open` (default **off**). When on **and** a mirror exists:

1. **Pull when the Vault opens:** pulls as `Mirror.Pull` does: fetches without the write lock and takes it for the join only (STO-4, GIT-11), then releases it.
2. **Push after a write:** the push of `Mirror.Push` after the lock is let go.

A failure of either neither fails `Scheda.Open` nor undoes the write; the Vault keeps the last failure and `Mirror.Info.last_auto_sync_error` shows it. If `auto_sync` is on and there is no mirror, `Open` and writes still succeed locally; the steps are skipped (GIT-8).

*Check:* `auto_sync` off, the mirror has new commits → `Scheda.Open` does not change `HEAD`. `auto_sync` on, the mirror has new commits → `HEAD` matches the mirror after `Open` (`tests/mirror.rs`: `auto_sync_pulls_at_open`). `auto_sync` on, a write → the commit is on the mirror (`auto_sync_pushes_every_write_of_the_main_repository`). A failed sync by itself shows in `Mirror.Info` (`tests/objects.rs`: `mirror_info_gives_the_url_auto_sync_and_the_last_failure_of_a_sync_by_itself`). A pull the mirror's commit would make unreadable (GIT-11) is such a failure: `open` succeeds and `last_auto_sync_error` holds it (`tests/mirror.rs`: `auto_sync_at_open_keeps_a_refused_pull_as_the_sync_failure`).

**GIT-11. Explicit mirror operations.** Always available when a mirror exists, independent of `auto_sync`. They take no argument:

- `Mirror.Pull` — fetch the branches of `origin` into references of Scheda's own and join the one `HEAD` names with the Vault under the write lock. The fetch is `git fetch --prune --no-tags --no-write-fetch-head --refmap= -- origin +refs/heads/*:refs/scheda/mirror/*`, run under `{vault}/.scheda/fetch.lock` and not under the write lock, so a slow or stalled network holds up no writer of any handle or process; only pulls take `fetch.lock`, one at a time, and a pull that finds another pull's fetch running waits for it at most `OpenOptions.write_timeout_ms`, past it the call is `ABORTED` (retryable); `FETCH_HEAD` is not written. The pull then takes the write lock and joins `refs/scheda/mirror/<branch>`, `<branch>` the branch `HEAD` names. A mirror that only added moves `HEAD` forward; when both sides moved, the histories are joined Document by Document (never line by line, since a Document is bytes): a file changed on one side takes that side, a file changed on both sides the same way stays, and a file changed on both sides differently is `MIRROR_CONFLICT` with nothing changed. A join is one commit with both parents, and the work tree follows it as after a write (GIT-2). A mirror that holds nothing yet, or lacks the branch (or deleted it), has no such reference and is nothing to pull. Before `HEAD` moves, the pull reads the commit it would move to (the mirror's, or the join) as `Scheda.Open` reads a Vault (GIT-14): its marker first, then its collection files. A commit of another generation is `GENERATION`, one with no marker `NOT_A_VAULT`, and a broken marker or a collection file that does not load `INVALID_ARGUMENT` naming the file; `HEAD`, the work tree, and git's index are as they were. `Sync` and the pull of `Scheda.Open` with `auto_sync` (GIT-10) refuse the same way.
- `Mirror.Push` — push the current branch to `origin`, no lock taken. The push is read from `git push --porcelain`: a reference the mirror rejected as `fetch first` or `non-fast-forward`, because it holds writes this Vault has not pulled, is `MIRROR_AHEAD`; a rejection for another reason (a hook that declined, a protected branch) is `REPLICATION` naming the mirror's reason. There is no remote-name argument.
- `Mirror.Sync` — `Pull`, then `Push`. If the pull fails, the push is not attempted. Against a mirror that holds nothing yet, it pushes.

Credentials refused are `UNAUTHENTICATED`; a mirror that cannot be reached is `UNAVAILABLE` (both told from the `stderr` of git, GIT-1). `Mirror.Set` attaches a mirror (the same URL is nothing to do; another URL is `ALREADY_EXISTS` unless `replace_existing`; a URL that carries a password is `INVALID_ARGUMENT`) and `Mirror.Remove` detaches it (none: `NOT_FOUND`); neither contacts the network.

*Check:* a pull with nothing new changes nothing; a fast-forward pull is read at once; histories that both moved join; a pull from an empty mirror is nothing to pull (`tests/mirror.rs`: `pull_with_nothing_new_changes_nothing`, `a_pull_fast_forwards_and_get_document_reads_the_new_documents_at_once`, `both_sides_changing_different_documents_join_in_one_commit_with_both_parents`, `a_pull_from_an_empty_mirror_is_nothing_to_pull`). *Check:* two pulls at once from two handles both succeed, a pull after the mirror deleted the branch is nothing to pull, and a lock on a remote-tracking reference fails neither a pull nor a push (`two_pulls_at_once_from_two_handles_both_succeed`, `a_pull_after_the_mirror_deleted_the_branch_is_nothing_to_pull_and_forgets_it`, `a_lock_on_a_remote_tracking_reference_fails_neither_a_pull_nor_a_push`). *Check:* a push is told by its porcelain status (`git::tests`: `a_rejected_reference_is_told_by_its_porcelain_status`, `a_push_that_rejected_nothing_has_no_refusal`). *Check:* `Sync` against an empty mirror pushes, and two clones that wrote different Documents end with everything everywhere (`sync_against_an_empty_mirror_pushes`, `sync_of_two_clones_that_wrote_different_documents_ends_with_everything_everywhere`). *Check:* `Set` and `Remove` (`set_mirror_sets_repeats_refuses_another_url_and_replaces_on_request`, `remove_mirror_detaches_it_and_again_is_not_found`).

**GIT-12. `Push` failure does not roll back the local commit.** The caller retries `Push` or `Sync`. *Check:* the mirror holds writes this Vault has not pulled → `Push` is `MIRROR_AHEAD` and the local commits stay (`tests/mirror.rs`: `push_sends_the_commits_and_a_mirror_ahead_is_mirror_ahead`).

Hooks on the Vault repository are the consumer's. They must not assume they may recurse into the same process's write lock.

## 4. Index location (git)

**GIT-13. Index is in the Vault tree and gitignored.** Creating a Vault writes `.gitignore` entries for `.scheda/` and `.isolated/` (and the marker, GIT-14, in the same first commit). There is one Index per Vault, under `{vault}/.scheda/`, and on Unix it is owner-only (`0700` directories, `0600` files) because it holds identity and Projector-derived values from isolated collections (IDX-4, ISO-4). There is no nested Index (ISO-10 retired). Callers do not choose an Index directory. `{vault}/.scheda/commit.lock` holds the paths of a write in flight (STO-5), and `{vault}/.scheda/writer` the writer identity (MOD-10), and `{vault}/.scheda/fetch.lock` is the lock of the fetches of pulls (GIT-11), owner-only and created on first use (a Vault without it works); none is Index, and a rebuild does not delete them. If a consumer puts another cache inside the working tree, it must also be gitignored. *Check:* `git check-ignore` / `git status` after writes does not show Index files (`tests/write.rs`: `a_missing_path_becomes_a_vault_in_one_commit`); deleting `.scheda/` does not delete Documents (STO-1), including `{vault}/.isolated/` Documents; `Vault.Check` reports a tracked isolated path and a wide mode (`check::tests`: `a_tracked_isolated_path_and_a_wide_mode_are_reported`); the nested repository and the directories of `.scheda/` are owner-only (`tests/documents.rs`: `the_nested_repository_is_made_owner_only_by_the_first_write_that_needs_it`; `writer::tests`: `the_scheda_directory_and_the_token_are_owner_only`).

Format and rebuild semantics: `06`.

**GIT-14. The marker `.scheda.yaml`.** A Vault carries a file `.scheda.yaml` at its root, committed to git so that it survives a clone (`.scheda/` is gitignored and does not). Its content is `version: 2`, the generation of the Vault format (`VaultMarker`; `version` is field 1 in every generation, so a later Scheda reads it before it decides how to read the rest). `Scheda.Open`, `Vault.Check`, and a pull (GIT-11, for the commit it would move `HEAD` to) read it before any other file. A git working tree that holds it is a Vault; Scheda then creates its service folders and files (`.scheda/`, the `.gitignore` entries) as GIT-13 says. A marker of another generation is `GENERATION`, in every open mode, before any collection file is read and with nothing written. A marker that cannot be read (not YAML, no `version`, a `version` of the wrong type, a directory in its place) is `INVALID_ARGUMENT` with `path` `.scheda.yaml`, in every open mode, and nothing is written. `Vault.Check` reads the marker of `HEAD` first, and a marker of another generation, a broken one, or none (`NOT_A_VAULT`) is the one problem it reports, with `path` `.scheda.yaml`; no other check runs. A key other than `version` is read past (`20` D21), not refused. The generation moves only for a change an earlier Scheda could not safely ignore; no step moves a Vault from one generation to another. In the default mode `Scheda.Open` writes the marker into the first commit of a new or cloned Vault, together with `.gitignore`; and adds it, together with a missing `.gitignore` entry, in one commit to a git working tree that lacks it, under the write lock. A Vault that already tracks a valid marker is not committed to. *Check:* a new path has one commit, which holds `.scheda.yaml` and `.gitignore` (`tests/write.rs`: `a_missing_path_becomes_a_vault_in_one_commit`, `an_empty_folder_becomes_a_vault_in_one_commit`). *Check:* an unmarked git work tree gets exactly one commit that adds `.scheda.yaml` and keeps its files, and a second `Open` adds none (`a_git_work_tree_without_the_marker_gets_it_in_one_commit_on_top_of_head`, `a_work_tree_with_a_gitignore_that_has_the_entries_gets_only_the_marker`). *Check:* a clone of an unmarked mirror gets the marker in one commit, a clone of a marked one none, and a mirror of another generation is `GENERATION` and leaves nothing (`tests/mirror.rs`: `a_plain_repository_as_mirror_gets_the_marker_on_top_of_its_history`, `a_mirror_built_by_hand_that_is_a_vault_opens_with_its_documents`, `a_mirror_with_a_marker_of_another_generation_is_generation_and_leaves_nothing`). *Check:* another generation is `GENERATION` in every mode and before any collection file; an unknown key is read past; a broken marker is `INVALID_ARGUMENT` and writes nothing (`tests/open.rs`: `another_generation_is_generation_in_every_mode_and_before_any_collection_file`, `an_unknown_key_in_the_marker_and_a_leftover_version_in_a_collection_file_open`, `a_broken_marker_is_invalid_argument_and_writes_nothing`; `marker::tests`: `the_marker_made_is_accepted_and_is_of_this_generation`, `a_missing_or_mistyped_version_is_invalid_argument`). *Check:* a pull or a join with a mirror of another generation is `GENERATION`, one with no marker `NOT_A_VAULT`, and a collection file that does not load `INVALID_ARGUMENT` naming it, each with `HEAD`, the work tree, and git's index as they were (`tests/mirror.rs`: `a_pull_of_a_mirror_of_another_generation_is_generation_and_changes_nothing`, `a_join_with_a_mirror_of_another_generation_is_generation_and_changes_nothing`, `a_pull_of_a_commit_without_the_marker_is_not_a_vault_and_changes_nothing`, `a_pull_of_a_collection_file_that_does_not_load_is_invalid_argument_naming_it`). *Check:* `Vault.Check` of a marker of another generation or of a commit with no marker is that one problem, and a collection file that does not load is a problem with its path while the other collections are still checked (`check::tests`: `a_marker_of_another_generation_is_the_one_problem`, `a_commit_without_the_marker_is_the_one_problem`, `a_collection_file_that_does_not_load_is_a_problem_and_the_other_checks_go_on`).

## 5. What this document does not decide

Collection declaration keys and the numeric segment size default — `05`.

How `Get` finds a journal `id` without a full scan — `06`.

The journal line form is STO-2 / MOD-16 (`{id}: {payload}\n`). The library writes that form on `Create`. LIB-18 (RFC 8785 of consumer fields) is retired.

Optional age encryption of a collection's Document files — `09`.

Multi-master without taking turns on the write lock, CRDT, custom merge of Document bytes — deferred (`10`).
