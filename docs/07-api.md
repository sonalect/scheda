# 07. Library API

Document 7 of the Scheda package. Version 0.81, 1 September 2026.

Language-neutral contract: operations, arguments, outcomes, and error codes.
Message field names and constraints live in `api/v1` (Protobuf edition 2024,
protovalidate rules). Bindings (Rust first; later Python, Java, Go,
TypeScript, and others) use these names or a documented 1:1 mapping. A
caller-supplied message that fails those rules is `invalid`, before Schema,
git, or the write lock. Agent transport (`08`) is the Protobuf JSON mapping
of those messages. Codes: `LIB`. Phase **core** unless marked **search** or **agent**.

Idioms of one language appear only in a sentence that names that language (`02`).

An assertion without a check is not a requirement.

---

## 1. Shape of a binding

**LIB-1. In-process library.** The caller loads Scheda in its own process. A Scheda daemon or HTTP server is not required to read or write. *Check (**core**):* a test writes and reads a local Vault (`auto_sync` off) with no second process and no network.

**LIB-2. Same operations in every language.** Required names: `open`, `info`, `collection`, `add`, `get`, `replace`, `remove`, `find`, `search`, `begin`, `commit`, `discard`, `push`, `pull`, `sync`, `check`, `reindex`. **Agent** also requires `create_collection` (LIB-21). AGT-1 listing is `info` (LIB-4, LIB-20), not a separate `catalog` method. Optional: `history`, `lines`, `documents`, `ids` (core in this binding). There is no `init`, `clone`, `catalog`, `walk`, `walk_inverse`, or `scan` as a public name: creating or cloning a Vault is `open` (LIB-13, GIT-9). Ordered journal read without the Index is `lines` (LIB-19), not `scan`. Listing a `document` collection without the Index is `documents` and `ids` (LIB-25, LIB-26), also not `scan`. The CLI does not encode `begin` / `commit` / `discard` (GIT-2: a process-per-command CLI cannot hold a transaction). In Rust `scheda`, `find`, `search`, and `encrypt` are opt-in crate features; Cargo default is `remote-git` only and omits those method names (`10` §2). `encrypt` adds no method name — it decides whether the handle can read and write an encrypted collection at all, and a build without it refuses those collections by code (LIB-15, ISO-5). *Check:* a binding that omits a required name is incomplete; aliases are allowed only if the docs of that binding list the mapping.

**LIB-3. Whole-record writes.** Mutation is `add`, `replace`, or `remove` of the whole Record. There is no partial field patch. SQL against the Index is not a caller API. *Check:* `replace` on `journal` is a failure (`unsupported`). *Check:* `remove` on `journal` is a failure (`unsupported`).

**LIB-4. Observable `open`.** After `open`, `info` returns `api.v1.VaultInfo`: Vault path, Index path (`{vault}/.scheda/index`), `remote` (GIT-7: `origin` or empty), `auto_sync` on this handle, and the collection list. The Vault root is the only filesystem path the caller supplies. **Later:** isolated collections listed with `schema.isolated` and encrypted ones with `schema.encrypted` (ISO-3, SCH-16); the two marks are independent and `info` reports each on its own. No process-global singleton that forbids a second Vault. Options at `open` include `auto_sync` (GIT-10), `remote_repo` (GIT-9; an absolute URI when set), commit identity (`OpenOptions.author`, `api.v1.Author`; GIT-2), and an embedder (IDX-8). There is no option that turns autocommit off: the only supported batch is a transaction (GIT-2). **Later:** `encryption` (`api.v1.Encryption`), the one secret this handle uses for every encrypted collection it touches (ISO-5, ISO-7). Setting it never encrypts anything by itself: what is ciphertext on disk is decided by each collection's Schema (SCH-16). In a build without the `encrypt` feature, setting it is `unsupported_encryption` and `open` creates nothing. The Index directory is not a caller option (GIT-13). `open` does not keep the write lock; mutating calls take it for that write. Repairing `.gitignore` on an existing Vault takes the lock for that write, then releases it before `open` returns. When `auto_sync` is on and a Remote exists, the auto-pull on `open` takes the lock for that pull (STO-4, GIT-10), then releases it; a writer already holding the lock → `locked`. *Check (**core**):* two `open`s on different roots in one process. *Check:* creating a Vault writes `.gitignore` with `.scheda/` and `.isolated/`; Index files are ignored; deleting `.scheda/` does not delete Records. *Check:* `open` with network disabled still reports `origin` on `info.remote` when that remote is configured (GIT-7). *Check:* `open` with `auto_sync` on while another handle holds the write lock → `locked`.

**LIB-5. Failures are coded.** Every failure has a stable code plus an optional human message. The message must not replace the code. The code is `api.v1.Error.Code` (Protobuf JSON `CODE_*`). **Core** includes at least: `not_found`, `invalid`, `duplicate_id` (same Record `id` already present), `conflict_markers` (git conflict markers in a file), `not_fast_forward` (GIT-10, GIT-11), `locked` (STO-4), one `io_*` per stable `std::io::ErrorKind` (no coarse `io`), one `git_*` per `git2::ErrorCode` (no coarse `git`; a non-fast-forward pull/push stays `not_fast_forward`), Index `index_missing` / `index_version` / `index_lexical` / `index_vector` / `index_corrupt` (QRY-4; no coarse `index_unusable`), `unsupported` (`replace` / `remove` on `journal`; `lines` on `document` / `singleton`; `documents` / `ids` on `journal`; `find` / `search` naming an encrypted collection). **Later:** `crypto` (the secret is absent, wrong, or the bytes will not decrypt — ISO-5) and `unsupported_encryption` (this build has no `encrypt` feature, so no secret and no retry helps; `repeat` is false). Those two are not interchangeable and neither is a substitute for `unsupported` or `invalid`: `crypto` says supply a secret, `unsupported_encryption` says use another build, `unsupported` says the operation does not apply however it was built, and `invalid` says the Schema is wrong (SCH-16). *Check:* negative tests assert codes, not only message text. *Check (**later**):* a wrong passphrase is `crypto`, a thin build is `unsupported_encryption`, `find` on an encrypted collection is `unsupported`, and an encrypted `journal` Schema is `invalid` — four distinct codes.

How a language surfaces a code is that language's affair. Examples: Rust `Result` with an error type that carries the code; Go `(value, error)`; Python exception or a result object; Java exception or a result type; TypeScript throw or a result object. The code string is what tests and `08` share.

**LIB-6. Sync is enough for core.** `add`, `replace`, `remove`, `get`, `find`, `lines`, `begin`, `commit`, `discard` must not require an async runtime. `search` with a local embedder or reranker may be synchronous in the same process. *Check (**core**):* a binding's core tests run without starting an async executor. (Rust: no Tokio required for those tests.)

## 2. Record I/O

**LIB-7. `add(id, record, message?)`.** On the collection handle. `id` is a method argument; the library checks the slug (Unicode letter or digit, then letters, digits, combining marks, `.`, `_`, `-`, `+`, `(`, `)`, space, or `@`; at most 255 bytes; not a Windows device name such as `CON`; no leading/trailing whitespace; no trailing `.`) before Schema (SCH-12). Argument `record` is `api.v1` `RecordAdd` (`fields`, `body`). Optional `message` is the git commit subject outside a transaction; omitted → `scheda`. A message that is present but empty is `invalid` before any file is written. Inside a transaction the argument is ignored; `commit` supplies the subject (GIT-2). Creates a `document` file, appends a journal line, or creates a `singleton` if absent (MOD-15–17), then updates the Index (IDX-10). Success is `()`. Same `id` already present → `duplicate_id`. Collection is the handle, not a field. Outside a transaction, then one git commit (GIT-2). Inside a transaction, does not `commit`. There is no `OpenOptions` switch that turns autocommit off; a consumer that writes many lines must `begin` first (GIT-2). Does not `pull`. *Check:* `add` with empty `id` → `invalid`. *Check:* `id` starting with `.` or `-`, or containing `$` / `;` → `invalid`. *Check:* trailing space → `invalid`. *Check:* round-trip with `get`. *Check:* without `begin`, `git log` gains one commit. *Check:* without `begin`, a passed message is that commit's subject; omitted → `scheda`. *Check:* a present but empty message is `invalid` and no file is written. *Check:* 10³ journal `add` after `begin`, one `commit` → `git log` grows by one. *Check:* drop the handle mid-transaction after complete lines plus a truncated tail; reopen without `begin` / `discard`; `get` returns the complete Records and not the truncated line.

**LIB-8. `get(id)`.** On the collection handle. Validate the slug (same rules as LIB-7), then open the Record file for that identity (IDX-10, QRY-1). Does not consult the Index for `document` / `singleton` (journal uses the IDX-5 map to find the segment). Returns `api.v1` `Record`: `collection` (output only), `id`, fields, body, path, raw bytes, and `valid` (false if the file exists but fails current Schema). Missing Record → code `not_found`, not an empty Record. **Later:** on an encrypted isolated collection, fields/body/raw bytes are the **decrypted** Record (STO-2 plaintext), not the age armor on disk. *Check:* missing id → `not_found`; invalid old file → `valid: false` and bytes still present (SCH-12). *Check:* illegal slug → `invalid` and no file open. *Check (**later**):* encrypted fixture → `get` bytes match `age -d` of the path.

**LIB-9. `replace(id, record, message?)`.** On the collection handle. When `find` is on, resolve `id` in the Index first (IDX-10); unknown → `not_found`. Do not open `{id}.md` from the raw argument. When `find` is off, and on an isolated collection, existence is the Record file (same path as `get`). Argument is `api.v1` `RecordReplace` (`fields`, `body`); `id` is the method argument, not a field. Optional `message` is the same as LIB-7: subject outside a transaction, ignored inside one, empty → `invalid` before any file is written. Whole `document` or `singleton` only. `journal` → `unsupported`. Autocommit rules are the same as LIB-7 (GIT-2). *Check:* empty `id` → `invalid`. *Check:* journal call fails; `get` matches the new record. *Check (**find**):* file on disk but not in the Index → `not_found`. **Later:** on an encrypted isolated collection, the file at the path is age armor, not plaintext YAML.

**LIB-24. `remove(id, message?)`.** On the collection handle. `document` and `singleton` only. `journal` → `unsupported` (MOD-16: a journal line does not leave). Validate the slug first (same rules as LIB-7): illegal → `invalid` before any file is touched. Optional `message` is the same as LIB-7: subject outside a transaction, ignored inside one, empty → `invalid` before any file is written. Unknown `id` → `not_found`. When `find` is on, resolve `id` in the Index first (IDX-10), as `replace` does. When `find` is off, and on an isolated collection, existence is the Record file (same path as `get`). Unlinks the Record file as a whole (STO-5: the path holds the file or nothing, never a partial) and stages the deletion like any other mutation: autocommit outside a transaction, part of the batch inside one (GIT-2). Isolated collections use the nested git. The Record leaves the Index, so `find` and `search` stop returning it and `get` answers `not_found`. Under a build without `find` the file still goes and the Index is marked stale. `history(id)` still answers from git after the file is gone. *Check:* `remove` then `get` → `not_found`; the file is gone. *Check:* unknown `id` → `not_found`. *Check:* illegal slug → `invalid` and no file is touched. *Check:* `journal` → `unsupported`. *Check:* `history` after `remove` still returns the commits that stored the file. *Check (**find**):* `find` / `search` no longer return that `id`; file on disk but not in the Index → `not_found`.

**LIB-10. `find(collections, query, offset, count)`.** On the Vault, and on the collection handle as `find(query, offset, count)` (that form calls the Vault method with that collection's name). `collections` is a set of names. Empty → every non-isolated, non-encrypted collection on this handle; an empty set stays non-isolated so a broad scan does not surface sealed values (ISO-3). A named set: unknown name → `not_found`; isolated → an ordinary query, because one Index holds them too (ISO-4), and a set mixing isolated with plain names is one page with one `total`; encrypted → `unsupported`, because no Index holds one (ISO-4) and an empty page would be a lie the caller cannot tell from "nothing matched". An explicit name whose Schema cannot accept the `Filter` (SCH-8) → `invalid`. Empty set: collections that cannot accept the `Filter` are omitted. Run a Tantivy 0.26 `Query` on the Index, then open files for the matching `(collection, id)`s (IDX-10). Query argument is `api.v1` `FindQuery` (`find.proto`): required `Filter` (the same kinds as `tantivy::query`: `all`, `empty`, `term`, `term_set`, `phrase`, `phrase_prefix`, `fuzzy`, `regex`, `regex_phrase`, `range`, `exists`, `boolean` with `must` / `should` / `must_not`, `boost`, `const_score`, `disjunction_max`, `more_like_this`) plus `include_raw` (unset or false omits `Record.raw`; `get` always returns `raw`). Collector is `(Count, TopDocs::with_limit(count).and_offset(offset))` (not a field on `FindQuery`). Order: one `journal` collection → append order (QRY-7: `order_by_fast_field` on the indexed ordinal); otherwise Tantivy score descending with equal scores broken by that same ordinal ascending, so a page is reproducible for a given Index (QRY-7). `more_like_this` whose source is an `id` builds its terms from that Record's indexed text, so an unknown source `id` is `not_found`, not an empty page: a caller asking for "similar to X" cannot otherwise tell a missing X from nothing being similar. `count` `0` is `invalid` (Tantivy panics). Returns `api.v1` `FindResult` (same file): `records` (length at most `count`) and `total` (Tantivy `Count`: indexed hits matching the Filter). A missing file is omitted from the page and does not decrease `total`. Past the end → empty `records`; `total` is still the match count. Every indexed Record in the selected collections is `Filter` `all`. There is no `scan` method. Collection is not a field on `Filter` / `FindQuery`. `Record.collection` is output only. *Check:* `should` of two `term`s on different fields returns the union. *Check:* `must` of two `term`s returns the intersection. *Check:* `count` `0` → `invalid`; `offset` beyond the last match → empty `records`. *Check:* empty `collections` on a two-collection fixture returns both; a one-name set returns only that collection. *Check:* `all` on a three-Record fixture with `count` 1 returns one Record and `total` 3. *Check:* default `find` omits `raw`; `include_raw` true fills `Record.raw`.

**LIB-11. `search(collections, query, reranker?)`.** Hybrid retrieval (`13`): BM25 and ANN when both are on, RRF, then optional rerank. On the Vault, and on the collection handle as `search(query, reranker?)` (that form calls the Vault method with that collection's name). `collections` is the same set as LIB-10. Argument is `api.v1` `SearchQuery` plus an optional caller `Reranker` (`score` / `score_many`; `many_limit` of 0 is `invalid`; not proto). `k` unset or `0` → 10. Weights unset → `1`; **zero turns that leg off**. `filter` set → Tantivy first on the selected collections; both legs on that `(collection, id)` set. Fusion pool is at least `max(k, 50)`. With a reranker the library opens those Records, scores (`score` when there is one candidate or `many_limit` is 1, otherwise `score_many` in chunks of `many_limit`), sorts, returns `k` with `rerank_score`. Without it, RRF order and no `rerank_score`. `include_raw` true fills `Hit.raw` (file bytes); unset or false omits it. Output is `api.v1` `SearchHits`. `Hit.collection` is output only (same as `Record.collection`). Scheda does not load a ranking model. **Search.** *Check:* QRY-3 fixture ids all appear at the given `k`; a hit from both legs carries both scores. *Check:* negative or non-finite weight → `invalid`. *Check:* `filter` that excludes a Record keeps it out of both legs. *Check:* reranker that inverts two hits is reflected in hit order. *Check:* empty `collections` on a two-collection fixture can hit both; a one-name set does not. *Check:* default `search` omits `Hit.raw`; `include_raw` true fills it.

**LIB-20. Catalog is `info`.** AGT-1 listing is `Vault.info` (`api.v1.VaultInfo`: nested `Schema` per collection). Same content as Schema files (`05` §8): collections, kinds, fields, index marks, edges. Not inferred from directories. No `catalog()` method and no request envelope. Isolated collections are listed with `schema.isolated` and without `schema.fields` (ISO-3). **Agent.** *Check:* AGT-1.

**LIB-21. `create_collection(name, schema, message?)`.** Write one collection declaration. Argument is the collection name plus `api.v1` `Schema`. Optional `message` is the same as LIB-7: subject outside a transaction, ignored inside one, empty → `invalid` before any file is written. Schema has no layout and no Record path. A Schema that fails `api/v1` is `invalid` before the collection file is written. Then SCH-2–SCH-14 (same rules as load). Needs the write lock. Writes `{name}/.schema.yaml`, or replaces an existing `.schema.yaml` / `.schema.yml` / `.schema.json` in that directory. `name` is the collection name and the on-disk directory (MOD-8). `schema.isolated` → Record files under `{vault}/.isolated/{name}/`; creates the nested git if needed; then `collection(name)` is the handle for those Records. After a successful write, `info` and `collection` on this handle see the new Schema (no reopen). Returns the live `Collection` handle. Autocommit rules are the same as LIB-7 (GIT-2). Isolated Record paths commit in the nested git; the Schema stub commits in the main repository. **Agent.** *Check:* `create_collection` then `add` on that collection without reopen; a leftover `layout` key or an extra Schema key → `invalid` and no file. *Check:* `isolated: true` writes the Schema stub and nested git; `add` then `get` round-trip under `{vault}/.isolated/{name}/`.

## 3. Git and maintenance

**LIB-12. `commit(message)`.** GIT-2. Ends the transaction on this handle. A transaction is the only supported batch. `invalid` if none is open on this handle, or if the message is empty, or if there is nothing to commit. Creates one git commit per repository that has recorded paths (main and/or `{vault}/.isolated/`). Nested is committed first; if the main commit then fails, nested `HEAD` is reset to the commit it had before that nested commit (GIT-2). If `auto_sync` is on, then `push` of the main tree only (GIT-10, GIT-12, ISO-6). The CLI does not encode this name.

**LIB-22. `begin()`.** GIT-2. Enter a transaction on this handle. Needs the write lock. Discards leftover Scheda writes first. `invalid` if a transaction is already open on this handle. The flag is in memory on this handle; `open` does not resume another process's transaction. Dropping the handle ends it without a git commit. The CLI does not encode this name.

**LIB-23. `discard()`.** GIT-2. Restore Scheda-recorded paths to HEAD, end the transaction if any on this handle, reload Schema, and rebuild the Index. Needs the write lock. Allowed without an open transaction (crash leftovers). The CLI does not encode this name.

**LIB-13. `open(path)`.** GIT-9. One public call. Path exists as a Vault → open (`remote_repo` ignored). Path missing and `remote_repo` set → `git clone`. Path missing → `git init`, no Remote. Path exists but is not a Vault → `invalid`. A set `remote_repo` must be an absolute URI (RFC 3986); an empty string, a filesystem path, or SCP `git@host:path` is `invalid`. `OpenOptions.author` (`api.v1.Author`) is the git author and committer for every commit on this handle (main tree and `{vault}/.isolated/`): required `name` and `email` when set; a name git cannot carry (`<`, `>`, a newline) or an address that is not an HTML email is `invalid` here (GIT-2). Unset: local git config, then `Scheda <scheda@invalid>`. **Later:** `{vault}/.isolated/` is created by Scheda, never cloned (ISO-6). `OpenOptions.encryption` applies when that nested tree is first created; isolated Record I/O then requires it (ISO-5, ISO-7). `open` of the Vault does not require `encryption`.

**LIB-14. `pull` / `push` / `sync`.** GIT-11–12. Always `origin`; there is no remote-name argument. **Later:** these never publish `{vault}/.isolated/` (ISO-6).

**LIB-15. `check`.** Validates Schema, encodings (STO-2), journal lines (STO-3), `id` uniqueness, conflict markers (GIT-4). Isolated Record files are scanned when `{vault}/.isolated/` exists. Parent git must not track `.isolated/` (ISO-2). On Unix, `{vault}/.scheda/` must be owner-only — `0700` directories, `0600` files — and a wider mode is reported with that path (IDX-4); the Index holds sealed values now, so the mode is part of the perimeter and not housekeeping. **Later:** an encrypted collection is validated like any other when the handle carries the secret — armor form first (ISO-8), then decrypt, then the same Schema and encoding rules. Without the secret `check` fails with `crypto`, and in a build without `encrypt` with `unsupported_encryption`. It must never return success over files it did not open: that would report health it never verified. The two codes say "not verified", not "broken", and a caller tells them from `invalid` or `conflict_markers` by the code, which is the whole reason those codes are distinct. Does not write Records. Reports each problem with a code and path.

The shape of that answer is limited by the method, and the limit is stated rather than wished away. `check` returns success or one failure, so it cannot say "these collections are healthy and that one was not read". Any failure hides whatever the walk had not yet reached — true for every code, not only these two. A per-collection report needs a return type this method does not have; until it does, a caller who wants the plain collections verified while the secret is absent has to open a handle whose Vault has none. *Check (**later**):* the same fixture fails with `crypto` without the secret and succeeds with it; in a thin build it fails with `unsupported_encryption`; a corrupted armor file is a failure with a path, not a silent pass.

Lexical Index freshness is one more leg of `check`, and only a build with `find` walks it (`10` §2). There a stale Index is `index_lexical` and `reindex` is the cure. A build without `find` skips the leg: its own writes mark the Index stale, it holds no lexical segments, and its `reindex` cannot rebuild them, so reporting that state would leave `check` red from the first write onward with nothing able to clear it. Skipping it costs no honesty. The marker stays on disk for the next build with `find`, and `find` itself fails closed on it (QRY-4), so an aged Index still never serves a hit. *Check (**find**):* `add`, then `check` → `index_lexical`; after `reindex`, `check` passes. *Check:* Cargo default build — `add`, then `check` passes while the stale marker exists on disk.

**LIB-16. `reindex`.** IDX-1. Returns `api/v1` `ReindexResult`: Records read, skipped invalid, segments seen. Needs the write lock. Writes Index format version `3` as `{vault}/.scheda/index/format` (one decimal integer and a newline) and the journal `id` map (IDX-5) for every collection the build can read, isolated included; encrypted collections are skipped (ISO-4). There is no nested rebuild: a leftover `{vault}/.isolated/.scheda/` from an older build is removed, since it is derived and gitignored. Owner-only modes are re-applied when the rebuild finishes (IDX-4). *Check:* after an isolated write no `.scheda/` exists under `.isolated/`, and `reindex` counts the isolated Records among those read.

**LIB-17. `history(id, offset, count)`.** GIT-3. On the collection handle. Same identity path as `get` (IDX-10): validate the slug, then git history of that file. Does not ask the Index which ids exist. **Core** for `document` / `singleton`. For `journal`, IDX-5 map then git history of the **segment file** (the whole file in `Entry.raw`); line-level blame is **later**. The caller passes Record `id`, not a file path. An `id` that never had a commit and has no file → `not_found`. After `remove`, the file is gone and `history` still returns the commits that stored it. Paged, newest first: `offset` skips that many commits, `count` is the page size (`invalid` if `count` is 0). Returns `api/v1` `History` with `repeated Entry`: commit hash, `google.protobuf.Timestamp` `time` (UTC; git stores whole seconds since epoch), author, message, and file bytes (`raw`). Isolated collections use the nested git. Past the end of history → empty `entries`.

On an **encrypted** collection the handle secret is required and `raw` is the decrypted plaintext of that revision — the bytes a `get` of that revision would have produced, not the armor git holds. Demanding the secret and then returning ciphertext would be the worse contract: the caller has proved it holds the key, and the library is the only component that knows the collection is encrypted. Without the secret, `crypto`; in a build without `encrypt`, `unsupported_encryption`. An entry whose `raw` is empty is returned as it is: a commit that deleted the file has no bytes, and there is nothing there to decrypt. *Check:* two commits editing one `document`; snapshots match `git show` of the file Scheda stores. *Check (**later**):* on an encrypted collection, both revisions come back as plaintext with the older one carrying the older value, and no entry begins with the armor header. *Check:* `count` `0` → `invalid`; `offset` beyond the last commit → empty `entries`; unknown `id` → `not_found`. *Check:* `remove` then `history` still matches `git show` of those commits. *Check:* delete `.scheda/`; `history` of a fixture `document` still matches `git show`.

**LIB-18. Canonical journal line.** `add` on `journal` writes one RFC 8785 object per line (JSON Canonicalization Scheme: keys in UTF-16 code unit order, numbers as ECMAScript `NumberToString`, strings escaped as the RFC states) so a consumer can hash bytes. `RecordAdd.fields` is `google.protobuf.Struct`; a JSON number there is `number_value` (IEEE 754 binary64). An `integer` field is accepted only when that double is a finite integer whose magnitude is at most 2^53. A larger magnitude is `invalid`; this API does not carry a wider integer. On disk the integer is the decimal digits (`1`), not `1.0`. *Check:* two inserts of equal fields produce equal line bytes aside from field values that differ. *Check:* `integer` `1` is stored as `1`; `1.5` and magnitude above 2^53 are `invalid`.

**LIB-19. `lines()`.** On the collection handle. `journal` only. Walks segment files in Schema sequence (SCH-14): closed segments by name, each file from first line to last, then the open segment. Rotation does not reorder earlier lines. Same append order as QRY-7, without opening the Index (not QRY-2, not IDX-5). Does not take a `Filter`. Each yielded Record has `raw` equal to that line including the trailing newline (LIB-18, STO-2). A line that is not a complete JSON object, or a final line without `\n`, is `invalid` and stops the walk (STO-3). A well-formed line that fails current Schema is yielded with `valid: false`, as `get` does. `document` / `singleton` → `unsupported`. Isolated `journal` is allowed (ISO-2). A missing or corrupt `{vault}/.scheda/` does not stop the walk. Streaming: one Record at a time; the binding must not materialise the whole collection. Empty collection → empty walk. In Rust the return is `JournalLines` (`Iterator` of `Result<Record, Error>`). *Check:* insert A, B; rotate; insert C; `lines` → A, B, C in that order, and `raw` matches the segment files. *Check:* delete `.scheda/`; `lines` still yields those Records. *Check:* `document` → `unsupported`. *Check:* 10³ lines across rotated segments: every `id` once, in append order; memory does not grow with the line count.

**LIB-25. `documents()`.** On the collection handle. `document` and `singleton` only; `journal` → `unsupported` (ordered journal read is LIB-19). Walks the Record files the library names, in `id` order: the byte order of the file name, which is `{id}.md`. A `singleton` yields its one Record, or nothing before the first write. Does not open the Index (not QRY-2, not IDX-10), so the walk is the same in a build without `find` and is unaffected by a stale Index; it is the answer of last resort when the Index is gone. Does not take a `Filter`: selecting by field is LIB-10. Each yielded Record is what `get(id)` returns for that `id`, `raw` included, and that holds for a bad file too: a file that does not parse and a Record that parses but fails current Schema are both yielded with `valid: false`, and the walk continues. This is deliberately unlike LIB-19, which stops. A journal is one file, so a malformed line hides where the next line begins and there is nothing safe to do but stop; documents are separate files, so a bad one says nothing about the next, and stopping would hide every Record after it in `id` order. Reporting bad files is `check` (LIB-15), not this walk. Names that are not Record files are skipped and are not an error: a name starting with `.` (so `.schema.yaml` and `.scheda/` never appear), a name not ending in `.md`, and anything that is not a regular file. Subdirectories are not descended — a collection is one flat directory (MOD-8). Isolated collections are allowed and walk `{vault}/.isolated/{name}/` (ISO-2). **Later:** an encrypted collection is allowed too, and each file is decrypted as it is yielded, so the walk needs the handle secret and fails with `crypto` without it (ISO-5); a file that decrypts but does not parse is `valid: false` like any other bad file, while one that will not decrypt is an `Err`. Since `find` is `unsupported` there (ISO-4), this walk plus `get` are the only ways in, and a lookup by field costs on average half the collection rather than all of it. `ids()` reads file names only and needs no secret. Streaming: one Record at a time; the binding must not materialise the whole collection. Because the order is stable, the file names are held for the length of the walk, so memory grows with the **number** of Records, not with their contents. A missing collection directory and an empty one both give an empty walk. In Rust the return is `CollectionDocuments` (`Iterator` of `Result<Record, Error>`). *Check:* add `charlie`, `alpha`, `bravo`; `documents` yields `alpha`, `bravo`, `charlie`. *Check:* `.schema.yaml` and a stray `notes.txt` in the collection directory are not yielded and do not fail the walk. *Check:* `journal` → `unsupported`. *Check:* delete `.scheda/`; `documents` still yields every Record. *Check:* a document whose fields fail current Schema is yielded with `valid: false`, and so is a `.md` file that is not a Record at all; in both cases the next Record still arrives. *Check:* `singleton` before the first write → empty walk; after → one Record. *Check:* 10³ documents: every `id` once, in `id` order.

**LIB-26. `ids()`.** On the collection handle. Same kinds, same order, and the same skipping rules as LIB-25, but no Record file is opened: the answer is the names the library gave those files. This is how a caller asks which Records exist without paying for their contents; contents then come from `get`, or from LIB-25 when all of them are wanted. Independent of the Index in the same way, so the list is correct in a build without `find` and with a stale Index. `journal` → `unsupported`: a journal `id` lives inside the line, so enumerating those ids is LIB-19, or IDX-5 when `find` is on. Returns the ids in one list (`Vec<String>` in Rust): memory is the ids, never Record contents. An `id` here is the name the library gave the file, while `Record.id` from LIB-25 is the one inside the file; for anything the library wrote they are the same string, and after a hand-edit that renames one without the other they can differ. `check` is what reports that; `ids` reports the files. *Check:* a three-document fixture gives its three ids in `id` order. *Check:* `.schema.yaml` is not an id. *Check:* empty and missing collection → empty list. *Check:* `journal` → `unsupported`. *Check:* `singleton` before the first write → empty; after → one id equal to `singleton_id`. *Check (**find**):* with a deliberately stale Index the list still matches the files on disk.

## 4. What this API refuses

- Partial field patch.
- A Record file path from the caller. `get` / `add` / `history` take a validated `id` and the library opens, creates, or gits the file. `find` / `replace` / `remove` / `search` take `id`s from the Index when `find` is on (IDX-10). `lines` walks journal segment files the library names, and `documents` / `ids` walk the Record files the library named; the caller does not pass a path, a directory, or a glob.
- Delete of a journal line (`remove` on `journal` is `unsupported`). `remove` of a `document` or `singleton` is LIB-24.
- Cross-Vault query unless the caller passes two handles into a combined helper (**later**).
- Shipping a ranking model in the library (QRY-5). An optional reranker **callback** on `search` is allowed (`13`).

## 5. First implementation (Rust)

The crate `scheda` is the first binding. It must:

- map every LIB operation above;
- use `Result` with a typed error that includes LIB-5 codes (no `panic!` / `unwrap` / `expect` / `assert!` on the library path; tests may assert);
- carry `[lints] workspace = true` as in this repository.

That panic policy is **Rust**, not a requirement on other languages (Python, Java, Go, TypeScript, and others use their usual error conventions, still with LIB-5 codes).
