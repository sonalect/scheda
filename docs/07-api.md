# 07. Library API

Document 7 of the Scheda package. Version 2.19, 20 October 2026.

Language-neutral contract: objects, operations, arguments, outcomes, and
error codes. The messages and the services are `api/scheda/v1/*.proto`
(Protobuf edition 2024, protovalidate rules). **What each call does, its
rules, and the codes it fails with are the comment of its rpc** in those
files (`20` D12): the plugin turns it into the rustdoc of both traits, and
any other binding reads the same text. This document keeps what spans
methods. Bindings (Rust first; later Python, Java, Go, TypeScript, and
others) use the rpc names or a documented 1:1 mapping. A caller-supplied
message that fails the protovalidate rules is `INVALID_ARGUMENT`, before
the collection declaration, git, or the write lock. Agent transport (`08`)
is the Protobuf JSON mapping of those messages. Codes: `LIB`. Phase
**core** unless marked **search** or **agent**.

Idioms of one language appear only in a sentence that names that language (`02`).

An assertion without a check is not a requirement.

---

## 1. Shape of a binding

**LIB-1. In-process library.** The caller loads Scheda in its own process. A Scheda daemon or HTTP server is not required to read or write. *Check (**core**):* a test writes and reads a local Vault (`auto_sync` off) with no second process and no network (`tests/reads.rs`: `an_arc_dyn_vault_sync_from_open_drives_a_vault_end_to_end`).

**LIB-2. The same objects and calls in every language.** The contract is a set of objects, each a service, reached from the one before it (`20` D24): `Scheda` (`Info`, `Open`) opens a `Vault`; a `Vault` gives a `Collection` (`Vault.GetCollection`), its `Mirror` (`Vault.Mirror`), and its `Index` (`Vault.Index`). An object travels as a *reference message* (`VaultRef`, `CollectionRef`, `MirrorRef`, `IndexRef`; for ports `EmbedderRef`, `RerankerRef`, `ProjectorRef`) that holds the implementation itself within one process; a reference has no Protobuf JSON form, and one that holds nothing is `INVALID_ARGUMENT` where it is given. A binding without such a thing documents its mapping. Required: every rpc of `Scheda`, `Vault`, `Collection`, `Mirror`, and, in a build with `index`, `Index`, the queries, the counts, and the searches. A method of a feature the build lacks answers `UNIMPLEMENTED`, and `Scheda.Info` lists the features of the build (`FEATURE_INDEX`, `FEATURE_ENCRYPT`). No call, field, or term of the API says commit, autocommit, transaction, or `HEAD` (`20` D6): there is no `begin`, `commit`, `discard`, `transaction`, `add`, `replace`, `remove`, `init`, `clone`, `catalog`, `walk`, `walk_inverse`, or `scan` as a public name. Creating or cloning a Vault is `Scheda.Open` (`OpenOptions.mode`, `OpenOptions.mirror`). Ordered journal read without the Index is `Collection.GetMany` with a listing, and listing a `standard` collection without the Index is the same call. In Rust `scheda`, `index` is a crate feature on by default (the Index on Lance, its queries, counts, and searches, and the ports; building it needs `protoc`), and `default-features = false` drops it: `Vault.Index`, the queries, the counts, the searches, and every port are then `UNIMPLEMENTED`, and the journal `id` maps are kept (`10` §2). `encrypt` is opt-in and adds no method — it decides whether the Vault can read and write an encrypted collection at all, and a build without it answers `UNIMPLEMENTED` for those collections (ISO-5). *Check:* `Scheda.Info` lists the features of the build, and a build without `index` answers its calls `UNIMPLEMENTED` (`tests/objects.rs`: `scheda_info_gives_the_version_and_the_features_of_the_build`; `tests/query.rs`: `without_the_index_the_four_calls_and_the_index_object_are_unimplemented`; `tests/search.rs`: `without_the_index_the_two_calls_are_unimplemented`). *Check:* no name of the contract carries a git term (`rust/api/tests/git_terms.rs`).

**LIB-3. Whole-Document writes.** Mutation is `Create`, `Update`, `Upsert`, or `Delete` of the whole Document's bytes. A Document is bytes: Scheda does not ask for UTF-8 (`20` D20). There is no partial patch of contents. SQL against the Index is not a caller API. The `id` is a method argument; the library checks it before any file is written (`03` MOD-6). *Check:* `Update` on a `journal` is `UNIMPLEMENTED`, and so is `Delete` (`tests/documents.rs`: `the_table_holds_for_a_journal`). *Check:* any bytes round-trip in `standard` and `singleton` collections (`tests/documents.rs`: `any_bytes_round_trip_in_standard_and_singleton_collections`).

**LIB-4. Observable `Scheda.Open`.** `Scheda.Open(VaultOpening)` takes the Vault path, the `OpenOptions`, and the three port references, and returns a `VaultRef`. After it, `Vault.Info` returns `VaultInfo`: the Vault path, the Index path (`{vault}/.scheda/index`), the writer identity of this clone, and `version`, the state token of the stored state now (`06` QRY-8). `Mirror.Info` returns the mirror `url`, `auto_sync`, and `last_auto_sync_error`; `Vault.ListCollections` returns the declarations (`05`): kind, isolation, encryption, caps, `index_scope` — not Document fields. The Vault root is the only filesystem path the caller supplies. No process-global singleton forbids a second Vault: opening the same path twice makes two Vaults on it, as two processes would. Options at `Scheda.Open`: `auto_sync` (GIT-10), `mirror` (the URL to clone from when the path holds no Vault; on an existing Vault it must be the mirror's URL), `encryption` (`Encryption`, the one secret this Vault uses for every encrypted collection, ISO-5, ISO-7), `author` (`Author`, GIT-2), `writer` (unset → generated into `{vault}/.scheda/writer`), `index_poll_ms` (`06` IDX-9), `index_wait_timeout_ms` (how long a call with `not_before` waits for the Index, default 60 s; `06` QRY-8), `filter_max_depth` (how deep a `Filter` may nest, default 32, at most 100; `13` §3), `mode` (`OPEN_MODE_OPEN_OR_CREATE`, `OPEN_MODE_OPEN_EXISTING`, `OPEN_MODE_CREATE_NEW`), `write_timeout_ms` (LIB-32), and `signing` (not built: `UNIMPLEMENTED`). Setting `encryption` never encrypts anything by itself: what is ciphertext on disk is decided by each collection's declaration (SCH-16); in a build without `encrypt`, setting it is `UNIMPLEMENTED` and nothing is created. The Index directory is not a caller option (GIT-13). `Scheda.Open` does not keep the write lock; every write takes it for that write only (LIB-32). Repairing `.gitignore` and adding the marker to an existing git work tree are one write each, made under the lock and released before `Open` returns. With `auto_sync` on and a mirror set, the pull at `Open` fetches without the lock and takes it for the join (STO-4, GIT-10, GIT-11); a failure of it neither fails `Open` nor is lost: `Mirror.Info` shows it. *Check (**core**):* `Vault.Info` gives the path, the Index path, and the writer (`tests/objects.rs`: `vault_info_gives_the_path_the_index_path_and_the_writer`). *Check:* creating a Vault is one commit with the marker and the `.gitignore` entries (`tests/write.rs`: `a_missing_path_becomes_a_vault_in_one_commit`); two opens of one new path make one Vault (`tests/write.rs`: `two_opens_of_one_new_path_at_once_make_one_vault_and_both_open_it`). *Check:* `Mirror.Info` gives the URL, `auto_sync`, and the last failure (`tests/objects.rs`: `mirror_info_gives_the_url_auto_sync_and_the_last_failure_of_a_sync_by_itself`). *Check:* each mode refuses what it must (`tests/open.rs`: `a_missing_path_is_not_found_in_open_existing_and_stays_missing`, `create_new_refuses_a_vault_and_the_other_modes_open_it`). *Check:* two Vaults on one path both write and each sees the other (`tests/consumer.rs`: `two_vaults_on_one_path_both_write_and_each_sees_the_other`).

**LIB-5. Failures are coded.** `scheda::Error` is `protocontract::Error`, and `VaultErrorCode` is the enum of the `Vault` service (Protobuf JSON `VAULT_ERROR_CODE_*`). A failure has a stable code, an optional human message, and a cause as its source; the message must not replace the code. A code is what a caller acts on; where Scheda means what a gRPC canonical code means, the code takes that name.

| `VaultErrorCode` | Retryable | The caller |
| - | - | - |
| `INVALID_ARGUMENT` | no | fixes the request |
| `NOT_FOUND` | no | treats it as absent |
| `ALREADY_EXISTS` | no | treats it as present |
| `FAILED_PRECONDITION` | no | reads again |
| `UNIMPLEMENTED` | no | calls something else or uses another build |
| `ABORTED` | yes | tries again |
| `UNAVAILABLE` | yes | tries again later |
| `UNAUTHENTICATED` | no | supplies credentials for the mirror |
| `NOT_A_VAULT` | no | opens another path |
| `GENERATION` | no | moves the Vault to this generation |
| `CRYPTO` | no | supplies the secret |
| `MIRROR_AHEAD` | no | pulls, then tries again |
| `MIRROR_CONFLICT` | no | resolves by hand |
| `UNRESOLVED_CONFLICT` | no | finishes the merge |
| `DEADLINE_EXCEEDED` | yes | tries again, or reads `Index.Status` |
| `INDEX_REBUILDING` | yes | tries again soon |
| `INDEX_STALE` | no | runs `Index.Reindex` |
| `INDEX_BROKEN` | no | runs `Index.Reindex` |
| `STORAGE` | per kind | reports it |
| `REPLICATION` | no | reports it |

A failure of `git` on a mirror is told by a signal of its own where it has one: only a refused login or certificate (`UNAUTHENTICATED`) and a network that cannot be reached or does not answer (`UNAVAILABLE`) are read from `stderr`, run with `LC_ALL=C`, and text no pattern knows is `REPLICATION`; a push is read from `--porcelain`, so only a reference rejected because the mirror holds writes this Vault lacks is `MIRROR_AHEAD` and another rejection is `REPLICATION` naming the reason; a repository of SHA-256 objects or reftable references is `UNIMPLEMENTED`, told from its configuration (`04` GIT-1, GIT-11). `STORAGE` is retryable for the transient kinds (`Interrupted`, `WouldBlock`, `ResourceBusy`). The flag is `retryable` on the error; a method that knows better than the table sets it on the instance. `UNIMPLEMENTED` also answers a call that does not apply (`Update` on a `journal`, a query naming an encrypted collection, ISO-4). A port has codes of its own (`EmbedderErrorCode`, `RerankerErrorCode`, `ProjectorErrorCode`: `UNAVAILABLE` retryable, `REFUSED` not); a panic of a port, or of the work of a call, is protocontract's `RuntimeCode::Panicked`, and a blocking form refused on a current-thread runtime is its `RuntimeCode::CannotBlock` (`CANNOT_BLOCK`, LIB-6). One Scheda type, `scheda::Fault`, carries a code, a message, an optional Vault-relative `path`, the retry flag, and the source; the library API returns the error, and a caller branches on the code, never on the message or on the `Fault`. For a transport (the CLI, `IndexState.last_error`) the error is written out as an `ErrorReport { code, message, retryable, stack, path }` with `code` the code's name (`08`, `14`). Messages never carry a credential. How a language surfaces a code is that language's affair: Rust `Result` with an error type that carries the code; Go `(value, error)`; Python exception or a result object; Java exception or a result type; TypeScript throw or a result object. The code name is what tests and `08` share. *Check:* negative tests assert codes, not only message text; every code has the retry flag of the table (`error::tests::every_code_has_the_retry_flag_of_the_table`); a report carries the code name, the flag, the stack, and the path (`error::tests::a_report_carries_the_code_name_the_flag_the_stack_and_the_path`); a foreign cause stays reachable through the source (`error::tests::io_failure_keeps_its_error_kind_through_source`, `error::tests::a_file_failure_keeps_its_path_and_shows_it`).

**LIB-6. Async only, on the caller's runtime.** The objects (`Scheda`, `Vault`, `Collection`, `Mirror`, `Index`) implement the async traits of the contract (`SchedaAsync`, `VaultAsync`, …) natively, and have no blocking form of their own. In Rust, tokio is a required dependency, and the objects run on the runtime of the caller, a multi-thread or a current-thread one, with the time and I/O drivers on (`Builder::enable_all`). Scheda has no runtime of its own and never calls `block_on` or `block_in_place`. A caller without async code builds a multi-thread runtime and takes the blocking form of a reference inside it (`reference.to_sync()`, protocontract's `Blocking`, which gives `VaultSync`, …); on a current-thread runtime that form is refused with `CANNOT_BLOCK`, not a hang and not a panic. Another binding states the same rule in its own terms: no call blocks the caller's event loop. *Check (**core**):* the objects work on a current-thread and a multi-thread runtime, and with a blocking pool of one thread (`tests/runtime.rs`: `the_objects_work_on_both_runtimes`, `the_objects_work_with_a_blocking_pool_of_one_thread`); a blocking caller wraps the Vault on a multi-thread runtime and is refused on a current-thread one (`tests/runtime.rs`: `a_blocking_caller_wraps_the_vault_on_a_multi_thread_runtime_and_is_refused_on_a_current_thread_one`); the batches and the search run inside `spawn_blocking` (`tests/consumer.rs`: `the_batches_and_the_search_run_inside_spawn_blocking`). *Check:* the indexer task ends with `Vault.Close` and with the last drop (`tests/index.rs`: `close_and_drop_end_the_indexer_task`).

**LIB-31. Ports.** The `Embedder`, the `Reranker`, and the `Projector` are services the caller implements and Scheda calls (`ports.proto`; `06` IDX-8; `13`). Scheda ships no model and does not know what a Document holds. A port is given as a reference in `VaultOpening` or later (`Vault.SetEmbedder`, `SetReranker`, `SetProjector`) and taken away with the matching `Remove…`; it is the Vault's until then and may change at any time. The indexer takes the new set into its next round (who indexes depends on the ports a Vault holds). Each of the six calls returns once the port is in place, with `PortChange.number`, the number of this port change of this open Vault; `IndexState.port_change` reaches it once the indexer has compared those ports, or later ones, with the Index (LIB-27). The `Describe` of an embedder and a Projector is read once, when the port is given; one that breaks its rules fails the call with `INVALID_ARGUMENT`. A port is given in the form its implementation has, blocking or async, and the Vault calls its async form: a blocking port runs on the blocking pool (`Offload`), an async one is awaited as a task of its own, so that a panic in it is `Panicked` and a dropped call aborts it. A port of a feature the build lacks is `UNIMPLEMENTED`, and so is the Projector, the embedder, and the reranker in a build without `index`; a reference that holds nothing is `INVALID_ARGUMENT`. Without a Projector, writes and `Collection.Get` still work, a query that names only `id` still works, any other column of a Filter is `INVALID_ARGUMENT`, and a search has no FTS/vector columns. Without an embedder, the Vault does not index a collection with a `vector` column and its searches run without the vector leg (`06` IDX-9). A `vector` column is a `text` or a `text list`: each text of a list gets its own vector, and a search ranks the Document once, by its closest text (`06` IDX-7). A search that sets `rerank_limit` needs a reranker (QRY-5). *Check:* a Projector, an embedder, and a reranker are installed with the Index and refused without it (`tests/ports.rs`: `an_embedder_and_a_reranker_are_installed_with_the_index_and_refused_without`, `a_projector_is_installed_with_the_index_and_refused_without`); a descriptor is read once (`ports::tests::describe_is_called_once_per_install_whatever_is_embedded_after`). *Check:* a descriptor that breaks its rules fails `Scheda.Open` and `Vault.SetEmbedder` (`tests/ports.rs`: `an_embedder_whose_descriptor_breaks_its_rules_is_invalid_argument_and_writes_nothing`); a reference without an implementation is `INVALID_ARGUMENT` and removing a port that is not there is nothing (`tests/objects.rs`: `a_port_without_an_implementation_is_refused_and_removing_one_is_nothing`). *Check:* an async port is awaited on either runtime and a port that panics fails the call with `Panicked` (`ports::tests::an_async_embedder_is_awaited_on_either_runtime`, `ports::tests::a_port_that_panics_fails_the_call_with_panicked`). *Check:* a Vault without the embedder a `vector` column needs does not index until one is given (`tests/consumer.rs`: `a_vault_without_an_embedder_does_not_index_until_one_is_set`).

**LIB-32. The write model.** A single write (`Collection.Create`, `Update`, `Upsert`, `Delete`; `Vault.CreateCollection`, `UpdateCollection`, `DeleteCollection`) is atomic: when the call returns `Ok` the write is stored, and when it fails nothing was written. Several writes are one batch: a stream of operations (`Collection.Batch`, `Vault.BatchDocuments`, `Vault.BatchCollections`) of which all happen or none; an `Err` item, a broken stream, or one write that fails, and none happened, and the error names the operation by its index. A batch holds Document writes or collection writes, never both, and `Vault.BatchDocuments` does not mix isolated collections with the others (`INVALID_ARGUMENT`: they are two repositories). Writes from every object and every process on one Vault are applied one after another, in the order they were made; no write fails because another one is running. A write waits for the write lock (STO-4) up to `OpenOptions.write_timeout_ms` (default 60000); past it the call is `ABORTED` and writes nothing, and once it holds the lock it finishes. A write is `ABORTED` too when `HEAD` moved under it (a `git` command run by hand). One verb per meaning: `Create` of a Document that is present is `ALREADY_EXISTS` (or, with `keep_existing`, the stored Document is returned and nothing is written); `Update` of an absent one is `NOT_FOUND`, with `revision` the stored revision must be that one or `FAILED_PRECONDITION`; `Upsert` creates or replaces; `Delete` of an absent one is `NOT_FOUND` (or nothing with `ignore_missing`). The same bytes store nothing and keep the revision. `Document.revision` is an opaque token that changes when the stored bytes change. Every write carries a `note` (why it is made; `Collection.History` shows it). `auto_sync` pushes after a write and a failure of the push neither fails nor undoes the write (`Mirror.Info`). A write answers with the state token of the Vault it made (`DocumentWriteResult { document, version }`, and `version` on the batch results); a call that stored nothing gives the token of the state it found, and an empty batch reads it without the lock. The token is for `not_before` (`06` QRY-8). A call that is dropped midway stops at its next `await` (LIB-29). There is no interactive transaction: a caller builds a write whole before it calls (`10`). The contract of each call is its rpc comment. *Check:* a batch is one commit with one result per operation (`tests/documents.rs`: `a_batch_is_one_commit_with_one_result_per_operation`); a failing write in the middle stores nothing and names its index (`tests/documents.rs`: `a_failing_write_in_the_middle_of_a_batch_stores_nothing_and_names_its_index`; `tests/collections.rs`: `a_batch_with_a_failing_third_operation_declares_changes_and_deletes_nothing`). *Check:* a call that cannot take the lock in time is `ABORTED` and stores nothing (`tests/documents.rs`: `a_call_that_cannot_take_the_lock_in_time_is_aborted_and_stores_nothing`; `tests/consumer.rs`: `a_write_while_another_holds_the_lock_past_the_timeout_is_aborted_and_retryable`). *Check:* writes from one handle and from three processes are each stored whole (`tests/documents.rs`: `sixty_four_document_writes_from_one_handle_are_each_stored_whole`, `sixty_six_document_writes_from_three_processes_are_each_stored_whole`). *Check:* a write returns the token of the commit it made, among many writers, and an empty batch waits for no lock (`tests/documents.rs`: `a_write_returns_the_token_of_the_commit_it_made_in_the_main_repository`, `the_token_of_a_write_names_its_own_commit_among_many_writers`, `an_empty_batch_waits_for_no_lock_and_answers_with_the_state_now`). *Check:* the verbs behave as the table says in every kind of collection (`tests/documents.rs`: `the_table_holds_for_a_standard_collection`, `the_table_holds_for_a_singleton`, `the_table_holds_for_a_journal`).

**LIB-33. Consistency.** Reads see stored state only: a write whose call has not returned is seen by no read (`document_calls::tests::a_write_that_has_not_returned_is_seen_by_no_read_and_touches_no_file`), and a file a person changed and did not commit is seen by none (`tests/documents.rs`: `a_persons_uncommitted_edit_is_seen_by_no_get_document_and_a_commit_by_hand_is`). A read of Documents (`Collection.Get`, `GetMany`, `History`) never waits on the Index. A stream is lazy and reads from one snapshot, so a Document written while it is read does not appear in it (`tests/reads.rs`: `a_stream_started_before_a_write_does_not_see_it`). The Index follows the stored state in the background (`06` IDX-9): queries and searches answer from what it holds, so without `not_before` they are eventually consistent. A call that names the token of a write (`not_before`) waits until the Index reflects it, up to `index_wait_timeout_ms`, then `DEADLINE_EXCEEDED`; `Index.Watch` tells how far the Index is. A query or a search reads one snapshot of the Index, so it sees one state across all collections. An Index not built yet is `INDEX_REBUILDING`, never an empty answer (`06` QRY-4). *Check:* a write is found by a query once the Index reached it, and by a call that names its token (`tests/consumer.rs`: `watch_reports_the_version_of_a_write_and_the_write_is_then_found`; `tests/query.rs`: `a_query_waits_for_its_write_with_not_before_and_a_reset_commit_does_not_wait`; `tests/search.rs`: `a_search_given_the_token_of_a_write_finds_it`).

**LIB-34. Requests are strict, stored data is read as Protobuf reads it.** A request that breaks a rule of its message is `INVALID_ARGUMENT` before the write lock is taken (`tests/documents.rs`: `a_request_that_breaks_a_rule_fails_before_the_lock_is_taken`). Protobuf JSON a caller sends (CLI stdin, an agent's request) is parsed as Protobuf JSON is by default: an unknown field is `INVALID_ARGUMENT` naming its path (`stored::tests::a_command_with_an_unknown_field_is_invalid_argument_naming_its_path`), since a binary that silently dropped an option of a later caller would do something other than asked. Files Scheda keeps as a message (the marker, a collection file) are read past a field they do not know, and a rewrite keeps it (`20` D21; `tests/open.rs`: `an_unknown_key_in_the_marker_and_a_leftover_version_in_a_collection_file_open`; `tests/collections.rs`: `update_keeps_the_unknown_keys_of_the_file_and_writes_no_default`).

## 3. Mirror and maintenance

**LIB-12.** *Retired (docs/20 D6):* there is no `commit`; a write is stored when its call returns (LIB-32).

**LIB-22.** *Retired (docs/20 D6):* there is no `begin`; several writes are one batch (LIB-32).

**LIB-23.** *Retired (docs/20 D6):* there is no `discard`; a write that fails wrote nothing (LIB-32).

**LIB-30.** *Retired (docs/20 D6):* there is no `transaction`; a batch is the one way to write several things as one (LIB-32).

**LIB-13.** *Retired (docs/20 D12):* `open` is `Scheda.Open`; the contract is its rpc comment in `scheda.proto` and the comments of `OpenOptions` in `options.proto`.

**LIB-14.** *Retired (docs/20 D12, D14):* `pull`, `push`, and `sync` are `Mirror.Pull`, `Mirror.Push`, and `Mirror.Sync` (with `Mirror.Info`, `Mirror.Set`, `Mirror.Remove`); the contract is their rpc comments in `mirror.proto`. The `*_isolated` calls are gone: isolated collections never leave the machine (ISO-6).

**LIB-15.** *Retired (docs/20 D12, D15):* `check` is `Vault.Check`, which returns a `CheckReport`; the contract is its rpc comment in `vault.proto`.

`Vault.Check` reads the marker of `HEAD` first (`04` GIT-14): a marker of another generation (`GENERATION`), a broken one (`INVALID_ARGUMENT`), or none (`NOT_A_VAULT`) is the one problem it reports, with `path` `.scheda.yaml`, and no other check runs; a collection file that does not load is a problem with its path, and the other collections are still checked. `Mirror.Pull` and `Mirror.Sync` read the marker and the collection files of the commit they would move `HEAD` to before they move it, and refuse with the same codes (`04` GIT-11). `Vault.Check` does not judge Index freshness: the Index lags `HEAD` by design (IDX-9), and `Index.Status` (LIB-27) reports the state it reached. It takes `index.lock` without waiting while it reads the Index modes; while a round holds it, the generations (Lance's files, written with the process umask and narrowed when the round ends) are not looked at, so they are not reported as a wide mode. After the round every file is owner-only (`tests/search.rs`: `every_file_of_the_index_is_owner_only_after_a_round`). *Check (**search**):* `Collection.Create`, then `Vault.Check` passes.

**LIB-16. `Index.Reindex`.** IDX-1, IDX-9. On the Index object of a Vault (`Vault.Index`), in a build with `index`. It asks this Vault's indexer for a rebuild and returns at once. The rebuild is an indexer round under `{vault}/.scheda/index.lock` (`06` IDX-9): it builds a new generation beside the live one from the git objects of `HEAD` of the Vault and of `{vault}/.isolated/` — never the work tree, so an uncommitted edit is not indexed — with this Vault's Projector and embedder, catches up once to the `HEAD` of the moment, and switches by writing `current`. **Meanwhile the live Index is frozen:** queries and searches keep answering from it, at its `version`; the writes made during the rebuild appear at the switch, and a call whose `not_before` is past that version waits for the switch (`DEADLINE_EXCEEDED` on a long rebuild). Writes, pulls, and syncs in every handle go on: the rebuild takes no write lock. `INDEX_REBUILDING` is only for an Index never built. Progress and result are in `IndexState.rebuild`: the stage (`RUNNING`, `DONE` — the switch, `FAILED` — the live Index stays), the cause (`CAUSE_REINDEX`, or `CAUSE_NEW` for an Index that did not exist), Documents read, Documents skipped (not read or refused by the Projector), journal segments read. A rebuild that fails is tried again from nothing after a pause; the request stands until a rebuild is done. The request records the live generation; when another Vault on the path, asked too, switched to a generation built with this Vault's ports and columns meanwhile, the request is done without a rebuild (`RUNNING`, then `DONE` with no Documents read). With the embedder model and vector length of the live generation, a text whose vector the live generation holds for the same Document is not embedded again (a live generation whose vectors cannot be read gives none); with another model every text is. The old generation is removed an hour after the switch. Because the rebuild uses this Vault's ports, **it is the only way the Index moves to a new projection, other columns, or a new embedder model**, and how an `INDEX_BROKEN` Index is repaired; after the switch a Vault of other ports is `INDEX_STALE`. Encrypted collections are skipped (ISO-4); isolated collections are indexed. A Vault that lacks a port the Index needs (an embedder for a `vector` column, or a Projector when the Index was built with one) → `FAILED_PRECONDITION` naming it; a rebuild already asked for and not done in this Vault → `ABORTED`. *Check:* `Reindex` returns before the rebuild ends and a second one meanwhile is `ABORTED` (`indexer::tests::a_rebuild_waits_for_the_lock_and_a_second_request_is_aborted`); a rebuild that fails is tried again until it is done (`tables::tests::a_rebuild_that_fails_is_tried_again_until_it_is_done`); a rebuild two Vaults ask for at once is built once and done for both (`tables::tests::a_rebuild_asked_by_two_vaults_at_once_is_built_once_and_done_for_both`). *Check:* a rebuild answers from the live generation and switches with the writes made meanwhile; a process killed during one leaves the live generation serving (`tests/search.rs`: `a_rebuild_answers_from_the_live_generation_and_switches_with_the_writes_made_meanwhile`, `a_process_killed_during_a_rebuild_leaves_the_live_generation_serving`); searches go on during a `Reindex` (`tests/consumer.rs`: `searches_go_on_while_the_index_is_rebuilt`). *Check:* a Vault of other ports is `INDEX_STALE` (`tests/query.rs`: `an_index_never_built_is_rebuilding_and_one_of_another_projection_is_stale`). *Check:* a rebuild with the same model embeds no text again, one with another model every text, and one beside unreadable vectors embeds them again (`tables::tests::a_rebuild_with_the_same_model_embeds_no_text_again_one_with_another_embeds_each`, `a_rebuild_beside_a_generation_whose_vectors_cannot_be_read_embeds_them_again`).

**LIB-17.** *Retired (docs/20 D12):* `history` is `Collection.History`; the contract is its rpc comment in `collection.proto`.

**LIB-18 (retired).** RFC 8785 canonical JSON of journal lines. A journal `Collection.Create` writes the envelope `{id}: {payload}\n` (MOD-16). A journal Document's `raw` is the payload. There is no library canonicalization of consumer fields.

**LIB-19.** *Retired (docs/20 D12):* `lines` is `Collection.GetMany` with a listing of a `journal`, in append order; the contract is its rpc comment in `collection.proto`.

**LIB-25.** *Retired (docs/20 D12):* `documents` is `Collection.GetMany` with a listing of a `standard` or `singleton` collection, in `id` order, with `include_raw`; the contract is its rpc comment in `collection.proto`.

**LIB-27. `Index.Status` / `Index.Watch`.** On the Index object of a Vault, in a build with `index`; a build without it has no Index object (`UNIMPLEMENTED`). `Status` returns `IndexState` now. `Watch` streams it: the state at once, then one item per change (an indexer round, a failure, `stored_version` moving, a rebuild starting, moving on, ending); it does not end by itself, and the caller drops it when it has what it waited for. The fields are those of `06` IDX-9: `version` (the opaque token of the state the whole Index reflects; unset only before the first build ends), `stored_version` (the stored state the indexer last saw, never behind `version`), `pending`, `role`, `rebuild` (`stage`, `cause`, counts), `last_error`, `port_change` (the last port change of this Vault the state reflects). Neither call runs git or reads the Index. A port set or removed (`Vault.Set…`, `Remove…`), or other ports given at open, shows in the round it wakes, with no write: `last_error` becomes `INDEX_STALE`, with the reason a query or a search gives, or `FAILED_PRECONDITION` naming the port the Vault lacks, and clears once the Index's port is set again (`06` IDX-9). The caller waits for that state by the number its call returned: it watches, or reads `Status`, until `port_change` is at least `PortChange.number`, then reads `last_error`, the verdict for the ports it set; a look that compares and finds nothing else new still gives that item. It decides from it whether to call `Index.Reindex`, needs no probe search, and need not know the verdict in advance. A caller that must see its write passes the token of that write as `not_before` to the query or search (`06` QRY-8), or watches until `version` equals the token. `Watch` waits without holding a thread: a watcher that drops its stream is gone at once. *Check:* `Watch` gives the state at once and then one item per round; a watcher that falls far behind skips to the oldest item kept (`indexer::tests::the_watch_gives_the_state_at_once_and_then_one_item_per_round`, `indexer::tests::a_watcher_that_falls_far_behind_skips_to_the_oldest_item_kept`); a write's `version` is then reported (`tests/consumer.rs`: `watch_reports_the_version_of_a_write_and_the_write_is_then_found`); a port set or removed shows in both with no write (`tests/search.rs`: `a_port_set_or_removed_shows_in_the_index_state_without_a_write`), and a wait by the number of the change alone gives its verdict, in the Vault that indexes and in one beside it on the same path, whose numbers are its own, while the other's round holds `index.lock` too (`tests/search.rs`: `a_port_change_gives_a_number_the_index_state_reaches_with_its_verdict`, `a_vault_beside_the_one_that_indexes_reaches_the_number_of_its_port_change_with_its_verdict`).

**LIB-28. `Vault.Close`.** On the Vault. Shuts the gate of the Vault: new calls through the Vault and every object reached from it fail with `FAILED_PRECONDITION` from the start of `Close`, and a wait for `not_before` ends with the same code. `Close` waits, without a thread, for the calls and blocking steps that run (a step of a call that was dropped included), stops the indexer, awaits its task, and returns with every lock let go. A task that ended by a panic outside a round is reported as `PANICKED`, and one the runtime cancelled (the runtime shut down under it) as `CANCELLED`. A round stops between the portions of an embedding and between steps, so the wait is bounded by one portion of the caller's embedder. A second `Close` does nothing. An open stream does not hold `Close` up: its next item is `FAILED_PRECONDITION`. **Drop:** a Vault whose references (its objects' and streams' included) are all dropped cannot wait in its destructor; it signals the indexer to stop, and the task ends after its current round, in the background, so `index.lock` may be held a moment longer and another Vault takes the role a round later. A Vault lives on the runtime that opened it: when that runtime shuts down, its indexer ends with it, and the Index stays sound (`06` IDX-2). `commit` stays at the last finished round; what a stopped round wrote stays ahead of it, believed by no reader, and the next round starts from `commit` again. Scheda installs no signal handler: a program that wants a clean exit on `SIGINT` / `SIGTERM` catches the signal and calls `Vault.Close`; being killed instead loses nothing. A `git` command runs apart from the program's terminal (`04` GIT-1), so a terminal's signal does not reach it, and `Close` waits for the call that runs it: such a program drops those calls first. *Check:* after `Vault.Close` (or the last drop) the indexer task is gone (`tests/index.rs`: `close_and_drop_end_the_indexer_task`); a cancelled task is `CANCELLED` and a panicked one `PANICKED` (`indexer::tests::stop_reports_a_cancelled_task_as_cancelled_and_a_panicked_one_as_panicked`); after `Close` every object is `FAILED_PRECONDITION`, a second `Close` is nothing, and a stream fails its next item (`tests/objects.rs`: `after_close_every_object_is_failed_precondition_and_a_second_close_is_nothing`; `tests/runtime.rs`: `a_stream_after_close_fails_its_next_item_and_ends`); `Close` waits for a running write (`tests/objects.rs`: `close_waits_for_a_running_write_and_holds_no_lock_after`) and for a write dropped during its commit (`service::tests::a_write_dropped_during_its_commit_is_stored_and_close_waits_for_it`).

**LIB-29. Waiting, steps, and dropped calls.** A call waits without holding a thread: for the write turn (first come, first served) and for `commit.lock` with an `await` (a `try_lock` and an async sleep, up to `write_timeout_ms`), for `git clone`, `fetch`, and `push` (child processes that are awaited; when the call is dropped, the command and every process it started are killed: on Unix its process group, on Windows its job object), for another `open` of the same new path, for the caller's async ports, for the Index's own futures, and for the signals of the indexer. The work itself is done in blocking steps on the blocking pool of the runtime of the call, the smallest piece that must not be cut in two: one commit, the read of one Document, the tree difference of a round, the projection of one Document. A step enters the core only through the gate of `scheda-blocking`, which the compiler checks. A call whose future is dropped stops at its next `await`: the step it is in runs to its end and no step after it starts. A write dropped while it waits for the lock stores nothing and takes no lock; a write dropped during its commit is stored, as if awaited, and the caller does not learn it; dropped during the push of `auto_sync`, the push is killed with every process it started (the mirror's side of a `file://` push, `ssh`), the commit stays local, and the next push carries it. A read dropped midway changes nothing. A panic in a port, or in the work of a call on the Index, is `Panicked`. A write runs the checks that need no lock first, so a request that can never succeed fails at once, never `ABORTED`. *Check:* a write waiting for the lock holds no pool thread and aborts at the deadline (`tests/runtime.rs`: `a_write_waiting_for_the_write_lock_holds_no_pool_thread_and_aborts_at_the_deadline`); a write dropped while it waits writes nothing and takes no lock (`tests/runtime.rs`: `a_write_dropped_while_it_waits_for_the_lock_writes_nothing_and_takes_no_lock`); a push dropped midway leaves the commit local and no process of the push behind, and the next push carries it (`tests/runtime.rs`: `a_push_dropped_midway_leaves_the_commit_local_and_the_next_push_carries_it`); a request that can never succeed fails at once while the lock is held (`tests/runtime.rs`: `a_request_that_can_never_succeed_fails_at_once_while_the_write_lock_is_held`); a panicking port is `Panicked` (`ports::tests::a_port_that_panics_fails_the_call_with_panicked`).

## 4. What this API refuses

- Partial patch of Document bytes.
- A Document file path from the caller. `Get` / `Create` / `Update` / `Delete` / `History` take a validated `id` and the library opens, creates, or gits the file. A query and a search take `id`s from the Index (IDX-10). `GetMany` walks the Documents under the collection; the caller does not pass a path, a directory, or a glob.
- Delete of a journal line (`Collection.Delete` on a `journal` is `UNIMPLEMENTED`).
- A request with a field the contract does not know, or that breaks its rules (LIB-34).
- A call, field, or term that says commit, transaction, or `HEAD` (LIB-2), and an interactive transaction that holds the write lock while the caller works (LIB-32).
- Cross-Vault query unless the caller passes two Vaults into a combined helper (**later**).
- Shipping a ranking model in the library (QRY-5). A `Reranker` and a `Projector` are ports the caller gives (LIB-31); they are not Vault data.

## 5. First implementation (Rust)

The crate `scheda` is the first binding. It must:

- implement every rpc above through the generated async traits (`VaultAsync`, `CollectionAsync`, `MirrorAsync`, `IndexAsync`, `SchedaAsync`); the blocking traits (`VaultSync`, …) come from `to_sync()` on a reference (LIB-6);
- keep the objects private: the public surface is `scheda::Scheda` (the root), `scheda::v1`, `Error`, `Fault`, `Context`, `error_report`, `redact_remote_text`, `parse_command`, the fixed-portion adapters `FixedEmbedder` and `FixedReranker` and their async forms `FixedEmbedderAsync` and `FixedRerankerAsync` (`13`), and, with `encrypt`, `parse_age_identity`;
- use `Result` with `scheda::Error` carrying the LIB-5 codes (no `panic!` / `unwrap` / `expect` / `assert!` on the library path; tests may assert);
- carry `[lints] workspace = true` as in this repository.

That panic policy is **Rust**, not a requirement on other languages (Python, Java, Go, TypeScript, and others use their usual error conventions, still with LIB-5 codes).

## 6. What this document does not decide

How a binding wraps generated types (builders, `Result`, exceptions) as long as proto field names and rpc names hold. How a binding writes a port and gives it to the Vault is the binding's affair. How a binding offers a blocking form: Rust gives `to_sync()` inside a multi-thread runtime (LIB-6).

Isolated `encryption` / age armor — `09` (**later**).
`Projector.Columns` returns an `IndexSchema` (`ports.proto`). Filter column names — `06` / `13`.
