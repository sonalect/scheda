# 07. Library API

Document 7 of the Scheda package. Version 1.03, 19 October 2026.

LIB-16, LIB-27, and LIB-28 follow the indexer of the `proto-contract` branch (`06` IDX-9, `20` D18, D23). The rest of this document is rewritten per `20` D12 in the docs pass of `20` §5.

Language-neutral contract: operations, arguments, outcomes, and error codes.
Message field names and constraints live in `api/v1` (Protobuf edition 2024,
protovalidate rules). Bindings (Rust first; later Python, Java, Go,
TypeScript, and others) use these names or a documented 1:1 mapping. A
caller-supplied message that fails those rules is `invalid`, before the
collection declaration, git, or the write lock. Agent transport (`08`) is
the Protobuf JSON mapping of those messages. Codes: `LIB`. Phase **core**
unless marked **search** or **agent**.

Idioms of one language appear only in a sentence that names that language (`02`).

An assertion without a check is not a requirement.

## 1. Shape of a binding

**LIB-1. In-process library.** The caller loads Scheda in its own process. A Scheda daemon or HTTP server is not required to read or write. *Check (**core**):* a test writes and reads a local Vault (`auto_sync` off) with no second process and no network.

**LIB-2. Same operations in every language.** Required names: `open`, `info`, `collection`, `add`, `get`, `replace`, `remove`, `find`, `search`, `begin`, `commit`, `discard`, `push`, `pull`, `sync`, `check`, `reindex`. **Agent** also requires `create_collection` (LIB-21). AGT-1 listing is `info` (LIB-4, LIB-20), not a separate `catalog` method. Optional: `history`, `lines`, `documents`, `ids` (core in this binding), `push_isolated`, `pull_isolated`, `sync_isolated`, `transaction` (LIB-30), `index_status`, `wait_indexed`, `close` (LIB-27, LIB-28; in this binding with `find`, `close` in every build). There is no `init`, `clone`, `catalog`, `walk`, `walk_inverse`, or `scan` as a public name: creating or cloning a Vault is `open` (LIB-13, GIT-9). Ordered journal read without the Index is `lines` (LIB-19), not `scan`. Listing a `document` collection without the Index is `documents` and `ids` (LIB-25, LIB-26), also not `scan`. The CLI does not encode `begin` / `commit` / `discard` (GIT-2: a process-per-command CLI cannot hold a transaction). The CLI does encode `documents` / `ids` and the isolated Remote calls. In Rust `scheda`, `find`, `search`, and `encrypt` are opt-in crate features; there is no default feature set, so a plain `cargo add scheda` omits those method names (`10` §2). `encrypt` adds no method name — it decides whether the handle can read and write an encrypted collection at all, and a build without it refuses those collections by code (LIB-15, ISO-5). *Check:* a binding that omits a required name is incomplete; aliases are allowed only if the docs of that binding list the mapping.

**LIB-3. Whole-record writes.** Mutation is `add`, `replace`, or `remove` of the whole Record's bytes. There is no partial patch of contents. SQL against the Index is not a caller API. *Check:* `replace` on `journal` is a failure (`unsupported`). *Check:* `remove` on `journal` is a failure (`unsupported`).

**LIB-4. Observable `open`.** After `open`, `info` returns `api.v1.VaultInfo` (same proto object as today): Vault path, Index path (`{vault}/.scheda/index`), `remote` (GIT-7: `origin` or empty), `auto_sync` on this handle, and the collection list. The list is collection declarations (`05`): kind, isolation, encryption, caps, Index-exclusion flags — not Record fields. The Vault root is the only filesystem path the caller supplies. **Later:** isolated collections listed with `declaration.isolated` and encrypted ones with `declaration.encrypted` (ISO-3, SCH-16); the two marks are independent and `info` reports each on its own. No process-global singleton that forbids a second Vault. Options at `open` include `auto_sync` (GIT-10), `remote_repo` (GIT-9; an absolute URI or scp-style `git@host:path` when set), commit identity (`OpenOptions.author`, `api.v1.Author`; GIT-2), writer identity (`OpenOptions.writer`; unset → generated into `{vault}/.scheda/writer`), an embedder (IDX-8), and an optional **Projector** (same injection class as the embedder: caller code, not an `api/v1` field). The Rust shape of that option is the binding's affair. Without a Projector, writes and `get` still work; `find` on identity (`all`, `term` on `id`) still works; any other Filter field is `invalid`; `search` has no FTS/vector slots. There is no option that turns autocommit off: the only supported batch is a transaction (GIT-2). **Later:** `encryption` (`api.v1.Encryption`), the one secret this handle uses for every encrypted collection it touches (ISO-5, ISO-7). Setting it never encrypts anything by itself: what is ciphertext on disk is decided by each collection's declaration (SCH-16). In a build without the `encrypt` feature, setting it is `unsupported_encryption` and `open` creates nothing. The Index directory is not a caller option (GIT-13). `open` does not keep the write lock; mutating calls take it for that write. Repairing `.gitignore` and adding the marker on an existing Vault take the lock for that write (one commit), then release it before `open` returns. When `auto_sync` is on and a Remote exists, the auto-pull on `open` takes the lock for that pull (STO-4, GIT-10), then releases it; a writer already holding the lock → `locked`. *Check (**core**):* two `open`s on different roots in one process. *Check:* creating a Vault writes `.gitignore` with `.scheda/` and `.isolated/`; Index files are ignored; deleting `.scheda/` does not delete Records. *Check:* `open` with network disabled still reports `origin` on `info.remote` when that remote is configured (GIT-7). *Check:* `open` with `auto_sync` on while another handle holds the write lock → `locked`.

**LIB-5. Failures are coded.** Every failure has a stable code plus an optional human message. The message must not replace the code. The code is `api.v1.Error.Code` (Protobuf JSON `CODE_*`). **Core** includes at least: `not_found`, `invalid`, `not_utf8` (non-UTF-8 `raw` on `add` / `replace`), `duplicate_id` (same Record `id` already present), `conflict_markers` (git conflict markers in a file), `not_fast_forward` (GIT-10, GIT-11), `locked` (STO-4), one `io_*` per stable `std::io::ErrorKind` (no coarse `io`), one `git_*` per git failure class classified from the git CLI (no coarse `git`; a non-fast-forward pull/push stays `not_fast_forward`), Index `index_missing` / `index_version` / `index_lexical` / `index_vector` / `index_corrupt` (QRY-4; no coarse `index_unusable`), `unsupported` (`replace` / `remove` on `journal`; `lines` on `document` / `singleton`; `documents` / `ids` on `journal`; `find` / `search` naming an encrypted collection). **Later:** `crypto` (the secret is absent, wrong, or the bytes will not decrypt — ISO-5) and `unsupported_encryption` (this build has no `encrypt` feature, so no secret and no retry helps; `repeat` is false). Those two are not interchangeable and neither is a substitute for `unsupported` or `invalid`:`crypto` says supply a secret, `unsupported_encryption` says use another build, `unsupported` says the operation does not apply however it was built, and `invalid` says the collection declaration is wrong (SCH-16). *Check:* negative tests assert codes, not only message text. *Check (**later**):* a wrong passphrase is `crypto`, a thin build is `unsupported_encryption`, `find` on an encrypted collection is `unsupported`, and an encrypted `journal` declaration is `invalid` — four distinct codes.

How a language surfaces a code is that language's affair. Examples: Rust `Result` with an error type that carries the code; Go `(value, error)`; Python exception or a result object; Java exception or a result type; TypeScript throw or a result object. The code string is what tests and `08` share.

**LIB-6. Sync is enough for core.** `add`, `replace`, `remove`, `get`, `find`, `lines`, `begin`, `commit`, `discard` must not require an async runtime. The background indexer (IDX-9) is a plain thread, not a runtime task. `search` with a local embedder or reranker may be synchronous in the same process. An async layer is optional and sits on top of the sync calls (LIB-29). *Check (**core**):* a binding's core tests run without starting an async executor. (Rust: no Tokio required for those tests; a build without the `tokio` feature has no Tokio dependency.)

## 2. Record I/O

**LIB-7. `add(id, raw, message?)`.** On the collection handle. `id` is a method argument; the library checks it before any file is written (SCH-12). Each component is a slug (Unicode letter or digit, then letters, digits, combining marks, `.`, `_`, `-`, `+`, `(`, `)`, space, or `@`; not a Windows device name such as `CON`; no leading/trailing whitespace; no trailing `.`). A component must not be empty, `.`, or `..`, and must not start with `.`. A `document` `id` may be `/`-separated slugs (`work/meeting.toml` → `{name}/work/meeting.toml`); the whole string is at most 255 bytes. The library does not append `.md`. An extension, if any, is part of `id` (`foo.md`). `journal` and `singleton` remain a single slug. Argument `raw` is bytes, not an `api.v1` message. Empty `raw` is allowed (empty file / empty payload). Non-UTF-8 `raw` is `not_utf8`. In Rust the argument is `impl AsRef<[u8]>`. `add` does not call `Projector.project` to accept or reject the write. Optional `message` is the git commit subject outside a transaction; omitted → `scheda`. A message that is present but empty is `invalid` before any file is written. Inside a transaction the argument is ignored; `commit` supplies the subject (GIT-2). Creates a `document` file, appends a journal envelope line `{id}: {payload}\n` (MOD-16; payload is `raw`, which must not contain `\n` or `\r`), or creates a `singleton` if absent (MOD-15–17), and for a `journal` updates its `id` map at once (IDX-5); the lexical and vector Index follow the commit in the background (IDX-9). Success is `()`. Same `id` already present → `duplicate_id`. Collection is the handle, not a field. Outside a transaction, then one git commit (GIT-2). Inside a transaction, does not `commit`. There is no `OpenOptions` switch that turns autocommit off; a consumer that writes many lines must `begin` first (GIT-2). Does not `pull`. *Check:* `add` with empty `id` → `invalid`. *Check:* `id` starting with `.` or `-`, or containing `$` / `;` → `invalid`. *Check:* trailing space → `invalid`. *Check:* `../x`, `foo/./bar`, `/abs`, and `a\\b` → `invalid`. *Check:* round-trip with `get`. *Check:* empty `raw` round-trips as empty bytes. *Check:* without `begin`, `git log` gains one commit. *Check:* without `begin`, a passed message is that commit's subject; omitted → `scheda`. *Check:* a present but empty message is `invalid` and no file is written. *Check:* 10³ journal `add` after `begin`, one `commit` → `git log` grows by one. *Check:* drop the handle mid-transaction after complete lines plus a truncated tail; reopen without `begin` / `discard`; `get` returns the complete Records and not the truncated line. *Check:* `document` `add("work/meeting.toml")` writes `{name}/work/meeting.toml`. *Check:* `add("foo.md")` writes `{name}/foo.md`.

**LIB-8. `get(id)`.** On the collection handle. Validate the `id` (same rules as LIB-7), then open the Record file for that identity (IDX-10, QRY-1). Does not consult the Index for `document` / `singleton` (journal uses the IDX-5 map to find the segment; wipe-Index `get` may scan envelopes). Returns `api.v1` `Record`: `collection` (output only), `id`, `raw` (document / singleton: the file bytes; journal: the envelope payload, not the envelope). No `path`: identity is `(collection, id)`. Vault-relative file paths stay on `Error.path` when `check` / IO name a file. No `fields`, no `body`. `valid` is removed (it meant Schema match). Malformed UTF-8 on disk is reported by `check`, not by a flag on `get`; `get` still returns the bytes if the file exists. Missing Record → code `not_found`, not an empty Record. **Later:** on an encrypted collection, `raw` is the **decrypted** plaintext (STO-2), not the age armor on disk. *Check:* missing id → `not_found`; a file that exists is returned even when a later `Projector` would omit it (SCH-12). *Check:* illegal slug → `invalid` and no file open. *Check:* `get("foo.md")` reads `{name}/foo.md`. *Check:* `get("work/meeting.toml")` reads `{name}/work/meeting.toml`. *Check (**later**):* encrypted fixture → `get` bytes match `age -d` of the path.

**LIB-9. `replace(id, raw, message?)`.** On the collection handle. Existence is the Record file (same path as `get`, IDX-10), never the Index, which lags the last commit; missing → `not_found`. Do not invent a path by appending `.md` to the argument. Isolated is not a special case. Argument `raw` is bytes, not an `api.v1` message. Empty `raw` is allowed. Non-UTF-8 is `not_utf8`. In Rust the argument is `impl AsRef<[u8]>`. `id` is the method argument, not a field. Optional `message` is the same as LIB-7: subject outside a transaction, ignored inside one, empty → `invalid` before any file is written. Whole `document` or `singleton` only. `journal` → `unsupported`. Autocommit rules are the same as LIB-7 (GIT-2). *Check:* empty `id` → `invalid`. *Check:* journal call fails; `get` matches the new record. *Check (**find**):* a Record file the Index has not reached yet is replaced. **Later:** on an encrypted collection, the file at the path is age armor, not plaintext.

**LIB-24. `remove(id, message?)`.** On the collection handle. `document` and `singleton` only. `journal` → `unsupported` (MOD-16: a journal line does not leave). Validate the `id` first (same rules as LIB-7): illegal → `invalid` before any file is touched. Optional `message` is the same as LIB-7: subject outside a transaction, ignored inside one, empty → `invalid` before any file is written. Unknown `id` → `not_found`. Existence is the Record file (same path as `get`), as for `replace`. A file git never tracked is deleted without a commit. Isolated is not a special case. Unlinks the Record file as a whole (STO-5: the path holds the file or nothing, never a partial) and stages the deletion like any other mutation: autocommit outside a transaction, part of the batch inside one (GIT-2). Isolated collections use the nested git. After a nested `document` unlink, empty parent directories under the collection are removed. `get` answers `not_found` at once; the Record leaves the Index after the commit, in the background (IDX-9). `history(id)` still answers from git after the file is gone. *Check:* `remove` then `get` → `not_found`; the file is gone. *Check:* unknown `id` → `not_found`. *Check:* illegal slug → `invalid` and no file is touched. *Check:* `journal` → `unsupported`. *Check:* `history` after `remove` still returns the commits that stored the file. *Check:* `remove("work/meeting.toml")` unlinks `{name}/work/meeting.toml` and removes an empty `work/` directory. *Check (**find**):* after `wait_indexed`, `find` / `search` no longer return that `id`; a Record file the Index has not reached yet is removed.

**LIB-10. `find(collections, query, offset, count)`.** On the Vault, and on the collection handle as `find(query, offset, count)` (that form uses Collection-handle Filter scope: a bare Projector field is this collection; it does not go through Vault `find` with one name). `collections` is a set of names. Empty → every non-isolated, non-encrypted collection on this handle; an empty set stays non-isolated so a broad scan does not surface sealed values (ISO-3). A named set: unknown name → `not_found`; isolated → an ordinary query, because one Index holds them too (ISO-4), and a set mixing isolated with plain names is one page with one `total`; encrypted → `unsupported`, because no Index holds one (ISO-4) and an empty page would be a lie the caller cannot tell from "nothing matched". An explicit name whose Projector cannot accept the `Filter` → `invalid` (`06` / `13`). Without a Projector, only identity (`all`, `term` on `id`) is accepted; any other field is `invalid`. Empty set: collections that cannot accept the `Filter` are omitted. Run a Tantivy 0.26 `Query` on the Index, then open files for the matching `(collection, id)`s (IDX-10). Query argument is `api.v1` `FindQuery` (`find.proto`): required `Filter` (the same kinds as `tantivy::query`:`all`, `empty`, `term`, `term_set`, `phrase`, `phrase_prefix`, `fuzzy`, `regex`, `regex_phrase`, `range`, `exists`, `boolean` with `must` / `should` / `must_not`, `boost`, `const_score`, `disjunction_max`, `more_like_this`) plus `include_raw` (unset or false omits `Record.raw`; `get` always returns `raw`). Collector is `(Count, TopDocs::with_limit(count).and_offset(offset))` (not a field on `FindQuery`), with `count` and `offset` clamped to the live document count first, because `TopDocs` reserves memory for both up front. Order: one `journal` collection → append order (QRY-7: `order_by_fast_field` on the indexed ordinal); otherwise Tantivy score descending with equal scores broken by that same ordinal ascending, so a page is reproducible for a given Index (QRY-7). `more_like_this` whose source is an `id` builds its terms from that Record's indexed text, so an unknown source `id` is `not_found`, not an empty page: a caller asking for "similar to X" cannot otherwise tell a missing X from nothing being similar. `count` `0` is `invalid` (Tantivy panics). Returns `api.v1` `FindResult` (same file): `records` (length at most `count`, each `api.v1.Record` as LIB-8: `collection`, `id`, `raw` when requested) and `total` (Tantivy `Count`: indexed hits matching the Filter). A missing file is omitted from the page and does not decrease `total`. Past the end → empty `records`; `total` is still the match count. Every indexed Record in the selected collections is `Filter` `all`. There is no `scan` method. Filter leaves may set proto `collection` (required on Vault projector columns; on the Collection handle, unset means this collection). `FindQuery` has no collection field. `Record.collection` is output only. *Check:* `should` of two `term`s on different fields returns the union. *Check:* `must` of two `term`s returns the intersection. *Check:* `count` `0` → `invalid`; `offset` beyond the last match → empty `records`. *Check:* empty `collections` on a two-collection fixture returns both; a one-name set returns only that collection. *Check:* `all` on a three-Record fixture with `count` 1 returns one Record and `total` 3. *Check:* `count` `u32::MAX` returns every match, and `offset` `u32::MAX` an empty page with the true `total`, without aborting. *Check:* `fuzzy.distance` 3 and a broken `regex_phrase` pattern are `invalid` and leave no `damaged` file in the generation. *Check:* default `find` omits `raw`; `include_raw` true fills `Record.raw`.

**LIB-11. `search(collections, query, reranker?)`.** Hybrid retrieval (`13`): BM25 over Projector `fts` columns and ANN over Projector `vector` slots (one slot, one vector; digest skip unchanged). No Projector: no FTS/vector slots; the embedder is not called on write. BM25 and ANN when both are on, RRF, then optional rerank. On the Vault, and on the collection handle as `search(query, reranker?)` (that form uses Collection-handle Filter scope, same as LIB-10). `collections` is the same set as LIB-10. Argument is `api.v1` `SearchQuery` plus an optional caller `Reranker` (`score_many` required, `score` provided as the batch call with one Record; `many_limit` is a non-zero size; not proto). `k` unset or `0` → 10; `k` and `rerank_limit` are at most 10000 (`invalid` above). Weights unset → `1`; **zero turns that leg off**. `filter` set → both legs search only the Records the Filter matches on the selected collections (BM25 with the Filter as a `Must` clause, USearch `filtered_search` on the `(collection, id)` set Tantivy returns). Fusion pool is at least `max(k, 50)`. With a reranker, `rerank_limit` N above that floor deepens both legs to `max(k, 50, N)` so the reranker can score a candidate at fused rank N, then cuts the fused list to N before Records are opened — unset scores every fused hit, `0` or a value below the effective `k` is `invalid`, and without a reranker it is ignored (pool stays `max(k, 50)`). N larger than the corpus scores every hit that exists. With a reranker the library opens those Records, scores (`score` when there is one candidate or `many_limit` is 1, otherwise `score_many` in chunks of `many_limit`), sorts, returns `k` with `rerank_score`. Without it, RRF order and no `rerank_score`. `include_raw` true fills `Hit.raw` (file bytes / journal payload); unset or false omits it. Output is `api.v1` `SearchHits`. `Hit.collection` is output only (same as `Record.collection`). `SearchHits.vector_leg` is set on every reply and says whether the vector leg ran or why not, the first that applies: not asked (`vector_weight` 0), no requested collection with vector slots (all excluded or encrypted, no Projector, or no Projector column marked `vector`), no embedder, no vectors in the Index yet, an embedder of another model than the Index vectors, else ran. It is decided before the query from what the handle holds, without extra I/O, so a vector-only query with no hits can tell "nothing matched" from "the vectors were not searched" without `index_status`. An Index built by a Projector of another projection, or a collection whose columns changed, is `INDEX_STALE`, Filter or not, as for `find` (`06` IDX-9). Scheda does not load a ranking model. **Search.** *Check:* QRY-3 fixture ids all appear at the given `k`; a hit from both legs carries both scores. *Check:* negative or non-finite weight → `invalid`. *Check:* `filter` that excludes a Record keeps it out of both legs. *Check:* reranker that inverts two hits is reflected in hit order. *Check:* empty `collections` on a two-collection fixture can hit both; a one-name set does not. *Check:* default `search` omits `Hit.raw`; `include_raw` true fills it. *Check:* `rerank_limit` above 50 hands that many candidates to the reranker; unset stays at the floor of 50. *Check:* `k` and `rerank_limit` of 10000 return; 10001 is `invalid`. *Check:* a reranked `search` skips a hit whose Record file is gone (the Index lags a `remove`) and succeeds. *Check:* one test per `vector_leg` value; a vector-only query with an embedder of another model returns no hits and `VECTOR_LEG_MODEL_MISMATCH`, with the matching embedder hits and `VECTOR_LEG_RAN` (`19` F2).

**LIB-20. Catalog is `info`.** AGT-1 listing is `Vault.info` returning `api.v1.VaultInfo` (nested `api.collection.v1.Schema` per collection inside `api.collection.v1.CollectionInfo.schema`; each list item includes `version`). Same content as collection files (`05` §7): collections, kinds, isolation, encryption, caps, Index-exclusion flags. Not a field catalog, not inferred from directories. No `catalog()` method and no request envelope. Isolated collections are listed with `schema.isolated`; encrypted ones with `schema.encrypted`. ISO-3 still omits sealed material from a broad scan; there are no field values to omit from `info`. **Freshness.** A handle reads the declarations from the work tree at `open`, and again from the work tree: once when a name it is asked for is unknown (`collection`, a `find` / `search` collection, a Filter leaf's `collection`), before it answers `not_found`; and, with `find`, whenever the Index passes a commit (the background indexer of any handle, with an indexing role or without, compares the main lexical and vector marks with those it last saw; `wait_indexed` does the same before it returns). So `info` and name lookups see a collection another handle or process declared, and a changed declaration of a known one, without a reopen. Reading the work tree keeps this handle's own uncommitted declaration inside a transaction. A collection handle keeps the declaration it was made with. **Agent.** *Check:* AGT-1. *Check:* `info` has no field list. *Check:* a handle opened before another handle or process declared `x` gets `collection("x")` without reopening, with and without `find`; after `wait_indexed`, `info` shows another handle's changed `exclude_vector_index`; a reload during an open transaction keeps the handle's own uncommitted collection (`19` F1).

**LIB-21. `create_collection(name, schema, message?)`.** Write one collection Schema. Argument is the collection name plus `api.collection.v1.Schema`. Not a YAML string and not a language-native hashmap. Optional `message` is the same as LIB-7: subject outside a transaction, ignored inside one, empty → `invalid` before any file is written. The proto Schema has no layout, no Record path, no `fields`, and no `version`. `create_collection` always writes `version: 1` on the collection file (SCH-13) as `CollectionInfo`; the caller does not set it. A leftover `version` or `declaration` key on the proto JSON `Schema` is `invalid` (unknown key). A message that fails `api.collection.v1` is `invalid` before the collection file is written. Then SCH-2, SCH-9, SCH-14 (same rules as load). A leftover `fields` or `layout` key is `invalid`. Needs the write lock. Writes `{name}/.collection.yaml`, or replaces an existing `.collection.yaml` / `.collection.yml` / `.collection.json` in that directory. `name` is the collection name and the on-disk directory (MOD-8). `schema.isolated` → Record files under `{vault}/.isolated/{name}/`; creates the nested git if needed; then `collection(name)` is the handle for those Records. Over an existing declaration the kind must stay the same and `isolated` must stay the same unless the collection holds no Record files; otherwise `invalid` and the declaration file is unchanged (SCH-13, SCH-15). After a successful write, `info` and `collection` on this handle see the new Schema (no reopen). `Collection.schema()` returns that `api.collection.v1.Schema`. Returns the live `Collection` handle. Autocommit rules are the same as LIB-7 (GIT-2). Isolated Record paths commit in the nested git; the collection file commits in the main repository. A declaration committed while `reindex` builds is applied after publish: the background indexer re-indexes that collection in full (IDX-9). **Agent.** *Check:* `create_collection` then `add` on that collection without reopen; a leftover `layout` key, a `fields` key, a leftover `version` or `declaration` key on the proto JSON, or an extra Schema key → `invalid` and no file. *Check:* the written collection file has `version: 1`. *Check:* `isolated: true` writes the collection file and nested git; `add` then `get` round-trip under `{vault}/.isolated/{name}/`. *Check:* `create_collection` while `reindex` builds succeeds (`reindex` takes no `write.lock`, LIB-16); after the build publishes, the collection is in the Index.

## 3. Git and maintenance

**LIB-12. `commit(message)`.** GIT-2. Ends the transaction on this handle and releases the write lock before return (including after `auto_sync` push), so a second handle can write immediately. It wakes the background indexer; the Index follows the commit (IDX-9). A transaction is the only supported batch. `invalid` if none is open on this handle, or if the message is empty, or if there is nothing to commit (no recorded path, or none that can be staged; recorded writes that leave the tree as at `HEAD` commit nothing and succeed). `transaction` (LIB-30) is the batch form that takes nothing to commit as success. `locked` if another thread on this handle opened the transaction. Creates one git commit per repository that has recorded paths (main and/or `{vault}/.isolated/`). Nested is committed first; if the main commit then fails, nested `HEAD` is reset to the commit it had before that nested commit (GIT-2). If `auto_sync` is on, then `push` of the main tree only (GIT-10, GIT-12, ISO-6). The CLI does not encode this name.

**LIB-22. `begin()`.** GIT-2. Enter a transaction on this handle. Takes the write lock and holds it until `commit`, `discard`, or drop. Writes inside the transaction do not touch the lexical or vector Index, and `find` / `search` do not see them. Discards leftover Scheda writes first. `invalid` if a transaction is already open on this handle. A mutating call, `commit`, or `discard` from another thread while the transaction is open is `locked` (retryable) and does not join it. The flag is in memory on this handle; `open` does not resume another process's transaction. Dropping the handle ends it without a git commit and releases the lock. The CLI does not encode this name.

**LIB-23. `discard()`.** GIT-2. Restore Scheda-recorded paths to HEAD, end the transaction if any on this handle, reload collection declarations, and drop the journal `id` map lines the restore removed. The Index is not rebuilt: it only ever held committed state. Needs the write lock and releases it before return. Allowed without an open transaction (crash leftovers). `locked` if another thread on this handle holds the write lock. The CLI does not encode this name.

**LIB-30. `transaction(message, f)`.** GIT-2. On the Vault: `begin`, the caller's `f` with the handle, then one git commit per repository the writes changed, `message` as the subject, all on the calling thread. Every write `f` makes through the handle, or a collection handle from it, joins the transaction. When `f` succeeds and its writes leave both repositories as at `HEAD` (nothing written, or only bytes `HEAD` already holds), no commit is made and `f`'s value is returned: a batch replayed after a crash succeeds. The decision comes from the recorded writes and the staged tree, not from an error message. `f` returns the caller's own error type; Scheda's failures reach it through the binding's conversion (in Rust, `E: From<scheda::Error>`): an empty `message` (before `begin`), `begin`, the commit, `locked`. An error from `f` or a failed commit discards the writes, then returns that error. A panic (exception) in `f` discards the writes, then propagates; the binding does not turn it into a code. While the same handle holds a transaction on another thread, the result is `locked` at once and `f` does not run. `commit` on its own stays strict (LIB-12). *Check:* `f` that writes nothing → its value, `git log` unchanged; identical-bytes `replace` → no commit in either repository; the caller's own error comes back as that variant with the writes discarded; `locked` arrives through the conversion; a panic discards the writes and propagates (`19` F4).

**LIB-13. `open(path)`.** GIT-9. One public call. Path exists as a Vault → open. A set `remote_repo` must match the fetch URL of `origin` (`invalid` if there is no `origin` or the URL differs); `origin` is not added or rewritten. Unset `remote_repo` attaches and does not change `origin`. Path missing and `remote_repo` set → `git clone`. Path missing → `git init`, no Remote. A git working tree without the marker `.scheda.yaml` (GIT-14) gets the marker in one commit, then opens. Path exists but is not a git working tree → `invalid`. `OpenOptions.existing_only` (unset means off) opens only a git working tree that already holds the marker: a missing path is `not_found`, a folder without the marker or that is not a git working tree is `not_a_vault`, it never runs `git init` or clones, and a refused folder is left untouched (GIT-9). A marker that cannot be read, or whose `version` is not 1, is `invalid` in both modes (GIT-14). A set `remote_repo` must be an absolute URI (RFC 3986: `https://…`, `ssh://…`, `file:///…`) or an scp-style `git@host:path`; an empty string, a filesystem path, or a hybrid `ssh://git@host:path` is `invalid`. `OpenOptions.author` (`api.v1.Author`) is the git author and committer for every commit on this handle (main tree and `{vault}/.isolated/`): required `name` and `email` when set; a name git cannot carry (`<`, `>`, a newline) or an address that is not an HTML email is `invalid` here (GIT-2). Unset: local git config, then `Scheda <scheda@invalid>`. `OpenOptions.writer` is the machine-local identity of this clone (journal segment names, `Vault.writer()`). Unset → generated on first `open` into `{vault}/.scheda/writer`. A set value is lowercase alphanumeric plus `-`, 1–32 bytes, and must not start with eight hex digits (`invalid` otherwise). An optional Projector is accepted the same way as an embedder: caller code at `open`, not an `api/v1` field (LIB-4). **Later:** `{vault}/.isolated/` is created by Scheda, never cloned (ISO-6). `OpenOptions.encryption` is the secret this handle uses for collections whose declaration marks `encrypted` (SCH-16, ISO-5, ISO-7). Isolated Record I/O does not require it unless that collection is also `encrypted`. `open` of the Vault does not require `encryption`.

**LIB-14. `pull` / `push` / `sync`.** GIT-11–12. Always `origin`; there is no remote-name argument. These never publish `{vault}/.isolated/` (ISO-6). Reaching a nested Remote is `push_isolated` / `pull_isolated` / `sync_isolated`: same fast-forward rules, same `origin` name, on the nested work tree only. Missing nested work tree or no Remote there → `invalid`. A `pull` or `sync` that moved `HEAD` wakes the background indexer, which applies what moved (IDX-9); none of these calls rebuilds the Index. The CLI encodes both sets.

**LIB-15. `check`.** Validates collection declarations (`05`), encodings (STO-2: UTF-8), journal envelopes (STO-3, MOD-16), `id` uniqueness, conflict markers (GIT-4), leftover `.schema.yaml` (SCH-1), isolation gitignore, and Index modes. It does not parse Record contents as YAML, Markdown, or any consumer format, and it does not type-check bytes against a field Schema. Isolated Record files are scanned when `{vault}/.isolated/` exists. Parent git must not track `.isolated/` (ISO-2). A journal `id` map line whose path is outside that collection is `index_corrupt` (the Index is not opened as a filesystem path). On Unix, `{vault}/.scheda/` must be owner-only — `0700` directories, `0600` files — and a wider mode is reported with that path (IDX-4); the Index holds sealed values now, so the mode is part of the perimeter and not housekeeping. **Later:** an encrypted collection is validated like any other when the handle carries the secret — armor form first (ISO-8), then decrypt, then the same encoding and envelope rules (not a field Schema). Without the secret `check` fails with `crypto`, and in a build without `encrypt` with `unsupported_encryption`. It must never return success over files it did not open: that would report health it never verified. The two codes say "not verified", not "broken", and a caller tells them from `invalid` or `conflict_markers` by the code, which is the whole reason those codes are distinct. A symlink inside a collection (a Record file, a journal segment, a subdirectory, or the collection directory itself, `.isolated/` included) is `invalid` and names its path; Record reads and writes never follow one (a link could lead outside the Vault), while `documents` / `ids` / `lines` skip a symlinked file. Does not write Records. Reports each problem with a code and path.

The shape of that answer is limited by the method, and the limit is stated rather than wished away. `check` returns success or one failure, so it cannot say "these collections are healthy and that one was not read". Any failure hides whatever the walk had not yet reached — true for every code, not only these two. A per-collection report needs a return type this method does not have; until it does, a caller who wants the plain collections verified while the secret is absent has to open a handle whose Vault has none. *Check (**later**):* the same fixture fails with `crypto` without the secret and succeeds with it; in a thin build it fails with `unsupported_encryption`; a corrupted armor file is a failure with a path, not a silent pass.

`check` does not judge Index freshness: the Index lags `HEAD` by design (IDX-9), and `Index.Status` (LIB-27) reports the state it reached. `check` takes `index.lock` without waiting while it reads the Index modes; while a round holds it, the Tantivy files that round is making (and narrows when it ends) are not looked at, so they are not reported as a wide mode. *Check (**find**):* `add`, then `check` passes.

**LIB-16. `Index.Reindex`.** IDX-1, IDX-9. On the Index object of a Vault (`Vault.Index`), with `find`. It asks this Vault's indexer for a rebuild and returns at once. The rebuild is an indexer round under `{vault}/.scheda/index.lock` (`06` IDX-9): it removes `commit` first, then every other file of the Index, indexes the git objects of `HEAD` of the Vault and of `{vault}/.isolated/` from nothing with this Vault's Projector and embedder — never the work tree, so an uncommitted edit is not indexed — and writes `commit` last. Meanwhile queries and searches are `INDEX_REBUILDING` (retryable), and writes, pulls, and syncs in every handle go on: the rebuild takes no write lock. Its progress and result are in `IndexState.rebuild`: the stage (`RUNNING`, `DONE`, `FAILED`), Documents read, Documents skipped (not read or refused by the Projector), journal segments read. A rebuild that fails is tried again from nothing after a pause. Every text is embedded again, since the stored vectors go with the rest of the Index. Because the rebuild uses this Vault's ports, it is how the Index moves to a new projection or a new embedder model, and how an `INDEX_BROKEN` Index is repaired. Encrypted collections are skipped (ISO-4); isolated collections are indexed. A Vault that lacks a port the Index needs → `FAILED_PRECONDITION` naming it; a rebuild already asked for or running in this Vault → `ABORTED`. *Check:* `Reindex` returns before the rebuild ends, a second one meanwhile is `ABORTED`, and the journal maps match afterwards (`tests/index.rs`: `reindex_returns_before_the_rebuild_a_second_is_aborted_and_the_maps_match`). *Check:* an embedder of another model sets `model_mismatch` and indexes nothing; a `Reindex` from it makes the vectors again with its model (`vector::tests::an_embedder_of_another_model_indexes_nothing_and_a_reindex_from_it_remakes_the_vectors`). *Check:* a Vault without a needed port gets `FAILED_PRECONDITION` (`vector::tests::a_handle_without_a_projector_or_a_needed_embedder_never_takes_a_round`).

**LIB-17. `history(id, offset, count)`.** GIT-3. On the collection handle. Same identity path as `get` (IDX-10): validate the `id` (LIB-7), then git history of that file. Does not ask the Index which ids exist. **Core** for `document` / `singleton`. For `journal`, IDX-5 map then git history of the **segment file** (the whole file in `Entry.raw`); line-level blame is **later**. The caller passes Record `id`, not a file path. An `id` that never had a commit and has no file → `not_found`. After `remove`, the file is gone and `history` still returns the commits that stored it. Paged, newest first: `offset` skips that many commits, `count` is the page size (`invalid` if `count` is 0). Returns `api/v1` `History` with `repeated Entry`: commit hash, `google.protobuf.Timestamp` `time` (UTC; git stores whole seconds since epoch), author, message, and file bytes (`raw`). Isolated collections use the nested git. Past the end of history → empty `entries`.

On an **encrypted** collection the handle secret is required and `raw` is the decrypted plaintext of that revision — the bytes a `get` of that revision would have produced, not the armor git holds. Demanding the secret and then returning ciphertext would be the worse contract: the caller has proved it holds the key, and the library is the only component that knows the collection is encrypted. Without the secret, `crypto`; in a build without `encrypt`, `unsupported_encryption`. An entry whose `raw` is empty is returned as it is: a commit that deleted the file has no bytes, and there is nothing there to decrypt. *Check:* two commits editing one `document`; snapshots match `git show` of the file Scheda stores. *Check (**later**):* on an encrypted collection, both revisions come back as plaintext with the older one carrying the older value, and no entry begins with the armor header. *Check:* `count` `0` → `invalid`; `offset` beyond the last commit → empty `entries`; unknown `id` → `not_found`. *Check:* `remove` then `history` still matches `git show` of those commits. *Check:* delete `.scheda/`; `history` of a fixture `document` still matches `git show`.

**LIB-18 (retired).** RFC 8785 canonical JSON of journal lines. Journal `add` writes the envelope `{id}: {payload}\n` (MOD-16). `Record.raw` / `lines` `raw` is the payload. There is no library canonicalization of consumer fields.

**LIB-19. `lines()`.** On the collection handle. `journal` only. Walks segment files in declaration sequence (SCH-14): closed segments by name, each file from first line to last, then the open segment. Rotation does not reorder earlier lines. Same append order as QRY-7, without opening the Index (not QRY-2, not IDX-5). Does not take a `Filter`. Each yielded Record is `api.v1.Record` as LIB-8: `raw` is the payload after the first `:` that is followed by a space (the envelope delimiter), not the envelope and not including the trailing newline. A line with no `:` followed by a space, an empty envelope `id`, or a final line without `\n` is `invalid` and stops the walk (STO-3, MOD-16). `document` / `singleton` → `unsupported`. Isolated `journal` is allowed (ISO-2). A missing or corrupt `{vault}/.scheda/` does not stop the walk. Streaming: one Record at a time; the binding must not materialise the whole collection. Empty collection → empty walk. In Rust the return is `JournalLines` (`Iterator` of `Result<Record, Error>`). *Check:* insert A, B; rotate; insert C; `lines` → A, B, C in that order, and each `raw` is the payload that `add` received. *Check:* delete `.scheda/`; `lines` still yields those Records. *Check:* `document` → `unsupported`. *Check:* 10³ lines across rotated segments: every `id` once, in append order; memory does not grow with the line count.

**LIB-25. `documents()`.** On the collection handle. `document` and `singleton` only; `journal` → `unsupported` (ordered journal read is LIB-19). Walks regular files under the collection (isolated: `{vault}/.isolated/{name}/`), in `id` order: the byte order of the full `id`, where `/` in a `document` `id` is a directory. The library does not require a `.md` suffix and does not skip `.md` files. A `singleton` yields its one Record (the declared `id`), or nothing before the first write. Does not open the Index (not QRY-2, not IDX-10), so the walk is the same in a build without `find` and is unaffected by a stale Index; it is the answer of last resort when the Index is gone. Does not take a `Filter`: selecting by Index column is LIB-10. Each yielded Record is what `get(id)` returns for that `id`, `raw` included. A file that exists is yielded even when a later `Projector` would omit it; the walk continues. This is deliberately unlike LIB-19, which stops. A journal is packed lines, so a malformed envelope hides where the next line begins and there is nothing safe to do but stop; documents are separate files, so a bad one says nothing about the next, and stopping would hide every Record after it in `id` order. Reporting bad files (non-UTF-8, conflict markers) is `check` (LIB-15), not this walk. Names that are not Record files are skipped and are not an error: a name starting with `.` (so `.collection.yaml` and `.scheda/` never appear; a leftover `.schema.yaml` is a dotfile here and `invalid` on `check`), and anything that is not a regular file. Mixed extensions in one collection are Records (`a.yaml` and `b.md` both yield). Directories whose names are slugs are descended; other subdirectories are skipped. Isolated collections are allowed (ISO-2). **Later:** an encrypted collection is allowed too, and each file is decrypted as it is yielded, so the walk needs the handle secret and fails with `crypto` without it (ISO-5); a file that will not decrypt is an `Err`. Since `find` is `unsupported` there (ISO-4), this walk plus `get` are the only ways in. `ids()` reads file names only and needs no secret. Streaming: one Record at a time; the binding must not materialise the whole collection. Because the order is stable, the file names are held for the length of the walk, so memory grows with the **number** of Records, not with their contents. A missing collection directory and an empty one both give an empty walk. In Rust the return is `CollectionDocuments` (`Iterator` of `Result<Record, Error>`). *Check:* add `charlie.md`, `alpha.yaml`, `bravo`; `documents` yields `alpha.yaml`, `bravo`, `charlie.md`. *Check:* `.collection.yaml` is not yielded and does not fail the walk. *Check:* `journal` → `unsupported`. *Check:* delete `.scheda/`; `documents` still yields every Record. *Check:* `singleton` before the first write → empty walk; after → one Record. *Check:* 10³ documents: every `id` once, in `id` order. *Check:* `add("work/meeting.toml")`; `documents` / `ids` include `work/meeting.toml` and skip a non-slug subdirectory.

**LIB-26. `ids()`.** On the collection handle. Same kinds, same order, and the same skipping rules as LIB-25, but no Record file is opened: the answer is the relative path under the collection, including any extension. This is how a caller asks which Records exist without paying for their contents; contents then come from `get`, or from LIB-25 when all of them are wanted. Independent of the Index in the same way, so the list is correct in a build without `find` and with a stale Index. `journal` → `unsupported`: a journal `id` lives in the envelope, so enumerating those ids is LIB-19, or IDX-5 when `find` is on. Returns the ids in one list (`Vec<String>` in Rust): memory is the ids, never Record contents. `id` is the path (MOD-5); there is no identity key inside the file. After a rename of the file, `ids` reports the new path and `get` of the old `id` is `not_found`. *Check:* a three-document fixture gives its three ids in `id` order. *Check:* `.collection.yaml` is not an id. *Check:* empty and missing collection → empty list. *Check:* `journal` → `unsupported`. *Check:* `singleton` before the first write → empty; after → one id equal to the declared `id`. *Check (**find**):* with a deliberately stale Index the list still matches the files on disk.

**LIB-27. `Index.Status` / `Index.Watch`.** On the Index object of a Vault, with `find`; a build without `find` has no Index object (`UNIMPLEMENTED`). `Status` returns `IndexState` now. `Watch` streams it: the state at once, then one item per change (an indexer round, a failure, a rebuild starting, moving on, ending); it does not end by itself, and the caller drops it when it has what it waited for. The fields are those of `06` IDX-9: `version` (the opaque token of the state the whole Index reached), `pending`, `role`, `model_mismatch`, `rebuild`, `last_error`. Neither call runs git or reads the Index. There is no call that waits for a given write: `version` is opaque, and no call gives the token of `HEAD` to compare it with. The async form of `Watch` waits without holding a thread of the blocking pool. *Check:* `Watch` gives the state at once and then one item per round; a watcher that falls far behind skips to the oldest item kept (`indexer::tests::the_watch_gives_the_state_at_once_and_then_one_item_per_round`, `indexer::tests::a_watcher_that_falls_far_behind_skips_to_the_oldest_item_kept`; `tests/index.rs`: `the_status_gives_the_state_at_once_and_then_the_version_of_each_write`).

**LIB-28. `close()`.** On the Vault. Stops the indexer and joins its thread: a round stops at its next check (every 256 Documents, and around the embedding), and an `Embed` call in progress runs to the end of its stream first, so the caller bounds the wait with its embedder's own timeout. Then it drops the handle, returning an error where `Drop` cannot. Dropping the last handle does the same. `commit` stays at the last finished round; what a stopped round wrote stays ahead of it, and the next round starts from `commit` again. `Collection` handles made from the Vault keep reading and writing, but nothing indexes their commits until a handle is opened again. Scheda installs no signal handler: a program that wants a clean exit on `SIGINT` / `SIGTERM` catches the signal and calls `close`; being killed instead loses nothing. *Check:* after `close` (or the last drop) the indexer thread is gone (`tests/index.rs`: `close_and_drop_end_the_indexer_thread`).

**LIB-29. Async layer.** Optional, over the sync calls of LIB-6; a binding that offers one keeps the operation names. Each call that does I/O or calls caller code (embedder, Projector, reranker) runs the sync call off the async scheduler's threads and returns the same outcome and code. A transaction does not span awaits: the handle's write lock (STO-4) belongs to the thread that took it, and two awaits may resume on two threads. So the async layer has no `begin` / `commit` / `discard`; `transaction(message, f)` runs the sync `transaction` (LIB-30) in one blocking unit, with the same rules: nothing to commit is success, `f` keeps the caller's error type, Scheda's failures arrive through the conversion. A panic of `f` is `io_other` there (after the sync form discarded), and the unit is `locked` at once while the same handle holds a transaction on another thread. `Index.Watch` waits without holding a blocking thread. A blocking unit cancelled by a runtime that shuts down is `io_interrupted`. In Rust this is the opt-in `tokio` feature: `scheda::nonblocking` with `AsyncVault` and `AsyncCollection` (`as_vault()` / `as_collection()` reach the sync handle; `lines` / `documents` return the whole list). *Check:* the async surface passes on a multi-threaded and a single-threaded runtime. *Check:* 64 concurrent `transaction`s on one handle each end committed in one commit or `locked`, never split. *Check:* on a blocking pool of one thread, a pending `wait_indexed` does not stop another call.

## 4. What this API refuses

- Partial patch of Record bytes.
- A Record file path from the caller. `get` / `add` / `history` take a validated `id` and the library opens, creates, or gits the file. `find` / `replace` / `remove` / `search` take `id`s from the Index when `find` is on (IDX-10). `lines` walks journal segment files the library names, and `documents` / `ids` walk the Record files under the collection; the caller does not pass a path, a directory, or a glob.
- Delete of a journal line (`remove` on `journal` is `unsupported`). `remove` of a `document` or `singleton` is LIB-24.
- Cross-Vault query unless the caller passes two handles into a combined helper (**later**).
- Shipping a ranking model in the library (QRY-5). An optional reranker **callback** on `search` is allowed (`13`). An optional Projector **callback** on `open` is allowed (LIB-4); it is not Vault data.

---

## 5. First implementation (Rust)

The crate `scheda` is the first binding. It must:

- map every LIB operation above;
- use `Result` with a typed error that includes LIB-5 codes (no `panic!` / `unwrap` / `expect` / `assert!` on the library path; tests may assert);
- carry `[lints] workspace = true` as in this repository.

That panic policy is **Rust**, not a requirement on other languages (Python, Java, Go, TypeScript, and others use their usual error conventions, still with LIB-5 codes).

## 6. What this document does not decide

How a binding wraps generated types (builders, `Result`, exceptions) as long
as proto field names and LIB-2 operation names hold. The Rust type of the
Projector option on `open` is the binding's affair.

Isolated `encryption` / age armor — `09` (**later**).
`Projector.schema` returns `api.v1.IndexSchema` (`index.proto`). The
Projector trait is still a caller callback, not proto. Filter column names —
`06` / `13`.
