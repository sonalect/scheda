# 06. Index and search

Document 6 of the Scheda package. Version 0.60, 20 October 2026.

Normative rules for the derived Index and the reads that need it. **Queries and searches (how they must work) are `13`.** Terms are in `02`. Collection declaration (write mode, perimeter, Index exclusion) is `05`. Index columns come from a `Projector` the caller gives the Vault, not from the declaration. The per-method contract is in the rpc comments of `api/scheda/v1/*.proto` (`07`). The Index is built on Lance (`21`). Codes: `IDX`, `QRY`. Phase **core** or **search** as marked.

An assertion without a check is not a requirement. The Index is never source of truth (STO-1, GIT-13).

---

## 1. The Index is disposable

**IDX-1. Rebuild from commits.** The Index is `{vault}/.scheda/index/` (gitignored; GIT-13). It is not part of a Vault commit or backup. It holds committed state only: it is built from the git objects of `HEAD` of the Vault and of `{vault}/.isolated/`, never from the work tree, so an uncommitted edit or a write still in progress is not indexed. Deleting it loses nothing: the next round of the indexer builds it again from `HEAD` (IDX-9). `Collection.Get`, `Collection.History`, and the lines of a journal never need it. *Check (**core**):* delete `.scheda/`; `Collection.Get` and `Collection.History` of a fixture Document still return that file, and every line of a fixture journal is still found; once the indexer rebuilt the Index, a fixture query matches the committed files (`tests/index.rs`: `an_index_of_another_format_or_without_a_commit_is_rebuilt`, `a_line_is_found_before_the_indexer_ran_after_it_and_without_its_map`).

**IDX-2. Layout and one state.** The Index is these files:

```text
{vault}/.scheda/index.lock                    flock, held for one indexer round
{vault}/.scheda/index/format                  the layout number (now 3) and a newline
{vault}/.scheda/index/current                 the name of the live generation, g-…
{vault}/.scheda/index/g-…/commit              the state, the ports, the tables and their versions; written last
{vault}/.scheda/index/g-…/t{n}.lance          the rows of one collection (a Lance table)
{vault}/.scheda/index/g-…/t{n}.files.lance    the files those rows came from (path, blob)
{vault}/.scheda/index/commit                  the state the journal id maps reflect
{vault}/.scheda/index/journal/{name}/ids      the id map of a journal (IDX-5)
```

A **generation** is one build of the tables. The live one is named by `current`; a rebuild makes another beside it and switches (IDX-9). Per indexed collection a generation holds a rows table and a files table. A rows table has one row per Document, or per journal line: `id`, `file` (the Vault-relative path of the Document or of the journal segment), `order` (the place in a listing: the `id`, or for a journal line the segment's place in append order and the line's), the columns the Projector declares for the collection, typed, and for each `vector` column `_vector_{name}` (the embedding) and `_digest_{name}` (the git blob id of the text that was embedded). A caller's column name never starts with `_`. A files table has one row per file the rows came from, with its git blob id.

A state is one line: `main {oid}`, followed by `isolated {oid}` when the nested repository has a commit (`-` for no commit); `IndexState.version` reports it as an opaque token. The `commit` of a generation holds the state, the ports the generation was built with (the projection, the embedder's model and vector length, the columns of each collection), and for each collection the Lance versions of its two tables. It is written whole and last, so it is the one state every table reflects: a reader opens exactly the versions it names, and one call sees one state across all collections. A table version ahead of `commit` (left by a round that died) is believed by no reader and is rolled back to the committed version before the next round writes. Every file Scheda writes under `index/` is written whole (temporary file, `fsync`, rename) and owner-only (IDX-4); Lance writes its own files.

An Index whose `format` is not this build's number, or that has no `current` and `commit` that parse, is not built: queries and searches are `INDEX_REBUILDING` (retryable), and the indexer builds it (IDX-9). The files of the `0.22` Index (Tantivy and USearch, `format` 2) are never read; the first round removes them. A file that does not read is `INDEX_BROKEN` until `Index.Reindex`: nothing repairs a damaged Index by itself. Queries and searches fail with that code, never answer from another Vault's ids. *Check (**core**):* another `format` or a `commit` that does not parse reads as not built (`index::tests::another_format_or_a_broken_commit_reads_as_not_built`); `commit` is written last and a reset removes it first (`index::tests::the_commit_is_written_whole_and_reset_removes_it_first_and_every_other_file`); a round cut short is rolled back to the committed versions (`store::tests::a_round_cut_short_is_rolled_back_to_the_versions_the_commit_names`); a killed process leaves an Index that opens, counts, and searches (`tests/search.rs`: `a_process_killed_while_it_indexes_leaves_an_index_that_opens_counts_and_searches`); a map that is not one is `INDEX_BROKEN` (`idmap::tests::bytes_that_are_not_a_map_are_index_broken`).

**IDX-3. A refused projection stays out of the Index.** A Document whose `Projector.Project` fails with `REFUSED`, or gives a value of another kind than its column's, is left out of the Index, and the round goes on; a Document for which it gives no values is indexed by identity only. `UNAVAILABLE` is retryable: it fails the round, which is tried again (IDX-9). `Collection.Get` still returns the bytes of a Document that is left out. For a `journal` the id map is **not** dropped: the envelope still has `id`, so `Collection.Get` after the Index was wiped can find the line. Encrypted collections enter no Index (IDX-4). A write does not call the Projector to accept or reject a Document. *Check (**search**):* a Document without values is indexed by identity and the rows follow their files (`tables::tests::documents_and_lines_become_rows_that_follow_their_files`); a projector failure keeps its code (`ports::tests::a_projector_failure_keeps_its_code`). *Check:* a journal line is found by `Collection.Get` after `.scheda/` is wiped (`tests/index.rs`: `a_line_is_found_before_the_indexer_ran_after_it_and_without_its_map`).

**IDX-4. One Index, owner-only; encrypted stays out.** There is one Index per Vault, `{vault}/.scheda/`, and it holds every collection the build can read — isolated collections included (ISO-4). On Unix that directory is owner-only: `0700` on directories, `0600` on files, applied when it is created and after every round, including the files Lance creates that Scheda never opens. A wider mode is a `Vault.Check` problem naming the path. There is no nested Index (ISO-10 retired).

An **encrypted** collection (SCH-16) enters no Index at all: the Index is plaintext on disk, so an entry for one would publish what the encryption was for. `Index.Reindex` and the background indexer skip those collections, and a query or a search naming one is `UNIMPLEMENTED` rather than empty.

*Check:* no test yet reads the Index files for the plaintext of an encrypted collection, or queries a collection that is encrypted. *Check:* owner-only modes are applied and a wider one is reported (`tests/search.rs`: `every_file_of_the_index_is_owner_only_after_a_round`; `fs::tests::owner_only_modes_are_applied_and_checked`; `check::tests::a_tracked_isolated_path_and_a_wide_mode_are_reported`).

**IDX-5. Journal `id` lookup.** Once the Index exists, `Collection.Get` on a journal must not scan every segment. The Index maps each line `id` to its segment: `{vault}/.scheda/index/journal/{name}/ids`, a text file: the line `scheda-ids 1`, the state the map is true at (IDX-2), the number of segments, the segments as JSON strings (Vault-relative), then `{id}\t{segment number}` per line, sorted by `id`. The map belongs to the Index format (IDX-2) and is built from the envelopes, not from `Projector.Project`. Only the indexer writes it, whole, in its round (IDX-9); a write never touches it. Because a map records the state it is true at, it is right on its own: a line it does not list is looked for only in the segments that differ between that state and `HEAD` (a tree comparison, no process), so a line just written is found before the indexer reaches it. A journal with no map, a map whose state is gone from its repository, and a map that names a segment without the line (a segment changed by hand) are scanned. The maps do not depend on the feature `index` or on any port: every build indexes them. *Check (**core**):* an absent `id` is looked for only in the segments changed since the map (`idmap::tests::an_absent_id_is_looked_for_only_in_the_segments_changed_since_the_map`); a line is found before the indexer ran after it and without its map (`tests/index.rs`: `a_line_is_found_before_the_indexer_ran_after_it_and_without_its_map`); a build without the feature keeps the maps (`tests/index.rs`: `the_index_object_needs_the_feature_and_the_maps_are_kept_either_way`).

**IDX-10. Caller `id` and the stored tree: `Collection.Get`, the writes, `Collection.History`.** Each validates the `id` against the rules of its collection, then uses that identity against the tree (MOD-8). `Get` and `History`: `standard` `{name}/{id}` (`/` in `id` is a directory; the library does not append `.md`); `singleton` `{name}/{declared id}`; `journal` the IDX-5 map to the segment (the segment is not named `{id}`). `Create` makes the file or the envelope line; the Index follows after the commit (IDX-9). `Update` and `Delete` also take the caller `id` against the tree: they find the Document, never the Index, because the Index lags the last commit. A Document that is not there is `NOT_FOUND` (do not invent `{id}.md` from the argument). `Delete` removes a `standard` / `singleton` Document (a `journal` is `UNIMPLEMENTED`); after it, `History` still gives the versions that stored it. `Collection.GetMany` takes no Index either: a listing walks the collection in its order, a journal in append order across segments. `Query` and `Search` take `id`s **from the Index**, then read those Documents from git at the state the Index reflects. An `id` the Index returns has already been accepted as a Document identity. *Check (**core**):* a query on `id =` an unindexed orphan file is empty; `Get` and `History` of that id still use the file (`tests/documents.rs`: `a_persons_uncommitted_edit_is_seen_by_no_get_document_and_a_commit_by_hand_is`). *Check:* `Update` and `Delete` of a Document the Index has not reached succeed (`tests/documents.rs`: `a_document_committed_by_a_person_is_read_replaced_and_deleted`); `History` still answers after `Delete` (`tests/reads.rs`: `history_lists_versions_newest_first_with_revision_author_note_and_bytes`).

## 2. Point read and query

**QRY-1. `Collection.Get`.** Check the `id` against the rules of the collection, then read the Document for that `id` from `HEAD` (IDX-10). Returns a `Document`: `collection`, `id`, `raw`, `revision`. A Document that is not there is `NOT_FOUND`, never a blank Document. Encrypted: the returned bytes are decrypted. *Check (**core**):* a stored Document reads back with the bytes written; an unknown one is `NOT_FOUND` (`tests/documents.rs`: `get_document_names_what_is_missing`). *Check:* an `id` that breaks the rules of its collection is `INVALID_ARGUMENT` before any file is opened (`tests/reads.rs`: `an_id_that_breaks_the_rules_of_the_collection_is_invalid_argument`).

**QRY-2. `Collection.Query` and `Vault.QueryDocuments`.** Run the `Filter` on the Index, then read the Documents of the `(collection, id)`s it selects from git (IDX-10). A query selects: the exact set the Filter matches, in a stable order (QRY-7), without scores (`13` §3). `Collection.Query` looks at its own collection. `Vault.QueryDocuments` takes a set of collection names (`CollectionNames`); an empty set is every collection that is neither isolated nor encrypted — broad scans must not surface sealed values by default (ISO-3) — while a **named** isolated collection is an ordinary query, and a set mixing isolated with plain names is one stream. The Filter is a typed tree the caller fills (`all_of`, `any_of`, `none_of`, `term`, `terms`, `range`, `exists`, `prefix`) over `id` and the columns the Projector declares; the library checks it and runs it in the Index itself, and no caller writes the query language of the engine (`13` §3). The request is a `DocumentQuery` (`VaultQuery` for the Vault): optional `filter` (unset: every Document), `order_by`, `offset`, `limit` (unset: every match), `start_after`, `include_raw` (unset or false omits `Document.raw`; `Collection.Get` always returns it), and `not_before` (QRY-8). The reply is a stream of `QueryItem`: first a `QuerySummary` with `total`, the number of Documents the filter matches in scope whatever `offset`, `limit`, and `start_after` say, then the Documents of the page. The total and the page are read from one snapshot of the Index, so they always agree; `Collection.Count` and `Vault.CountDocuments` give the same number without the Documents. There is no path query: the caller never supplies a Document path. Without a Projector only `id` can be named; any other column is `INVALID_ARGUMENT`. A collection the Index has not reached yet is empty. *Check (**core**):* each kind of leaf selects the exact set, and `none_of` counts a Document without a value as a match (`tests/query.rs`: `each_kind_of_leaf_selects_the_exact_set_and_none_of_counts_a_missing_value_as_false`). *Check:* a column no collection declares, a value of another kind, and a filter deeper than `filter_max_depth` are `INVALID_ARGUMENT` (`tests/query.rs`: `a_column_no_collection_declares_a_value_of_another_kind_and_a_deep_filter_are_invalid`; `filter::tests::a_column_no_collection_declares_and_a_value_of_another_kind_are_invalid`, `filter::tests::a_leaf_is_one_level_and_each_list_one_more`); a filter of depth 100 runs on a 2 MiB stack (`tests/query.rs`: `a_filter_of_depth_100_runs_on_a_two_megabyte_stack`). *Check:* a query of the Vault orders by its keys, then the collection, and pages across collections (`tests/query.rs`: `a_vault_query_orders_by_its_keys_then_the_collection_and_pages_across_collections`).

A query does not use vectors. That is a search. There is no magic `body` key unless the Projector names a column `body`. The text of the `fts` columns is for a search only.

**QRY-7. Query order.** The order of a query is its `order_by` keys (`id`, a journal's `order`, or a Projector column that is not a `text list`; a Document without a value comes last in both directions), then, in a query of the Vault, the collection name, then the default order of the collection: the byte order of the full `id` for a `standard` or `singleton` collection, append order for a `journal` (closed segments in declaration sequence (SCH-14), each file from first line to last, then the open segment; rotation does not reorder earlier lines). The order is total. Never score. `start_after` is a condition on that order, not a count of what comes before it: a page that begins where the last one ended is not shifted by a Document added meanwhile, and a deep page costs what the first costs. In the default order of a `standard` or `singleton` collection the `id` need not still be in the Index; in any other order the query finds that Document in the same snapshot to learn where it stood, and one no longer there is `FAILED_PRECONDITION` (start again). `offset` jumps to a page, after `start_after` when that is set; a Document added meanwhile shifts the pages after it. A search ranks by relevance and promises no order beyond that (`13` §6). *Check (**core**):* the order is stable and paging by `start_after` neither repeats nor skips (`tests/query.rs`: `the_order_is_stable_and_paging_with_start_after_neither_repeats_nor_skips`); a query of the Vault gives collections in name order after its keys (`tests/query.rs`: `a_vault_query_orders_by_its_keys_then_the_collection_and_pages_across_collections`).

**QRY-8. Freshness: `not_before`.** A write returns the state token of the Vault it made (`DocumentWriteResult.version`, `DocumentBatchResult.version`); `Vault.Info` gives the token of the stored state now; `IndexState.version` the token of the state the Index reflects. A query, a count, or a search may name a token in `not_before`: it then waits until the Index reflects a state that contains that token, so a caller finds its own write without polling. Past `OpenOptions.index_wait_timeout_ms` (default 60 s) the call is `DEADLINE_EXCEEDED` (retryable); `Vault.Close` ends the wait at once with `FAILED_PRECONDITION`; a token whose commit is no longer in the history of `HEAD` (a reset, a pull that rewrote it) does not wait; text that is not a token is `INVALID_ARGUMENT`. Without `not_before` a call answers at once from what the Index holds. A write never waits for the Index. *Check:* a query given the token of its write finds it, and a token of a reset commit does not wait (`tests/query.rs`: `a_query_waits_for_its_write_with_not_before_and_a_reset_commit_does_not_wait`); a wait past its deadline is `DEADLINE_EXCEEDED` (`tests/query.rs`: `a_wait_past_its_deadline_is_deadline_exceeded`); a search given the token of a write finds it (`tests/search.rs`: `a_search_given_the_token_of_a_write_finds_it`).

## 3. Lexical and vector (**search**)

The Index is a **retrieval** engine an agent can recall from, not a substring demo. Grep, SQL `LIKE`, and scanning Vault files at query time are not a search.

Columns other than identity come from `Projector.Columns(collection)`: name, kind (`text` / `integer` / `number` / `boolean` / `text list`), and marks (`scalar_index` / `fts` / `vector`). Same column name may differ in kind across collections. `vector` is allowed on a `text` column only (one vector per value), `fts` on a `text` or `text list` column, and a name matches `^[a-z][a-z0-9_]*$` and is not `id`, `order`, `file`, or `collection`; the contract's validation refuses the rest with `INVALID_ARGUMENT`. A collection with no columns, or a Vault without a Projector: identity only; a search has nothing to rank there (lexical empty, vector off).

**IDX-6. Lexical index.** Ranked full-text (BM25) over Projector columns marked `fts`, by Lance's inverted index with its default tokenizer (lower case, no stemming) and without positions: there is no phrase query. In-process; a separate search server is not required. Identifiers and rare tokens must surface. Each collection is its own table, so BM25 statistics are per collection. The contract is the ranking class, not a crate name, and is not SQL. *Check:* an exact token in an `fts` column ranks that Document inside the requested `k` among distractors that lack the token (`tests/search.rs`: `a_text_search_fuses_the_lexical_and_the_vector_leg`); a column without the `fts` mark is not searched (no test names this yet).

**IDX-7. Vector index.** In-process nearest neighbours by cosine distance over Projector columns marked `vector`, in the same tables as the rest. A table with 10 000 rows or more gets an IVF_PQ index per `vector` column; the candidates it gives are ranked again with the full vectors. Below that size, and for the rows no index covers yet (written since), the search is an exact scan, so a write is found as soon as the Index holds it. No external vector database. *Check:* a query that shares no tokens with the Document but is a synonym (fixture) still ranks that Document inside the requested `k` when an embedder is present (`tests/search.rs`: `a_text_search_fuses_the_lexical_and_the_vector_leg`); a search through the vector index finds the exact nearest neighbours (`tests/search.rs`: `a_search_through_the_vector_index_finds_the_exact_nearest`); the indices are made and the scans use them (`store::tests::the_indices_are_made_and_the_scans_use_them`).

**IDX-8. The ports: `Embedder`, `Reranker`, `Projector`.** Scheda ships no model and does not know what a Document holds. The caller gives the Vault its ports as references, at `Scheda.Open` or later (`Vault.SetEmbedder`, `SetReranker`, `SetProjector`, and a `Remove…` for each; `07`). `Embedder`: `Describe` (the model id and the length of its vectors, read once and recorded with the Index), `Embed` (a stream of texts, one vector per text), `EmbedQuery` (the vector of a search text). `Projector`: `Describe` (the `projection_id`, read once and recorded with the Index), `Columns`, `Project`. A port may change at any time; the indexer takes the new set into its next round (IDX-9). The library does not require the network to embed. No embedder: the vector leg is off, the Vault does not index a collection with a `vector` column (IDX-9), and queries, the lexical leg, and writes still work. An embedder that calls the network is the caller's; the network stays opt-in (ISO-1). A port fails with its own codes (`EmbedderErrorCode`, `RerankerErrorCode`, `ProjectorErrorCode`): `UNAVAILABLE` is retryable, `REFUSED` is not. *Check:* a Vault without an embedder queries and writes, and does not index until one is given (`tests/consumer.rs`: `a_vault_without_an_embedder_does_not_index_until_one_is_set`); a descriptor is read once per install (`ports::tests::describe_is_called_once_per_install_whatever_is_embedded_after`); the summary of a search says why the vector leg did not run (`tests/search.rs`: `the_summary_names_why_the_vector_leg_did_not_run`). *Check:* with no Projector, only `id` can be named and any other column is `INVALID_ARGUMENT` (`tests/query.rs`: `a_column_no_collection_declares_a_value_of_another_kind_and_a_deep_filter_are_invalid`).

**IDX-9. The indexer.** Writes (single writes, write streams, batches, `Pull`, `Sync`) never touch the Index, the journal `id` maps included. Every open Vault runs one indexer task, on the runtime that opened it (`22` D6), that keeps the Index at `HEAD`. It wakes at once when a write of this Vault moves `HEAD`, when a port is set, and on `Index.Reindex`; otherwise it looks at `HEAD` every `OpenOptions.index_poll_ms` (default 1 s; 10 ms to 1 h), which finds the commits of other processes, of `git`, and of pulls. A look reads the two `HEAD`s and the `format`, `current`, and `commit` files, and starts no process.

*A round.* (1) The Vault takes a round only when it may index (*who indexes*, below). (2) It takes `flock` on `{vault}/.scheda/index.lock` without waiting; when another indexer, of this process or another, holds it, the round is skipped and the next look tries again. (3) It reads `HEAD` of both repositories. (4) It brings the journal id maps to `HEAD`, then each table from its own state to `HEAD`: the difference between the trees of the two states, git objects only. When the commit a table stands on is gone from its repository (a pruned or rebuilt repository, an ordinary event for an isolated collection), the round compares the tree of `HEAD` with the table of files instead, and applies the same difference: no rebuild, and unchanged texts keep their vectors. (5) It writes `commit` last, lets the lock go, and publishes the new state to `Index.Status` and `Index.Watch`. When `HEAD` moved meanwhile, the next round starts at once. The indexer never takes the write lock, so writes go on during a round. The difference is between trees, not along history: a reset, a rebase, or a pull that rewrote history is applied like any other move. A collection whose declaration file changed, or that the Index has not reached, is indexed whole inside the round.

*The tables.* A changed Document is projected once (`Projector.Project`) and upserted by `id` with all its columns (Lance's `merge_insert`); a deleted one is deleted by a typed expression, never by text built from values. A journal segment that grew by appending (its old bytes are a prefix of the new ones) gives only its new lines; one changed otherwise is indexed again whole. A text of a `vector` column whose digest (the git blob id of the text) the table holds for that Document keeps its vector; the other texts of the round go to `Embedder.Embed` in one stream. A blank text (only whitespace) has no vector. After a round that wrote rows, the indexer, still under the lock, compacts small fragments only (target 16 384 rows per fragment, so a large fragment is never rewritten), keeps a B-tree index on each `scalar_index` column, an inverted index on each `fts` column, and an IVF_PQ index on each `vector` column from 10 000 rows, brings the indices over the new rows when more than 10 000 are unindexed or every 50 rounds, and prunes a table version an hour after the version after it was made, never sooner, so a reader that still holds one keeps its files. Then `commit` is written again with the new versions of the same state. These values are constants of the library, not options.

*Who indexes.* A Vault takes a round only when it has every port the Index needs: a Projector of the projection the Index was built with, and, when a collection has a `vector` column that its declaration does not exclude, an embedder of the model and vector length the Index was built with. A Vault without a Projector indexes identity only and is stale against an Index built by a Projector. A Vault with no embedder is not stale: it does not index, its `role` stays false, its `IndexState.last_error` is `FAILED_PRECONDITION` naming the port, and its queries and searches read the Index others keep, the searches without the vector leg (`VECTOR_LEG_NO_EMBEDDER`). When no open Vault on the path can index, the Index does not move: one never built stays `INDEX_REBUILDING`, and a built one answers from its last state. **Only `Index.Reindex` changes the projection, the columns, or the embedder model of the Index.** A Vault whose Projector is of another projection, whose columns differ for a collection, or whose embedder is of another model or vector length than the Index was built with finds the Index `INDEX_STALE`: it does not index, and its queries and searches fail with that code, until a `Reindex` of a Vault with those ports has switched the Index to them. Given the Index's ports again, it is not stale. No Vault starts a rebuild by itself, but for an Index that does not exist.

*A failed round.* A round that fails changes no `commit` and fails no write. `IndexState.last_error` carries the failure until a round succeeds; the round is tried again after a pause that starts at `index_poll_ms` and doubles up to eight times it, or at once when a write moves `HEAD`. A panic inside a round, which runs as a task of its own, reaches the indexer as `Panicked` and is reported the same way. A table written before the failure stays ahead of `commit`, believed by no reader, and the next round rolls it back to the committed version and starts from `commit` again. The vectors an embedder gave before it failed are kept in this Vault's memory, by text digest, until a round succeeds, so the next try sends only the texts that have none; the Projector's answers are kept the same way, by Document and the digest of its bytes, so the next try projects only the Documents it has not answered (another projection forgets them); a text the embedder refuses (`REFUSED`) leaves its Document without that vector, as a refused projection leaves one out of the Index. Because readers open the versions `commit` names, an embedder that does not answer holds back `commit`, the reported `version`, and what a query sees of the new Documents. The stop is honoured between portions of an embedding, so `Vault.Close` waits for the portion in progress, not for the whole embedding.

*A rebuild.* When the Index does not exist (never built, another `format`, the files of `0.22`) or `Index.Reindex` was asked, the round is a rebuild: under the lock it makes a new generation beside the live one, indexes the snapshot of `HEAD` from nothing with this Vault's ports, catches up once with the tree difference to the `HEAD` of the moment it is built, writes the new `commit`, and switches by writing `current` (one atomic write). **The live Index is frozen during every rebuild:** it keeps answering queries and searches, at its `version`, until the switch; the writes made meanwhile appear at the switch (those made while it caught up, in the next round), and a `not_before` past the live `version` waits for the switch. `INDEX_REBUILDING` is only for an Index never built. A rebuild with the embedder model and vector length of the live generation takes the vector the live generation holds for the same text of the same Document and embeds only the rest; one with another model embeds every text. A live generation whose vectors cannot be read (a broken Index) gives none, and its texts are embedded. The vectors embedded by a failed try stay in that Vault's memory. The old generation is removed an hour after the switch; a generation no `current` names, left by a build that died, goes at the next round. A rebuild that fails leaves the live Index and starts again from nothing on its next try: an `Index.Reindex` stands until a rebuild is done. `Index.Reindex` returns at once; while this Vault has one asked for and not done, another is `ABORTED`; a Vault that lacks a port the Index needs is `FAILED_PRECONDITION` naming it. `IndexState.rebuild` reports the stage, the cause (`CAUSE_REINDEX`, or `CAUSE_NEW` for an Index that did not exist), the Documents read and skipped, and the segments read.

*The state reported.* `Index.Status` gives the state now; `Index.Watch` gives it at once, then one item per change (a round, a failure, `stored_version` moving, a rebuild starting, moving on, ending), and keeps the last 256 items for a watcher that falls behind. `version` is the state the Index reflects (the token of `commit`); `stored_version` is the stored state the indexer last saw, set in every Vault and never behind `version`: the Index is behind while they differ. `pending` is the number of files the running round has to read, `0` when the Index is at `stored_version`, and unset in a Vault that does not index; `role` is true while this Vault's round runs. During a rebuild `version` stays the live Index's. Queries and searches are eventually consistent unless they name a `not_before` (QRY-8).

*Stopping.* `Vault.Close` stops the indexer and awaits its task; dropping the last reference signals it to stop, and it ends after its current round, in the background (`22` D7). A round checks for the stop between the portions of an embedding and between steps.

## 4. Hybrid `search`

**QRY-3. One call, several legs.** When both lexical and vector legs are available, `Collection.Search` and `Vault.SearchDocuments` **must** run both and fuse ranks. Default fusion is Reciprocal Rank Fusion (RRF). The caller passes `k` and the two weights (`lexical_weight`, `vector_weight`; 0 turns a leg off); those weights are request parameters, not constants in implementation source. A binding may expose another fusion as an option; RRF must work without a consumer-specific constant in library source. The result is a stream: the first item is a `SearchSummary` (whether the vector leg ran, or why not), then `SearchHit`s best first, each a `Document` with its scores — not a generated answer. With a reranker, order is that score (`13`); without it, RRF. Without a Projector there are no `fts` or `vector` columns: the lexical leg is empty and the vector leg is off. *Check:* (1) token query: expected id in `k` from the lexical leg even if the embedder is a stub; (2) synonym query with no shared tokens: expected id in `k` from the vector leg; (3) hybrid fixture: all expected ids appear at the given `k`, and a hit retrieved by both legs carries both scores (`tests/search.rs`: `a_text_search_fuses_the_lexical_and_the_vector_leg`).

**QRY-4. Fail closed.** A query or a search answers from the Index only when the Index is built: an Index never built is `INDEX_REBUILDING` (retryable; IDX-2), a file that does not read is `INDEX_BROKEN` until `Index.Reindex`, and an Index built with other ports than this Vault's is `INDEX_STALE` (IDX-9); never ids of another Vault, and never an empty answer in place of those codes. A rebuild of a built Index is not one of them: the live Index answers until the switch. A call reads one snapshot of the Index: the `commit` it read once and the table versions it names, so a call sees one state across all collections, and no read of the Index outlives the call. *Check:* an Index never built is `INDEX_REBUILDING` and one of another projection or model is `INDEX_STALE` (`tests/query.rs`: `an_index_never_built_is_rebuilding_and_one_of_another_projection_is_stale`; `tests/search.rs`: `the_summary_names_why_the_vector_leg_did_not_run`); an Index of another format or without a `commit` is rebuilt (`tests/index.rs`: `an_index_of_another_format_or_without_a_commit_is_rebuilt`).

**QRY-5. No ranking model in Scheda; the `Reranker` is a port.** The crate does not load a ranking model, a cross-encoder, or an LLM. The caller gives the Vault a `Reranker` (`Vault.SetReranker`; IDX-8): `Score` gets the query text first, then the Documents with their `raw`, and returns one score per Document, higher is better. A search that sets `rerank_limit` sends the first that many fused hits to it, and the hits are then in its order (`13` §6). `rerank_limit` without a reranker is `INVALID_ARGUMENT`. *Check:* a search without `rerank_limit` calls no reranker; a reranker that prefers two ids reorders them and sees the query first (`tests/search.rs`: `a_reranker_orders_the_first_hits_and_sees_the_query_first`); `rerank_limit` without a reranker is `INVALID_ARGUMENT` (`tests/search.rs`: `rerank_limit_needs_a_reranker_and_covers_the_page`).

**QRY-6. Filters on a search.** Optional `filter` on `DocumentSearch`, the same `Filter` as a query's. Both legs apply it before they rank (a prefilter): the lexical leg takes the top pool among the Documents that pass it, the vector leg admits only the `(collection, id)`s it matches, and the Filter never changes a score. A filtered-out Document is not a hybrid candidate. Unset `filter` → both legs on the selected collections. Filter naming and the column checks are the same as QRY-2 / `13` §3: one filter applies to every collection in scope. *Check:* a Document that fails the filter is absent from both legs (`tests/search.rs`: `the_filter_narrows_both_legs_before_they_rank`). *Check:* a filtered search still returns the one filtered-in Document that many others outrank on BM25 (the same test).

## 5. Edges

**Retired.** Edges were Schema fields (SCH-11). Scheda does not store or validate graph links. There is no `walk` / `walk_inverse`. A consumer may put target ids in Document bytes and follow them after `Collection.Get`.

## 6. What this document does not decide

SQL as a caller API — forbidden as the main surface (`07`). The engine runs typed expressions the library builds; no text of a query language is made from a caller's values.

Filesystem watcher — none: the indexer polls `HEAD`, and an uncommitted edit is not indexed.

Vectors of two models at once — not kept: a model change is the caller's `Index.Reindex`.

Phrase queries and stemming on the lexical leg — not in this version (the inverted index has no positions); a later version can add them per column.

Server-side Index for huge Vaults — replacement behind this API (`10`), not a second primary layer.

How a binding gives the Vault its ports — the binding's affair (`07`).
