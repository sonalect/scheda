# 06. Index and search

Document 6 of the Scheda package. Version 0.52, 5 October 2026.

Normative rules for the derived Index and `get`. **`find` and `search` (how they must work) are `13`.** Terms are in `02`. Collection declaration (write mode, perimeter, Index exclusion) is `05`. Index columns come from a `Projector` at `open`, not from the declaration. The caller's method names are in `07`. Codes: `IDX`, `QRY`. Phase **core** or **search** as marked.

An assertion without a check is not a requirement. The Index is never source of truth (STO-1, GIT-13).

---

## 1. The Index is disposable

**IDX-1. Rebuild from commits.** The Index directory is `{vault}/.scheda/` (gitignored; GIT-13). It is not part of a Vault commit or backup. The Index holds committed state only: it is built from the git objects of `HEAD` (of the Vault and of `{vault}/.isolated/`), never from the work tree, so an uncommitted edit or an open transaction's write is not indexed. `reindex` reads the collection declarations and Records of `HEAD`, calls `Projector.project` for Index columns, fills a new generation directory, and points `current` at it (LIB-16). `open` prunes generation directories other than the live one and the immediately previous one when `{vault}/.scheda/write.lock` is free **and** `{vault}/.scheda/reindex.lock` is free. While `reindex.lock` is held, `N+1` is being filled and is not an orphan: `open` must not delete it. *Check (**core**):* delete `.scheda/`, `get` and `history` of a fixture `document` still return that file; `lines` of a fixture `journal` still yields every line. After `reindex` (or once the background indexer rebuilt it, IDX-9), a fixture `find` matches the committed files. *Check:* a second `open` during a `reindex` build does not delete `N+1`; after publish, `current` names that generation.

**IDX-2. Versioned format.** The Index carries its own format version. **Core** writes `{vault}/.scheda/index/<generation>/format`: one decimal integer (currently `6`) and a newline. `format` and the projector dump are written whole (temp file and rename), and a generation's first write puts `format` last, so a reader in another handle or process never takes a half-written file or a generation still being started for a mismatch. `{vault}/.scheda/index/current` names the live generation. Each generation records, per leg, the commit that leg reflects: `<generation>/marks/` holds `lexical`, `vector`, `ids`, and `isolated-lexical`, `isolated-vector`, `isolated-ids` for the nested repository, each one commit id and a newline, written by temp file and rename after the leg's writes are durable. A missing or unreadable mark means "nothing indexed yet". A lexical leg that already holds documents but has no mark for the main repository is rebuilt into a new generation, since those documents come from an unknown commit; the nested repository's first collection, declared after the main repository filled the leg, is instead filled in place, with its collections dropped first. An incompatible or corrupt file is not read “as best effort”: an Index code (`index_version`, `index_corrupt`, `index_lexical`, `index_vector`, `index_missing`) until the Index is rebuilt. `repeat` tells whether waiting helps: `index_version` for another format is `repeat: allowed`, since the background rebuild publishes a new generation; `index_version` for a generation another Projector built (or none, against a handle with one, or the reverse) is `repeat: forbidden`, since nothing rebuilds it by itself — `reindex` from a handle with the Projector the Index should follow is the way over, and the message says so. `find` and `search` (Filter or not) check that projector dump on every call. An Index of another format (`3`, `4`, `5`, or unknown) is rebuilt in the background into a new generation (IDX-9); so is a generation whose files no longer read. `get`, `history`, and `lines` still read Vault / git files, and so do `replace` / `remove` (IDX-10). `find` and `search` fail with that Index code or return empty, never another Vault's ids. A handle follows `current`: when another handle or process publishes a new generation, its background indexer switches to it. *Check (**core**):* corrupt or unknown version → `search` / `find` return no hits or a failure, never another Vault's ids (QRY-4); `get` and `lines` still match the files.

**IDX-3. `project` failure stays out of search.** A Record whose `project(collection, id, raw)` errors or returns empty is omitted from the lexical and vector indexes. `get` still returns the file bytes (LIB-8). For `journal`, the id map is **not** dropped: the envelope still has `id`, so wipe-Index `get` can find the line. Encrypted collections still enter no Index (IDX-4). `add` does not call `project` to accept or reject the write (SCH-12). *Check (**search**):* bytes that `project` omits are absent from `search` / field `find` and present in `get`. *Check:* journal `get` after wipe `.scheda/` still finds the envelope `id` when `project` would omit that payload.

**IDX-4. One Index, owner-only; encrypted stays out.** There is one Index per Vault, `{vault}/.scheda/`, with both legs, and it holds every collection the build can read — isolated collections included (ISO-4). On Unix that directory is owner-only: `0700` on directories, `0600` on files, applied when it is created and after every write, including the files Tantivy creates that Scheda never opens. A wider mode is a `check` problem naming the path. There is no nested Index (ISO-10 retired).

An **encrypted** collection (SCH-16) enters no Index at all: the Index is plaintext on disk, so an entry for one would publish what the encryption was for. `reindex` and the background indexer skip those collections, and `find` / `search` naming one is `unsupported` rather than empty.

*Check:* grep of `{vault}/.scheda/` does not contain a fixture value written into an encrypted collection, before or after `reindex`. *Check:* the Index directory and its files carry those modes after a write and after `reindex`; a wider mode fails `check`.

**IDX-5. Journal `id` lookup.** After **core** Index exists, `get` on a `journal` must not scan every segment. The Index maps `(collection, id)` → segment path. File: `{vault}/.scheda/index/<generation>/journal/{name}/ids` (the collection name, same directory as the collection files, MOD-8). JSONL, one object per Record, keys `id` and `path` (vault-relative POSIX path of the segment). The ids file carries no version of its own: it belongs to the Index format (IDX-2). `reindex` rewrites the files from Vault text (envelopes, not `project`). Missing or unreadable map: `get` scans segment files (IDX-2). Until that map exists, a correct full scan is allowed (MOD / `03` §6). *Check (**core**, once the map is implemented):* `get` cost does not grow linearly with unrelated segments.

Writes (`add` / `replace`) update this map at once, before the commit, so `get` of a line just written succeeds. Lines that reach `HEAD` another way (`pull`, `sync`, a `git` commit, another process) are applied to the map by the background indexer (IDX-9) and found by `get` after its next round. Every change to an `ids` file holds a short flock `ids.lock` beside it, and a handle re-reads the file when its length or modification time changed before it answers "unknown id". A human edit is indexed once it is committed; an uncommitted edit is not watched.

**IDX-10. Caller `id` on the filesystem: `get`, `add`, `history`.** Those three validate the `id` (LIB-7), then use that identity against the tree (MOD-8). `get` / `history`: `document` `{name}/{id}` (`/` in `id` is a directory; the library does not append `.md`); `singleton` `{name}/{declared id}`; `journal` the IDX-5 map to the segment (the segment is not named `{id}`). `add` creates the file or envelope line; the Index follows after the commit (IDX-9). `replace` / `remove` also take the caller `id` against the tree: they find the Record file, never the Index, because the Index lags the last commit. A missing file → `not_found` (do not invent `{id}.md` from the argument). `remove` unlinks a `document` / `singleton` file (`journal` is `unsupported`); a file git never tracked is deleted without a commit. After `remove`, `history` still walks git of that path. `lines` does not take a caller `id`: it walks every journal line in declaration sequence without the Index (`07` LIB-19). `find` and `search` take `id`s **from the Index**, then open those files. An `id` the Index returns has already been accepted as a Record identity. *Check (**core**):* `find` `id =` an unindexed orphan file is empty; `get` and `history` of that id still use the file. *Check (**find**):* `replace` / `remove` of a Record file the Index has not reached yet succeed.

## 2. Point read and filter

**QRY-1. `get`.** Validate the `id` (LIB-7), then read the file for that `id` (IDX-10). Returns `api.v1.Record`: `collection`, `id`, `raw` (LIB-8). Missing Record is a failure, or a documented empty result if `07` chooses that shape — one shape per implementation. It is not a blank document. Encrypted: returned bytes are decrypted (LIB-8). That clause is **later**. *Check (**core**):* round-trip `add` / `get` matches stored bytes. *Check:* empty / illegal slug → `invalid` before any file open.

**QRY-2. `find`.** Run a Tantivy 0.26 `Query` on the Index (IDX-10, `07` LIB-10), then open files for the `(collection, id)`s it returns. Names are a Vault method argument; `Collection.find` uses Collection-handle Filter scope (a bare Projector field is this collection). An empty set is every non-isolated, non-encrypted collection — broad scans must not surface sealed values by default (ISO-3) — while a **named** isolated collection is an ordinary query, and a set mixing isolated with plain names is one page with one `total`. Query argument is `api.v1.FindQuery`: required `Filter` plus `include_raw` (unset or false omits `Record.raw`; `get` always returns `raw`). Paging is `(Count, TopDocs::with_limit(count).and_offset(offset))`. Page order is QRY-7. Returns `api.v1.FindResult`: `records` (one page, each `Record` as LIB-8) and `total` (indexed hits; a missing file does not decrease it). Field `id` is Record identity, a library column. No path query: the caller never supplies a Record path. Projector-column leaves are validated against `schema(collection)` (`13` §3). On Vault `find` / `search` each such leaf must set proto `collection`; identity `id` is not qualified. There is no `exclude_find` in the Vault. `id` cannot be excluded. Without a Projector, only identity (`all`, `term` on `id`) is accepted; any other field is `invalid`. `Filter` with `all` matches every **indexed** Record in the selected collections; the page is still `offset` / `count`. *Check (**core**):* a Record that fails the query is absent from the result, not only from a later top-k; `all` on a three-Record fixture with `count` 3 returns three and `total` 3; with `count` 1, one Record and `total` 3. *Check:* `should` of two `term`s is the union; `must` of two `term`s is the intersection. *Check:* `term` `id = "alpha"` returns that Record only when it is in the Index. *Check:* `count` `0` → `invalid`; `offset` past the last match → empty `records` and `total` still the match count. *Check:* default `find` omits `raw`; `include_raw` true fills `Record.raw`. *Check:* Vault `find` with bare Projector field `foo` is `invalid`; Collection `find` with another collection's qualifier is `invalid`.

`find` does not use vectors. That is `search`. There is no magic `body` key unless the Projector names a column `body`. The concatenated BM25 blob is still `search` only.

**QRY-7. `find` order.** Exactly one selected collection and it is `journal`: append order, not score. Closed segments in declaration sequence (SCH-14), each file from first line to last, then the open segment. Rotation does not reorder earlier lines. Implemented as `order_by_fast_field` on an Index ordinal (segment + line, or a monotonic counter). Any other selection (`document` / `singleton`, several collections, mixed kinds): Tantivy score descending, and **equal scores break by the Index ordinal ascending** — the same monotonic per-collection counter QRY-7 uses for journal order. Paging is skip/take in that order.

An earlier revision of this rule broke a score tie by `DocAddress`. That was not an order at all: a document's address depends on which Tantivy segment it landed in, segment assignment varies between runs of the same inserts, and so two identical queries on identical content returned different pages — which made `offset` / `count` able to repeat or skip a Record. Two limits of the replacement are worth stating rather than discovering. The ordinal counts per collection, so two Records in **different** collections can share both score and ordinal, and their relative order stays unspecified. And the ordinal is assigned when a Record is indexed, not derived from its content, so `reindex` may hand out different ordinals than incremental writes did and change the order **within** a tie. A page is reproducible for a given Index; it is not a property of the data. Ordered journal read without the Index is `lines` (`07` LIB-19), not `find`. *Check (**core**):* insert A, B; rotate; insert C; `find` with `all`, `offset` 0 and `count` 3 → A, B, C. *Check:* `count` `0` → `invalid`.

## 3. Lexical and vector (**search**)

The Index is a **retrieval** engine an agent can recall from, not a substring demo. Grep, SQL `LIKE`, and scanning Vault files at query time are not `search`.

Columns other than identity come from `Projector.schema(collection)`: name, kind (`text` / `integer` / `number` / `boolean` / `text list`), and marks (`find` / `fts` / `vector`). Same column name may differ in kind across collections. Unknown collection on `schema`: empty columns or an error; both are allowed. No Projector: identity columns only; `search` has no FTS/vector slots (lexical empty, vector off).

**IDX-6. Lexical index.** Ranked full-text (BM25 or equivalent) over Projector columns marked `fts`. In-process; a separate search server is not required. Identifiers, rare tokens, and exact phrases must surface. The first implementation (Rust) pins a BM25 library (for example Tantivy); the contract is the ranking class, not a crate name, and is not SQL. *Check:* an exact token in an `fts` column ranks that Record inside the requested `k` among distractors that lack the token; the same token only in a column without `fts` is not a hit.

**IDX-7. Vector index.** In-process ANN nearest neighbours (HNSW or equivalent) over Projector columns marked `vector`. Same Index directory as lexical. No external vector database. At OPS-1, brute-force over every stored vector is not the implementation. The first implementation may pin an ANN library (for example USearch). Graph connectivity and the insert / search expansion of that graph are chosen by the binding, not left as library zero-defaults. Search expansion is a floor independent of the requested `k`: on a small fixture whose exact neighbours are known by brute force, the list for `N` is the prefix of the list for `2N`, and both match that exact order. *Check:* a query that shares no tokens with the Record but is a synonym (fixture) still ranks that Record inside the requested `k` when an embedder is present. *Check:* `search(N)` keys equal `search(2N)[..N]` and both equal brute-force nearest neighbours on a small in-process index.

**IDX-8. Embedder is injected.** The caller passes an embedder (a function or interface; in Rust, typically a trait). The library does not require the network to embed. No embedder → vector leg off; lexical, `find`, and writes still work. An embedder that calls the network is the caller's; core git with `auto_sync` off still GIT-8. The Projector is injected the same way at `open` (not proto). *Check:* build and query with no embedder; a stub that returns a fixed vector fills the vector table; those runs make no unexpected connections. *Check:* with no Projector, `find` `all` works and `find` on a Projector field is `invalid`.

**IDX-9. Background indexer.** Writes (`add` / `replace` / `remove` / `commit`) do not touch the lexical or vector Index; only the journal `id` map is updated at once (IDX-5). With **find**, `open` starts one thread per handle that keeps the Index on `HEAD`: it wakes on this handle's commits (`commit`, autocommit, `pull`, `sync`) and otherwise reads `HEAD` every `OpenOptions.index_poll_ms` (default 1 s), so commits from `git`, another process, or a build without **find** are indexed the same way. Each round diffs each leg's mark against `HEAD` (git objects only), applies the changed Records in batches, and moves the mark after the writes are durable; repeating a round is harmless. A change of a collection declaration re-indexes that collection in full; a mark whose commit is gone, or a reset or rebase, re-applies the leg from the empty tree. `find` / `search` are eventually consistent: `wait_indexed(timeout)` waits until every leg that has an owner reaches the `HEAD` seen at the call (`io_timed_out` past the timeout), and `index_status()` reports the marks, Records still to index per leg, roles, `model_mismatch`, and the last error.

One process indexes a work tree at a time: the lexical leg and the journal maps belong to the holder of `{vault}/.scheda/index.lock`, taken only by a handle whose Projector matches the generation; the vector leg to the holder of `vector.lock`, taken only by a handle whose embedder has the generation's `model_id` and dimensions. Both are `try_lock`; another handle takes the role when the holder exits. The indexer never takes `write.lock`. A handle without a role follows the holders: Tantivy reloads on each query, the vector dump on each round and each `search` (the dump is saved as a whole `vector/<seq>/` and then named by `vector/current`; a vector pass saves it once when it ends or stops, and only at geometrically spaced checkpoints during a long first pass, so embedding N slots writes O(N) bytes, not O(N²)). An indexing failure fails no write: the leg keeps its mark and is retried with backoff (100 ms doubling to 30 s; a vector failure holds back the vector leg alone), and the failure is `index_status().last_error`. Dropping the last handle, or `close`, stops and joins the thread after at most one embedder call.

Vector slots whose embedder text is unchanged are not sent to the embedder again: each slot stores a git blob hash of that text in `keys.json`, and a matching digest plus the same `model_id` and dimensions leaves the ANN entry untouched. A slot that disappears (`schema` no longer marks it `vector`, or this Record's `project` omits it) is removed. An embedder of another `model_id` or dimensions writes nothing and its `search` runs without the vector leg until the caller runs `reindex` with it, which re-embeds every slot; model identity lives in the Index, not on the Record. `reindex` builds `N+1` from `HEAD` the same way, without `write.lock`, marks it with the commits it read, and publishes; the indexer applies whatever was committed meanwhile. Without an embedder `reindex` carries the previous vectors and their marks over. *Check:* `add`, then `wait_indexed`, then `search` finds the new Record (both legs with an embedder). *Check:* `remove`, `wait_indexed`, then `find` / `search` do not return that `id`. *Check:* writing the same Records again does not call the embedder; changing one column re-embeds only that slot; a vanished slot is absent from vector `search`. *Check:* a commit made with `git` is found after `wait_indexed`; a stub embedder that fails twice then succeeds fails no write, shows the error in `index_status`, and the vectors land.

## 4. Hybrid `search`

**QRY-3. One call, several legs.** When both lexical and vector legs are available, `search` **must** run both and fuse ranks. Default fusion is Reciprocal Rank Fusion (RRF). The caller may pass `k` and merge weights; those weights are a request parameter, not constants in implementation source. A binding may expose another fusion as an option; RRF must work without a consumer-specific constant in library source. The result is ordered `id` plus scores — not a generated answer. `Hit.collection` is output only. With a reranker, order is that score (`13`); without it, RRF. Without a Projector there are no FTS/vector slots: the lexical leg is empty and the vector leg is off. *Check:* (1) token query: expected id in `k` from the lexical leg even if the embedder is a stub; (2) synonym query with no shared tokens: expected id in `k` from the vector leg; (3) hybrid fixture: all expected ids appear at the given `k`, and a hit retrieved by both legs carries both scores.

**QRY-4. Fail closed.** If the Index is missing or corrupt, `search` returns no hits or a failure, not stale ids. The handle that holds the lexical role checks a generation that failed to read and rebuilds it in the background from `HEAD`; queries fail until `current` names the new generation. An unfinished `N+1` is not served: readers stay on live `N` until `current` moves. *Check:* overwrite Index with junk; `search` does not return foreign ids, and after the rebuild `find` matches the files. *Check:* `find` / `search` on the live generation during a `reindex` build still return Records that were in `N`.

**QRY-5. No ranking model in Scheda.** The crate does not load a ranking model, a cross-encoder, or an LLM. Optional: `search` takes a caller `Reranker` callback (`13`); then returned hits are already in that order. *Check:* `search` without a callback does not pull a plugin; with a stub that swaps two ids, those ids swap in `SearchHits`.

**QRY-6. Filters on `search`.** Optional `api.v1.Filter` on `SearchQuery`. When set, Tantivy runs it first on the selected collections; BM25 and USearch search only that `(collection, id)` set (BM25: the Filter is a `Must` clause beside the text query, so the top pool is taken among Records that pass it; USearch: `filtered_search`). A filtered-out Record is not a hybrid candidate. Unset `filter` → both legs on the selected collections. Filter naming and `schema(collection)` checks are the same as QRY-2 / `13` §3. *Check:* a Record that fails the filter is absent from both legs. *Check:* 80 Records outrank the one filtered-in Record on BM25 and a filtered `search` still returns it. *Check:* Vault `search` with a Filter leaf that omits the collection qualifier on a Projector column is `invalid`.

## 5. Edges

**Retired.** Edges were Schema fields (SCH-11). Scheda does not store or validate graph links. There is no `walk` / `walk_inverse`. A consumer may put target ids in Record bytes and follow them after `get`.

## 6. What this document does not decide

SQL as a caller API — forbidden as the main surface (`07`). An implementation may use SQL internally.

Filesystem watcher — none: the indexer polls `HEAD`, and an uncommitted edit is not indexed.

Vectors of two models at once — not kept: a model change is the caller's `reindex`.

Server-side Index for huge Vaults — replacement behind this API (`10`), not a second primary layer.

The Rust type of `Projector` on `open` — the binding's affair (`07`).
