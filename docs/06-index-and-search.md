# 06. Index and search

Document 6 of the Scheda package. Version 0.53, 19 October 2026.

IDX-1, IDX-2, IDX-5, IDX-9, and QRY-4 describe the Index and its indexer as the code of the `proto-contract` branch builds them (`20` D23). The rest of this document still uses the names of `0.21` (Record, `add`, `find`, `search`, `reindex`) until the docs pass of `20` §5; in those sections a Record is a Document, `find` is a query, `search` is a search, and `reindex` is `Index.Reindex`.

Normative rules for the derived Index and `get`. **`find` and `search` (how they must work) are `13`.** Terms are in `02`. Collection declaration (write mode, perimeter, Index exclusion) is `05`. Index columns come from a `Projector` at `open`, not from the declaration. The caller's method names are in `07`. Codes: `IDX`, `QRY`. Phase **core** or **search** as marked.

An assertion without a check is not a requirement. The Index is never source of truth (STO-1, GIT-13).

## 1. The Index is disposable

**IDX-1. Rebuild from commits.** The Index is `{vault}/.scheda/index/` (gitignored; GIT-13). It is not part of a Vault commit or backup. It holds committed state only: it is built from the git objects of `HEAD` of the Vault and of `{vault}/.isolated/`, never from the work tree, so an uncommitted edit or a write still in progress is not indexed. Deleting it loses nothing: the next round of the indexer builds it again from `HEAD` (IDX-9). `GetDocument`, `History`, and the lines of a journal never need it. *Check (**core**):* delete `.scheda/`; `GetDocument` and `History` of a fixture Document still return that file, and every line of a fixture journal is still found; once the indexer rebuilt the Index, a fixture query matches the committed files (`tests/index.rs`: `an_index_of_another_format_or_without_a_commit_is_rebuilt`, `a_line_is_found_before_the_indexer_ran_after_it_and_without_its_map`).

**IDX-2. Layout and one state.** The Index is these files:

```text
{vault}/.scheda/index.lock             flock, held for one indexer round
{vault}/.scheda/index/format           the layout number (now 2) and a newline
{vault}/.scheda/index/commit           the state the Index reflects; the last write of a round
{vault}/.scheda/index/journal/{name}/ids   the id map of a journal (IDX-5)
{vault}/.scheda/index/lexical/         the Tantivy index; its commit payload is the state it reached
{vault}/.scheda/index/vector/vectors   the model, the key map, and the HNSW index, in one file
{vault}/.scheda/index/vector/state     the stamp of the vectors write it stands on, and the state reached
{vault}/.scheda/index/columns          the projection and the columns each collection was indexed with
{vault}/.scheda/index/stale            the collections whose columns changed since (IDX-9)
```

A state is one line: `main {oid}`, followed by `isolated {oid}` when the nested repository has a commit (`-` for no commit); `IndexState.version` reports it as an opaque token. Every file Scheda writes under `index/` is written whole (temporary file, `fsync`, rename) and owner-only (IDX-4); Tantivy commits its own files through its `meta.json`. There are no generations and no marks per part: `commit` is the one state every part reflects, so a part is never behind `commit` (a stale collection excepted, IDX-9), and a part ahead of it (left by a round that died, IDX-9) is not believed until `commit` moves. An Index whose `format` is not this build's number, or that has no `commit` that parses, is not built: queries and searches are `INDEX_REBUILDING` (retryable), and the indexer rebuilds it (IDX-9). A file that does not read is `INDEX_BROKEN` until `Index.Reindex`: nothing rebuilds a damaged Index by itself. Queries and searches fail with that code, never answer from another Vault's ids. *Check (**core**):* another `format` or a `commit` that does not parse reads as not built (`index::tests::another_format_or_a_broken_commit_reads_as_not_built`); a damaged `vectors` is `INDEX_BROKEN` and a `Reindex` repairs it (`vector::tests::a_damaged_vector_index_is_broken_and_a_reindex_repairs_it`); a map that is not one is `INDEX_BROKEN` (`idmap::tests::bytes_that_are_not_a_map_are_index_broken`).

**IDX-3. `project` failure stays out of search.** A Record whose `project(collection, id, raw)` errors or returns empty is omitted from the lexical and vector indexes. `get` still returns the file bytes (LIB-8). For `journal`, the id map is **not** dropped: the envelope still has `id`, so wipe-Index `get` can find the line. Encrypted collections still enter no Index (IDX-4). `add` does not call `project` to accept or reject the write (SCH-12). *Check (**search**):* bytes that `project` omits are absent from `search` / field `find` and present in `get`. *Check:* journal `get` after wipe `.scheda/` still finds the envelope `id` when `project` would omit that payload.

**IDX-4. One Index, owner-only; encrypted stays out.** There is one Index per Vault, `{vault}/.scheda/`, with both legs, and it holds every collection the build can read — isolated collections included (ISO-4). On Unix that directory is owner-only: `0700` on directories, `0600` on files, applied when it is created and after every write, including the files Tantivy creates that Scheda never opens. A wider mode is a `check` problem naming the path. There is no nested Index (ISO-10 retired).

An **encrypted** collection (SCH-16) enters no Index at all: the Index is plaintext on disk, so an entry for one would publish what the encryption was for. `reindex` and the background indexer skip those collections, and `find` / `search` naming one is `unsupported` rather than empty.

*Check:* grep of `{vault}/.scheda/` does not contain a fixture value written into an encrypted collection, before or after `reindex`. *Check:* the Index directory and its files carry those modes after a write and after `reindex`; a wider mode fails `check`.

**IDX-5. Journal `id` lookup.** Once the Index exists, `GetDocument` on a journal must not scan every segment. The Index maps each line `id` to its segment: `{vault}/.scheda/index/journal/{name}/ids`, a text file: the line `scheda-ids 1`, the state the map is true at (IDX-2), the number of segments, the segments as JSON strings (Vault-relative), then `{id}\t{segment number}` per line, sorted by `id`. The map belongs to the Index format (IDX-2) and is built from the envelopes, not from `Project`. Only the indexer writes it, whole, in its round (IDX-9); a write never touches it. Because a map records the state it is true at, it is right on its own: a line it does not list is looked for only in the segments that differ between that state and `HEAD` (a tree comparison, no process), so a line just written is found before the indexer reaches it. A journal with no map, a map whose state is gone from its repository, and a map that names a segment without the line (a segment changed by hand) are scanned. A Vault opened only by handles that cannot index (IDX-9) has no maps and scans; a build without `find` indexes the maps with every handle. *Check (**core**):* an absent `id` is looked for only in the segments changed since the map (`idmap::tests::an_absent_id_is_looked_for_only_in_the_segments_changed_since_the_map`); a line is found before the indexer ran after it and without its map (`tests/index.rs`: `a_line_is_found_before_the_indexer_ran_after_it_and_without_its_map`); a Vault opened only without ports finds its lines (`tests/index.rs`: `a_vault_opened_only_without_ports_finds_its_lines_without_an_index`).

**IDX-10. Caller `id` on the filesystem: `get`, `add`, `history`.** Those three validate the `id` (LIB-7), then use that identity against the tree (MOD-8). `get` / `history`: `document` `{name}/{id}` (`/` in `id` is a directory; the library does not append `.md`); `singleton` `{name}/{declared id}`; `journal` the IDX-5 map to the segment (the segment is not named `{id}`). `add` creates the file or envelope line; the Index follows after the commit (IDX-9). `replace` / `remove` also take the caller `id` against the tree: they find the Record file, never the Index, because the Index lags the last commit. A missing file → `not_found` (do not invent `{id}.md` from the argument). `remove` unlinks a `document` / `singleton` file (`journal` is `unsupported`); a file git never tracked is deleted without a commit. After `remove`, `history` still walks git of that path. `lines` does not take a caller `id`: it walks every journal line in declaration sequence without the Index (`07` LIB-19). `find` and `search` take `id`s **from the Index**, then open those files. An `id` the Index returns has already been accepted as a Record identity. *Check (**core**):* `find` `id =` an unindexed orphan file is empty; `get` and `history` of that id still use the file. *Check (**find**):* `replace` / `remove` of a Record file the Index has not reached yet succeed.

## 2. Point read and filter

**QRY-1. `get`.** Validate the `id` (LIB-7), then read the file for that `id` (IDX-10). Returns `api.v1.Record`: `collection`, `id`, `raw` (LIB-8). Missing Record is a failure, or a documented empty result if `07` chooses that shape — one shape per implementation. It is not a blank document. Encrypted: returned bytes are decrypted (LIB-8). That clause is **later**. *Check (**core**):* round-trip `add` / `get` matches stored bytes. *Check:* empty / illegal slug → `invalid` before any file open.

**QRY-2. `find`.** Run a Tantivy 0.26 `Query` on the Index (IDX-10, `07` LIB-10), then open files for the `(collection, id)`s it returns. Names are a Vault method argument; `Collection.find` uses Collection-handle Filter scope (a bare Projector field is this collection). An empty set is every non-isolated, non-encrypted collection — broad scans must not surface sealed values by default (ISO-3) — while a **named** isolated collection is an ordinary query, and a set mixing isolated with plain names is one page with one `total`. Query argument is `api.v1.FindQuery`: required `Filter` plus `include_raw` (unset or false omits `Record.raw`; `get` always returns `raw`). Paging is `(Count, TopDocs::with_limit(count).and_offset(offset))`. Page order is QRY-7. Returns `api.v1.FindResult`: `records` (one page, each `Record` as LIB-8) and `total` (indexed hits; a missing file does not decrease it). Field `id` is Record identity, a library column. No path query: the caller never supplies a Record path. Projector-column leaves are validated against `schema(collection)` (`13` §3). On Vault `find` / `search` each such leaf must set proto `collection`; identity `id` is not qualified. There is no `exclude_find` in the Vault. `id` cannot be excluded. Without a Projector, only identity (`all`, `term` on `id`) is accepted; any other field is `invalid`. `Filter` with `all` matches every **indexed** Record in the selected collections; the page is still `offset` / `count`. *Check (**core**):* a Record that fails the query is absent from the result, not only from a later top-k; `all` on a three-Record fixture with `count` 3 returns three and `total` 3; with `count` 1, one Record and `total` 3. *Check:* `should` of two `term`s is the union; `must` of two `term`s is the intersection. *Check:* `term` `id = "alpha"` returns that Record only when it is in the Index. *Check:* `count` `0` → `invalid`; `offset` past the last match → empty `records` and `total` still the match count. *Check:* default `find` omits `raw`; `include_raw` true fills `Record.raw`. *Check:* Vault `find` with bare Projector field `foo` is `invalid`; Collection `find` with another collection's qualifier is `invalid`.

`find` does not use vectors. That is `search`. There is no magic `body` key unless the Projector names a column `body`. The concatenated BM25 blob is still `search` only.

**QRY-7. `find` order.** Exactly one selected collection and it is `journal`: append order, not score. Closed segments in declaration sequence (SCH-14), each file from first line to last, then the open segment. Rotation does not reorder earlier lines. Implemented as `order_by_fast_field` on an Index ordinal (segment + line, or a monotonic counter). Any other selection (`document` / `singleton`, several collections, mixed kinds): Tantivy score descending, and **equal scores break by the Index ordinal ascending** — the same monotonic per-collection counter QRY-7 uses for journal order. Paging is skip/take in that order.

An earlier revision of this rule broke a score tie by `DocAddress`. That was not an order at all: a document's address depends on which Tantivy segment it landed in, segment assignment varies between runs of the same inserts, and so two identical queries on identical content returned different pages — which made `offset` / `count` able to repeat or skip a Record. Two limits of the replacement are worth stating rather than discovering. The ordinal counts per collection, so two Records in **different** collections can share both score and ordinal, and their relative order stays unspecified. And the ordinal is assigned when a Record is indexed, not derived from its content, so `reindex` may hand out different ordinals than incremental writes did and change the order **within** a tie. A page is reproducible for a given Index; it is not a property of the data. Ordered journal read without the Index is `lines` (`07` LIB-19), not `find`. *Check (**core**):* insert A, B; rotate; insert C; `find` with `all`, `offset` 0 and `count` 3 → A, B, C. *Check:* `count` `0` → `invalid`.

## 3. Lexical and vector (**search**)

The Index is a **retrieval** engine an agent can recall from, not a substring demo. Grep, SQL `LIKE`, and scanning Vault files at query time are not `search`.

Columns other than identity come from `Projector.schema(collection)`: name, kind (`text` / `integer` / `number` / `boolean` / `text list`), and marks (`find` / `fts` / `vector`). Same column name may differ in kind across collections. Unknown collection on `schema`: empty columns or an error; both are allowed. No Projector: identity columns only; `search` has no FTS/vector slots (lexical empty, vector off).

**IDX-6. Lexical index.** Ranked full-text (BM25 or equivalent) over Projector columns marked `fts`. In-process; a separate search server is not required. Identifiers, rare tokens, and exact phrases must surface. The first implementation (Rust) pins a BM25 library (for example Tantivy); the contract is the ranking class, not a crate name, and is not SQL. *Check:* an exact token in an `fts` column ranks that Record inside the requested `k` among distractors that lack the token; the same token only in a column without `fts` is not a hit.

**IDX-7. Vector index.** In-process ANN nearest neighbours (HNSW or equivalent) over Projector columns marked `vector`. Same Index directory as lexical. No external vector database. At OPS-1, brute-force over every stored vector is not the implementation. The first implementation may pin an ANN library (for example USearch). Graph connectivity and the insert / search expansion of that graph are chosen by the binding, not left as library zero-defaults. Search expansion is a floor independent of the requested `k`: on a small fixture whose exact neighbours are known by brute force, the list for `N` is the prefix of the list for `2N`, and both match that exact order. *Check:* a query that shares no tokens with the Record but is a synonym (fixture) still ranks that Record inside the requested `k` when an embedder is present. *Check:* `search(N)` keys equal `search(2N)[..N]` and both equal brute-force nearest neighbours on a small in-process index.

**IDX-8. Embedder is injected.** The caller passes an embedder (a function or interface; in Rust, typically a trait). The library does not require the network to embed. No embedder → vector leg off; lexical, `find`, and writes still work. An embedder that calls the network is the caller's; core git with `auto_sync` off still GIT-8. The Projector is injected the same way at `open` (not proto). *Check:* build and query with no embedder; a stub that returns a fixed vector fills the vector table; those runs make no unexpected connections. *Check:* with no Projector, `find` `all` works and `find` on a Projector field is `invalid`.

**IDX-9. The indexer.** Writes (single writes, write streams, batches, `Pull`, `Sync`) never touch the Index, the journal `id` maps included. Every open Vault starts one thread, `scheda-indexer`, that keeps the Index at `HEAD`. It wakes at once when a write of this Vault moves `HEAD`, when a port is set, and on `Index.Reindex`; otherwise it looks at `HEAD` every `OpenOptions.index_poll_ms` (default 1 s; 10 ms to 1 h), which finds the commits of other processes, of `git`, and of pulls. A look reads the two `HEAD`s and the `format` and `commit` files, and starts no process.

*A round.* (1) The Vault takes a round only when it may index (*who indexes*, below). (2) It takes `flock` on `{vault}/.scheda/index.lock` without waiting; when another indexer, of this process or another, holds it, the round is skipped and the next look tries again. (3) It reads `HEAD` of both repositories and the difference between the trees of `commit` and of `HEAD`, git objects only. (4) It gives that difference to each part in turn: the journal `id` maps, the lexical side, the vector side. (5) It writes `commit` last, lets the lock go, and publishes the new state to `Index.Status` and `Index.Watch`. When `HEAD` moved meanwhile, the next round starts at once. The indexer never takes the write lock, so writes go on during a round. The difference is between trees, not along history: a reset, a rebase, or a pull that rewrote history is applied like any other move as long as the object of the commit in `commit` is still in its repository; only when it is gone (pruned) is the round a rebuild. A collection whose declaration file changed is indexed whole inside the round.

*The parts.* The id maps update the map of each journal whose segments changed since the map's own state, and build a missing one (IDX-5). The lexical side reads each changed Document, or every line of each changed journal segment, projects it once (`Projector.Project`), replaces its Tantivy documents, and commits Tantivy once, with the round's target state as the commit payload. It hands the texts of the `vector` columns of those projections to the vector side, so a Document is projected once per round for both sides. The vector side reads `vectors` whole, drops the vectors of the changed Documents, keeps a stored vector whose text has the same digest (the git blob hash of the text), sends only the other texts to `Embedder.Embed` in one stream, and writes `vectors` whole with a new stamp, then `state`; a round that changes no vector writes `state` alone. An embedder of another model or dimensions than `vectors` records makes the round fail with `FAILED_PRECONDITION` rather than mix two models.

*Who indexes.* A Vault takes a round only when it has every port the Index needs: with `find`, a Projector of the projection the Index was built with (any while the Index records none); with `search`, when a collection has a `vector` column, an embedder of the Index's model and dimensions (any while the Index has none). A Vault without them never takes `index.lock`: it reads the Index others build, its `role` stays false, and its status follows the `commit` on disk. A build without `find` has no Projector to ask, and every Vault indexes the journal maps. When no open Vault on the path can index, the Index does not move: an Index never built stays `INDEX_REBUILDING`, and a built one answers from its last state. A Projector of another projection than the Index's makes this Vault's status `INDEX_STALE` and it does not index until its own `Reindex`. When the columns `Projector.Columns` gives for one collection change under the same projection, the round lists that collection in `stale`, keeps its old entries, and stops updating it: a lexical read that names it is `INDEX_STALE`, and while `stale` exists every vector read is `INDEX_STALE`, whatever collections it names, until `Reindex`.

*A failed round.* A round that fails changes no `commit` and fails no write. `IndexState.last_error` carries the failure until a round succeeds; the round is tried again after a pause that starts at `index_poll_ms` and doubles up to eight times it, or at once when a write moves `HEAD`. A panic inside a round is caught and reported the same way. The parts written before the failure stay, ahead of `commit`; the next round starts from `commit` again, and each part recognises what it already holds: a map records its own state; the lexical side compares its commit payload with `commit` and with the target, and walks every Document again when the payload is neither; the vector side compares `state` with `commit` and with the target. A vector side whose `state` names another write of `vectors`, or a state other than `commit` and the target, is out of step: the round fails with `INDEX_BROKEN` until `Reindex`. The vectors an embedder gave before it failed are kept in this Vault's memory, by text digest, until a round succeeds, so the next try sends only the texts that have none; a text the embedder refuses (`REFUSED`) leaves its Document out of the vector side, as a refused projection leaves one out of the lexical side. Because `commit` moves for the whole Index, an embedder that does not answer holds back `commit` and the reported `version`; the lexical side has already committed the new Documents, and a query sees them.

*A rebuild.* When the Index has no `commit`, another `format`, a `commit` whose object is gone, or `Index.Reindex` was asked, the round is a rebuild: under the same lock it removes `commit` first, then every other file of the Index, writes `format`, indexes `HEAD` from nothing, and writes `commit` last. Nothing is built beside the Index, so meanwhile queries and searches are `INDEX_REBUILDING` (retryable), and writes go on. A rebuild embeds every text again, since the stored vectors go with the rest. A rebuild that fails starts again from nothing on its next try; the vectors embedded so far stay in that Vault's memory. `Index.Reindex` returns at once; while this Vault has one asked for or running, another is `ABORTED` (a `Reindex` of another Vault on the path is not refused: it rebuilds again after this one); a Vault that lacks a port the Index needs is `FAILED_PRECONDITION` naming it. `IndexState.rebuild` reports the stage, the Documents read and skipped, and the segments read.

*The state reported.* `Index.Status` gives the state now; `Index.Watch` gives it at once, then one item per change (a round, a failure, a rebuild starting, moving on, ending), and keeps the last 256 items for a watcher that falls behind. `version` is the token of `commit`; `pending` is the number of files the running round has to read, counted when it starts, and `0` otherwise, also in a Vault that does not index while the Index is behind; `role` is true while this Vault's round runs; `model_mismatch` says this Vault's embedder is of another model than the vectors. Queries and searches are eventually consistent; `version` is the state every part has reached, and a query may see newer Documents.

*Stopping.* Dropping the last reference to a Vault stops its thread and joins it. A round checks for the stop every 256 Documents and between the embedding and the write of the vectors; an `Embed` call in progress is waited for to the end of its stream.

*Check:* a write is found after the Index reached it, both sides with an embedder; a deleted Document is gone from both (`vector::tests::a_documents_vector_values_are_in_the_index_replaced_on_change_and_removed_on_delete`; `tests/index.rs`: `a_write_is_indexed_and_the_map_lists_its_line`). *Check:* one `Project` per changed Document per round (`vector::tests::the_projection_is_shared_one_project_per_changed_document_per_round`). *Check:* an embedder that fails after the 7th of 20 texts fails no write and changes no `commit`; the next round sends only the other 13 (`vector::tests::a_failing_embedder_fails_the_round_keeps_the_vectors_and_the_next_round_sends_the_rest`; `tests/index.rs`: `a_round_that_fails_changes_no_commit_fails_no_write_and_the_next_one_succeeds`). *Check:* a round that walks every Document again sends only the texts that changed (`vector::tests::a_text_that_did_not_change_is_not_embedded_again_when_a_round_walks_every_document`). *Check:* a commit made with `git` and a pull are indexed (`tests/index.rs`: `a_commit_made_by_hand_is_indexed`, `a_pull_is_indexed`). *Check:* the rounds of two Vaults on one path never overlap, and three processes end at one version (`indexer::tests::the_rounds_of_two_handles_of_one_vault_never_overlap`; `tests/index.rs`: `handles_of_three_processes_take_turns_and_end_at_one_version`). *Check:* a Vault without a Projector, or without the embedder a `vector` column needs, never takes a round (`vector::tests::a_handle_without_a_projector_or_a_needed_embedder_never_takes_a_round`; `tests/index.rs`: `a_process_without_ports_leaves_the_indexing_to_the_one_with_them`). *Check:* `Watch` gives the state at once and then one item per round; `Reindex` returns before the rebuild, and a second one is `ABORTED` (`indexer::tests::the_watch_gives_the_state_at_once_and_then_one_item_per_round`, `indexer::tests::a_rebuild_waits_for_the_lock_and_a_second_request_is_aborted`; `tests/index.rs`: `reindex_returns_before_the_rebuild_a_second_is_aborted_and_the_maps_match`). *Check:* a round that fails or panics is reported and tried again (`indexer::tests::a_round_that_fails_or_panics_is_reported_and_tried_again`). *Check:* close and drop end the thread (`tests/index.rs`: `close_and_drop_end_the_indexer_thread`).

## 4. Hybrid `search`

**QRY-3. One call, several legs.** When both lexical and vector legs are available, `search` **must** run both and fuse ranks. Default fusion is Reciprocal Rank Fusion (RRF). The caller may pass `k` and merge weights; those weights are a request parameter, not constants in implementation source. A binding may expose another fusion as an option; RRF must work without a consumer-specific constant in library source. The result is ordered `id` plus scores — not a generated answer. `Hit.collection` is output only. With a reranker, order is that score (`13`); without it, RRF. Without a Projector there are no FTS/vector slots: the lexical leg is empty and the vector leg is off. *Check:* (1) token query: expected id in `k` from the lexical leg even if the embedder is a stub; (2) synonym query with no shared tokens: expected id in `k` from the vector leg; (3) hybrid fixture: all expected ids appear at the given `k`, and a hit retrieved by both legs carries both scores.

**QRY-4. Fail closed.** A query or a search answers from the Index only when the Index is built: no `format` of this build or no `commit` is `INDEX_REBUILDING` (retryable; IDX-2), a file that does not read is `INDEX_BROKEN`, and a stale projection or collection is `INDEX_STALE` (IDX-9); never ids of another Vault, and never an empty answer in place of those codes. A reader that finds a file gone under it re-reads `commit` and `format`: when a rebuild emptied the Index meanwhile, the answer is `INDEX_REBUILDING`, not a read failure. A reader keeps the Tantivy searcher and the vectors it opened for the whole call (one snapshot per stream), and opens them again only when `meta.json` or the stamp of `vectors` changed. A rebuild is not served half-built: there is no Index while it runs. *Check:* a damaged `vectors` is `INDEX_BROKEN`, and after `Reindex` a search finds the Document again (`vector::tests::a_damaged_vector_index_is_broken_and_a_reindex_repairs_it`). *Check:* during a rebuild, and with another format, the reader is `INDEX_REBUILDING` and reads afterwards (`lexical::tests::the_reader_is_rebuilding_without_a_commit_or_in_another_format_and_reads_afterwards`); an Index never built is `INDEX_REBUILDING` and retryable for a query and a search (`tests/query.rs`: `an_index_never_built_is_index_rebuilding_and_retryable`; `tests/search.rs`: `an_index_never_built_is_index_rebuilding_for_a_search`); an Index of another format or without a `commit` is rebuilt (`tests/index.rs`: `an_index_of_another_format_or_without_a_commit_is_rebuilt`).

**QRY-5. No ranking model in Scheda.** The crate does not load a ranking model, a cross-encoder, or an LLM. Optional: `search` takes a caller `Reranker` callback (`13`); then returned hits are already in that order. *Check:* `search` without a callback does not pull a plugin; with a stub that swaps two ids, those ids swap in `SearchHits`.

**QRY-6. Filters on `search`.** Optional `api.v1.Filter` on `SearchQuery`. When set, Tantivy runs it first on the selected collections; BM25 and USearch search only that `(collection, id)` set (BM25: the Filter is a `Must` clause beside the text query, so the top pool is taken among Records that pass it; USearch: `filtered_search`). A filtered-out Record is not a hybrid candidate. Unset `filter` → both legs on the selected collections. Filter naming and `schema(collection)` checks are the same as QRY-2 / `13` §3. *Check:* a Record that fails the filter is absent from both legs. *Check:* 80 Records outrank the one filtered-in Record on BM25 and a filtered `search` still returns it. *Check:* Vault `search` with a Filter leaf that omits the collection qualifier on a Projector column is `invalid`.

## 5. Edges

**Retired.** Edges were Schema fields (SCH-11). Scheda does not store or validate graph links. There is no `walk` / `walk_inverse`. A consumer may put target ids in Record bytes and follow them after `get`.

## 6. What this document does not decide

SQL as a caller API — forbidden as the main surface (`07`). An implementation may use SQL internally.

Filesystem watcher — none: the indexer polls `HEAD`, and an uncommitted edit is not indexed.

Vectors of two models at once — not kept: a model change is the caller's `reindex`.

Server-side Index for huge Vaults — replacement behind this API (`10`), not a second primary layer.

The Rust type of `Projector` on `open` — the binding's affair (`07`).
